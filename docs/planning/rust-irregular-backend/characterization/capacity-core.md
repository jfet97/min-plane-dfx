## 1. Purpose and role in Compact / Compact Short Side execution

All four files are **live on the production Compact path**, and — indirectly, through the placed/unplaced partition they can produce — also feed the production Compact Short Side path. This is proven by call-graph tracing, not assumed:

- `src/workers/algorithm/irregular/computeIrregularNesting.ts` is the coordinator for both profiles. Its function `coordinateIntrinsicSharedArchive` (`computeIrregularNesting.ts:474`) is guarded by `isIntrinsicSharedArchiveEligible(input.settings)` (`computeIrregularNesting.ts:483`, defined at `computeIrregularNesting.ts:1695-1697`), which delegates to `intrinsicSharedArchiveEligibility` in `src/shared/irregular/executionMode.ts:16-35`. That function returns `eligible: true` only when `optimizer.intrinsicSharedArchiveEnabled === true`, the placement policy is not `'short-side-fill'`, and GA is effectively disabled (`gaEnabled !== false` would disable eligibility) — this is documented there as "the production Compact shared archive" (`executionMode.ts:15`).
- Inside `coordinateIntrinsicSharedArchive`, when `archiveEnabled`, `preflightIntrinsicCompleteCapacity` (this cluster) is **always called first**, before the complete/sheetless archive search runs (`computeIrregularNesting.ts:526-531`).
  - If preflight proves impossibility (`preflight.kind === 'proven_impossible'`), the complete/sheetless archive is **skipped entirely** and `runIntrinsicCapacityMode` is invoked immediately with `routing: 'preflight-proven-impossible'` (`computeIrregularNesting.ts:570-594`).
  - If preflight is inconclusive, the complete/sheetless archive portfolio runs (`runIntrinsicSharedArchivePortfolio`, `computeIrregularNesting.ts:641` and surrounding), and only **if that complete search produces no fitting winner** (`winner === undefined`, `computeIrregularNesting.ts:959`) is `runIntrinsicCapacityMode` invoked again, this time with `routing: 'bounded-complete-archive-miss'` (`computeIrregularNesting.ts:960-978`).
- In both capacity-routed cases, the resulting `IntrinsicCapacityEndpoint` is converted into the coordinator's working `selected` result by `materializeIntrinsicCapacityResult` (`computeIrregularNesting.ts:1255-1320`), which builds an `IrregularBeamState` directly from `endpoint.placedCollisionGeometries` / `endpoint.unplacedPreparedIds` / `endpoint.placedPreparedIds` (`computeIrregularNesting.ts:1262-1267`).
- **Short Side dependency on capacity output:** further down, the Short Side directional construction derives its exact target placed-ID set from `selected.placedCollisionGeometries` (`computeIrregularNesting.ts:1141-1148`, `directionalTargetIds`/`directionalPreparedPieces`), not from the complete-archive endpoints directly. When the complete-archive route was bypassed (preflight proven impossible) or missed, `selected` **is** the capacity endpoint materialized by this cluster. Consequently, whenever Compact itself resolves through capacity mode, Compact Short Side's directional construction target set is exactly the capacity endpoint's placed/unplaced partition. This matches migration-prompt section 12, rule 1-2 ("Compact first selects the exact placed and unplaced piece-ID partition. Short Side receives that settled partition ...") — the capacity endpoint is one of the two possible sources of that settled partition (the other being the complete/sheetless archive winner).
  - Note: when preflight proves impossibility, `settledCompleteArchiveForShortSideObserver` stays as the empty array assigned at `computeIrregularNesting.ts:505` (it is only reassigned to the real sheetless archive at `computeIrregularNesting.ts:938`, inside the "inconclusive preflight" branch). The Short Side observer (`observeIntrinsicShortSideOrientations`, a different cluster) therefore runs with zero archive endpoints, but its `productionPlacedCollisionGeometries` input is still `selected.placedCollisionGeometries` (`computeIrregularNesting.ts:1088-1089`), i.e., the capacity-produced geometry. This is out of scope for deep analysis here (Short Side internals are a different cluster) but is recorded because it establishes that this cluster's output participates in Short Side even in the "archive skipped" case.
- `intrinsicCapacityPreflight.ts`'s `IntrinsicCapacityError` class is also imported (error-type reuse only, not logic reuse) by `intrinsicSharedArchivePortfolio.ts:39` and by `intrinsicCapacitySearch.ts` and `intrinsicPlaceDeferCompleteShadow.ts` and `intrinsicCapacityTelemetry.ts`.
- `intrinsicCapacityMaterial.ts` and `intrinsicCapacityEndpoint.ts` are shared utility/type modules consumed by the live search itself (`intrinsicCapacitySearch.ts`, not fully read for this cluster but traced — see section 2) and by prefix reuse (`intrinsicCapacityPrefixes.ts`) and by the non-authoritative shadow telemetry module (`intrinsicCapacityTelemetry.ts`) and by the experimental place/defer shadow (`intrinsicPlaceDeferCompleteShadow.ts`).

**Non-authoritative / shadow callers found during tracing** (do not affect selection, only diagnostics):
- `intrinsicCapacityTelemetry.ts` computes `measureIntrinsicCapacityShadowTelemetry` only when `input.options?.captureCapacityShadowTelemetry === true` (`computeIrregularNesting.ts:539-545`); its result (`capacityShadowTelemetry`) is attached to the compute result only as diagnostics, never consulted for routing.
- `runIntrinsicCapacityCohesionShadow` (`intrinsicCapacityMode.ts:1077-1129`) is an **observer-only** independent search run (`retentionMode: 'cohesion-frontier-shadow'`) gated by `input.captureCohesionShadow === true`; its endpoint is only ever handed to `input.onCohesionShadowLane` callback and stored in the trace's `cohesionShadow` field — it is explicitly documented as `outputInfluence: 'none'` (`intrinsicCapacityMode.ts:1118`) and never enters `retainIntrinsicAnytimeArchiveNamespace`.
- Independent warm-prefix lane telemetry captured when `captureWarmPrefixTelemetry === true` and coordination is not active (`intrinsicCapacityMode.ts:1244-1296`) is also non-authoritative unless `admitWarmPrefixEndpoints === true` is separately passed by the caller — see section 9.

**Conclusion:** `intrinsicCapacityPreflight.ts`, `intrinsicCapacityMaterial.ts`, and `intrinsicCapacityEndpoint.ts` are unconditionally live whenever the production shared-archive path (`intrinsicSharedArchiveEligibility`) is active — preflight always runs. `intrinsicCapacityMode.ts`'s `runIntrinsicCapacityMode` is live specifically on the two "capacity fallback" branches (proven-impossible and complete-archive-miss), which are exactly the branches the migration prompt's "capacity" scope section (11) and "Complete Compact semantics" section (10, rule 6: "A fitting complete endpoint dominates every capacity endpoint") describe. None of the four files are reachable from the excluded rectangular nesting algorithm.

## 3. Data in/out: exact types/shapes, optional-field presence/omission semantics

### `IrregularPreparedPiece` (input, `src/shared/irregular/domain.ts:644-676`)

Constructed with `declare readonly pieceId?: PieceId | undefined` and similar `declare` fields; the constructor only assigns a field **if the caller's `fields` object has the own property** (`Object.prototype.hasOwnProperty.call(fields, 'pieceId')`, lines 662-664, 665-667, 672-674). This means `pieceId` can be genuinely **absent** (property not present on the instance at all, `'pieceId' in piece === false`) as opposed to **present with value `undefined`**. `intrinsicCapacityPreparedPieceId` (`intrinsicCapacityMaterial.ts:9-11`) uses `piece.pieceId ?? piece.source.id`, which treats "absent" and "present-but-undefined" identically (both read as `undefined` through normal property access), so this cluster is insensitive to that distinction — but a Rust port that intends to reproduce the schema's "legacy payloads fall back to source.id" comment (`domain.ts:632`) exactly should still model `pieceId` as `Option<PieceId>` with no meaningful "absent vs. None" split for this cluster's purposes.

`piece.collisionGeometry` (`CollisionGeometry`, `domain.ts:572-598`) has both:
- `convexHull: IrregularPolygon` — the **unpadded** hull, used only by `preparedPieceDoubledMaterialAreaGrid2` (`intrinsicCapacityMaterial.ts:44-48`) for the material-area authority.
- `collisionPolygon: IrregularPolygon` — the **padded** polygon, used only indirectly by preflight via `geometryKernel.transformCollisionGeometry` (see section 2).

`piece.transforms: ReadonlyArray<IrregularTransformCandidate>` — preflight requires this to be non-empty per piece (`intrinsicCapacityPreflight.ts:102-109` fails with `IntrinsicCapacityError` operation `'preflightTransforms'` otherwise).

### `IntrinsicCapacityPreflightOutcome` (output of preflight, `intrinsicCapacityPreflight.ts:40-55`)

A discriminated union with `kind: 'proven_impossible' | 'inconclusive'`. The `'proven_impossible'` variant further discriminates on `reason: 'singleton-transform-set-does-not-fit' | 'minimum-collision-area-exceeds-sheet-area'`; only the first reason carries a `pieceId` field. All three variants carry the full `measurements` object (`IntrinsicCapacityPreflightMeasurements`, `intrinsicCapacityPreflight.ts:24-38`) — none of its fields are optional; `sheetDoubledAreaGrid2` and `minimumDoubledCollisionAreaSumGrid2` are `bigint`, `minimumCollisionAreaPressurePpm`/`maximumSingletonSpanPressurePpm` are `bigint` "parts per million" values, `singletonInfeasiblePieceIds` is a `ReadonlyArray<PieceId>` that may be empty.

### `IntrinsicCapacityMaterialAreas` result (`intrinsicCapacityMaterial.ts:51-66`)

A discriminated union: `{ kind: 'complete', areasByPieceId: ReadonlyMap<PieceId, bigint> }` or `{ kind: 'invalid', pieceId: PieceId }`. There is no partial/complete map on failure — the whole computation is fail-fast (see sections 4, 13).

### `IntrinsicCapacityEndpoint` (`intrinsicCapacityEndpoint.ts:40-54`)

Notable fields whose declared type is `X | undefined` **without** a `?:` optional marker — meaning the key is always structurally present on the object literal but may legitimately hold the value `undefined`:
- `sourceRole: string | undefined` (line 42)
- `prefixDepth: number | undefined` (line 43)

Both are populated only for `origin: 'prefix-incumbent'` (via `terminalizeIntrinsicCapacityPrefixEndpoints`, which always supplies `sourceRole`/`prefixDepth`) and for `origin: 'warm-prefix-continuation'` (via the coordinator, which also always supplies them); they are `undefined` for `origin: 'cold-search'` (see `materializeIntrinsicCapacityEndpoint`'s `input.sourceRole`/`input.prefixDepth` being themselves optional parameters at `intrinsicCapacityEndpoint.ts:149-150`, and the cold search calling this without them).

`selectedRotationDeg: 0 | 90` — a genuine two-value literal type, never a general angle.

`placedCollisionGeometries: ReadonlyArray<IrregularPlacedPiece>` — oriented, bottom-left anchored (per doc comment line 51).

### `IntrinsicCapacityEndpointMetrics` (`intrinsicCapacityEndpoint.ts:18-32`) — mixed bigint / string / number representation of the same conceptual quantities:
- `placedDoubledMaterialAreaGrid2: bigint` (native bigint)
- `totalEnclosedCavityDoubledAreaGrid2: string` (bigint **encoded as a base-10 string**, not a bigint)
- `envelopeAreaGrid2: string` (same encoding)
- All the `...Mm2`/`...Mm`/`...Grid` sibling fields are plain `number` (float mm or integer grid, respectively — see section 7).

This bigint-vs-string split is a genuine hazard: `placedDoubledMaterialAreaGrid2` is compared directly as a bigint in the comparator (`compareBigintDescending`, `intrinsicCapacityEndpoint.ts:278-281`), while `totalEnclosedCavityDoubledAreaGrid2` and `envelopeAreaGrid2` are round-tripped through `BigInt(stringValue)` inside the comparator (`intrinsicCapacityEndpoint.ts:336-337,340`) before being compared. A Rust port must reproduce both representations exactly if any external boundary (checkpoint bytes, decision trace, canonical JSON) observes these fields as encoded — this is why section 15 flags it as an open question for the checkpoint-encoding cluster to resolve definitively, but this document records the fact precisely because it originates here.

### `IntrinsicCapacityObjective` (`intrinsicCapacityEndpoint.ts:57-73`)

A pure projection of `IntrinsicCapacityEndpoint` used only for comparison and for trace display (it drops `placedPreparedIds`/`unplacedPreparedIds`/`placedCollisionGeometries`/`selectedRotationDeg`/`metrics.placedMaterialAreaMm2` — the last of which is separately re-added at call sites that need it, e.g. `intrinsicCapacityMode.ts:1399`, `intrinsicCapacityIncumbentTrace` at `intrinsicCapacityMode.ts:75`).

### `RunIntrinsicCapacityModeInput` (`intrinsicCapacityMode.ts:345-381`)

Nearly all fields beyond `sheet`, `preparedPieces`, `routing`, `preflight`, `prefixSources` are `readonly x?: T` **true optionals** (using `?:`), and the function body uses the conditional-spread idiom `...(x === undefined ? {} : { x })` extensively when forwarding them into `runIntrinsicCapacityColdSearch` (e.g. `intrinsicCapacityMode.ts:420-428,577-583,626-632,692-698,779-782,816-819`). This is the opposite convention from `IntrinsicCapacityTrace` (below) — here, absent optional input fields are genuinely **omitted** from the downstream call's argument object rather than passed through as `undefined`-valued keys, which matters if the downstream function distinguishes "key absent" (falls back to its own default) from "key present with `undefined` value" (which, for a plain TypeScript object type, is usually indistinguishable, but the coding convention itself needs to be reproduced faithfully if the downstream Rust equivalent uses `Option` fields with different defaulting per absent-vs-`None` — flagged for the capacity-search cluster to confirm).

### `IntrinsicCapacityTrace` (`intrinsicCapacityMode.ts:175-197`)

By contrast, this **output** trace object's construction (`intrinsicCapacityMode.ts:1356-1409`) assigns every declared key unconditionally, even when the value is `undefined` (e.g. `cohesionShadow: cohesionShadow?.trace`, `laneCoordinator: coordinated?.trace`, `preflightRuntimeMs: input.preflightRuntimeMs`) — it does **not** use the `...(x === undefined ? {} : {x})` omission idiom used elsewhere in `computeIrregularNesting.ts` for the surrounding result object (e.g. `computeIrregularNesting.ts:1221-1237`). Practically, `JSON.stringify` would drop these `undefined`-valued keys on serialization (producing byte-identical output to true omission), and `vitest`'s `toEqual` treats `{a: undefined}` as equal to `{}`, so existing tests would not currently distinguish the two conventions — but a Rust port targeting **byte-identical JSON** (per migration-prompt section 9) must know which convention applies at each key. This is recorded as an open question in section 15 for whichever module actually serializes `IntrinsicCapacityTrace` to canonical JSON/checkpoint bytes (not one of this cluster's four files).

## 4. Algorithm state and every mutation point

None of the four files hold module-level mutable state or class instance state; `IntrinsicCapacityError` and all interfaces are plain/immutable. All mutation is local to a single function call, using `let`, array `.push`, `Map.set`, or `Set.add`. Enumerated exhaustively:

## 5. Ordering sources

**Explicit sorts (all `Array.prototype.toSorted`, which is non-mutating and — per JS spec — stable):**
1. `intrinsicCapacityEndpoint.ts:199-202` — `legal.toSorted((first, second) => first.hash.localeCompare(second.hash) || first.rotationDeg - second.rotationDeg)[0]`. Chooses which of the (at most two) legal q0/q90 orientations becomes the endpoint's canonical geometry. Primary key: `localeCompare` on the hex SHA-256 hash string (see section 12 for the localeCompare hazard); tie-break: numeric rotation (`0` before `90`).

## 6. Comparators and tie rules

### `compareIntrinsicCapacityObjectives(first, second)` (`intrinsicCapacityEndpoint.ts:324-347`)

The authoritative total order for all capacity endpoints (used directly and via `compareIntrinsicCapacityEndpoints`, which projects both operands through `intrinsicCapacityObjective` first, `intrinsicCapacityEndpoint.ts:289-297`). Implemented as a JS `||`-chain over numeric sub-comparators; because `0` is falsy in JS, the chain proceeds to the next key **only when the previous key compares exactly equal**. Exact order, exact sign, and exact meaning of each step:

1. `second.placedCount - first.placedCount` — **descending** `placedCount` (endpoint with more placed pieces sorts first / "less than").
2. `compareBigintDescending(first.placedDoubledMaterialAreaGrid2, second.placedDoubledMaterialAreaGrid2)` (`intrinsicCapacityEndpoint.ts:278-281`) — **descending** unpadded placed material area (more material wins). `compareBigintDescending` returns `0` on equality, else `-1`/`1` via `first > second`.
3. `first.enclosedCavityCount - second.enclosedCavityCount` — **ascending** cavity count (fewer cavities wins).
4. `compareBigintAscending(BigInt(first.totalEnclosedCavityDoubledAreaGrid2), BigInt(second.totalEnclosedCavityDoubledAreaGrid2))` (`intrinsicCapacityEndpoint.ts:349-352`) — **ascending** cavity area, after parsing the field's string encoding back into `bigint`.
5. `first.envelopeMaximumSideGrid - second.envelopeMaximumSideGrid` — **ascending** intrinsic maximum side in **integer grid units**, plain `number` subtraction (not bigint).
6. `compareBigintAscending(BigInt(first.envelopeAreaGrid2), BigInt(second.envelopeAreaGrid2))` — **ascending** envelope area, again string-to-bigint round trip.
7. `first.envelopeSpanGrid - second.envelopeSpanGrid` — **ascending** envelope span, plain `number` subtraction.
8. `first.canonicalGeometryHash.localeCompare(second.canonicalGeometryHash)` — **ascending**, locale-sensitive string compare of the 64-hex-char SHA-256 digest (see section 12 hazard).
9. `intrinsicCapacityOriginRank(first.origin) - intrinsicCapacityOriginRank(second.origin)` (`intrinsicCapacityEndpoint.ts:354-356`) — `'cold-search'` ranks `0`; both `'prefix-incumbent'` and `'warm-prefix-continuation'` rank `1`. **Ascending**, so a `'cold-search'`-origin endpoint is preferred over an otherwise-tied prefix/warm-continuation endpoint.
10. `(first.prefixDepth ?? -1) - (second.prefixDepth ?? -1)` — **ascending**, with a missing `prefixDepth` treated as `-1` (sorts before any real, non-negative depth).
11. `(first.sourceRole ?? '').localeCompare(second.sourceRole ?? '')` — **ascending**, locale-sensitive, missing `sourceRole` treated as `''` (sorts before any non-empty role name).

This is a genuine 11-key total order; ties surviving all 11 keys mean the two endpoints are indistinguishable in every field the comparator inspects (they may still differ in fields it does not inspect, e.g. `origin` was already resolved at step 9, `placementOrder`/`unplacedPreparedIds` are never compared at all — two endpoints with the same hash/material/cavity/envelope numbers but a different **placement order** producing the same canonical geometry are treated as equal by this comparator).

### `IntrinsicCapacityEndpoint` orientation tie-break (`intrinsicCapacityEndpoint.ts:199-202`)

Two-key comparator over at most 2 elements: `hash.localeCompare(hash) || rotationDeg - rotationDeg`. Practically this means: prefer whichever of q0/q90 produces the lexicographically-smaller (locale order) canonical hash; if by coincidence both rotations somehow hashed identically (would imply identical canonical geometry, essentially impossible for a nondegenerate placement set), prefer `0` over `90`.

### `intrinsicCapacityLaneCoordinatorTraceValid` (`intrinsicCapacityMode.ts:200-314`)

Not a ranking comparator but a **structural chronology validator** — asserts monotonic `fromDepth <= toDepth`, non-negative deltas, `ordinal === index`, per-lane quantum-chain contiguity (`quantum.fromDepth === previous.toDepth`), and that the evaluation-delta sum equals the reported aggregate. Used only by tests/gates (`scripts/irregular-capacity-gate.ts:1132`), never by production control flow. Its exact rules are recorded here because a Rust port that wants an equivalent self-check must reproduce these exact inequalities (`>` vs `>=`, line 206-207 uses strict `>` against the cap, meaning consuming exactly the cap is valid).

## 7. Numeric semantics

### `toGridMm` (`src/workers/irregular/clipper2OffsetPolicy.ts:44-53`) — shared dependency, exhaustively load-bearing for this cluster

```
scaledAbsoluteValue = Math.abs(valueMm) * 1000
roundedAbsoluteValue = Math.floor(scaledAbsoluteValue + 0.5)
gridValue = Math.sign(valueMm) * roundedAbsoluteValue
return Number.isSafeInteger(gridValue) ? gridValue : undefined
```
- Rejects non-finite input up front (`Number.isFinite` guard, line 45) and rejects a non-finite scaled value (line 48).
- Rounding is "nearest, ties away from zero" via `floor(x + 0.5)` on the **absolute** value, then the sign is reapplied — this is the documented policy (`CLIPPER2_OFFSET_POLICY.rounding`, `clipper2OffsetPolicy.ts:13`).
- **Signed zero hazard**: `Math.sign(-0)` returns `-0` in JS. If `valueMm` is `-0` (or any value whose scaled-and-rounded magnitude is `0`, e.g. `valueMm` in `(-0.0005, 0)`), then `gridValue = -0 * 0 = -0` (in IEEE-754, `-0 * 0 === -0`). `Number.isSafeInteger(-0)` is `true` (since `-0 === 0` numerically), so `toGridMm` **can return `-0`**, a signed-zero grid coordinate, for negative-but-effectively-zero input. This propagates into every span/area computation in this cluster that calls `toGridMm` (`intrinsicCapacityPreflight.ts:79-80,244-245`, `intrinsicCapacityMaterial.ts:23-24`, `intrinsicCapacityEndpoint.ts:122-125`). A Rust `f64`/rounding-to-`i64` port must decide explicitly whether `-0.0_f64 as i64` or an equivalent sign-preserving path is required to match; since these values ultimately become bigint area terms, `-0` vs `0` grid coordinates are numerically identical in subsequent bigint arithmetic (subtraction/multiplication), so this is very likely unobservable **downstream of grid conversion** in this cluster specifically — but it is exactly the kind of "signed zero normalization" the migration prompt (section 8.1) requires auditing, so it is recorded here explicitly rather than assumed harmless.
- `Number.isSafeInteger` guard means very large millimeter inputs (beyond ~9,007,199,254 mm at scale 1000) become `undefined`, which this cluster always treats as an `IntrinsicCapacityError` or a `return undefined` propagating to endpoint-materialization failure (never silently treated as `0`).

### Exact bigint arithmetic (this cluster's real numeric authority)

- `exactDoubledPolygonAreaGrid2` (`intrinsicCapacityMaterial.ts:17-37`) — the shoelace formula computed entirely in `bigint`: `doubled += first[0]*second[1] - second[0]*first[1]` (line 33), then `magnitude = doubled < 0n ? -doubled : doubled` (line 35), returning `undefined` if `magnitude` is not `> 0n` (line 36) — i.e., a degenerate (zero-area, including exactly collinear or fewer-than-3-effective-vertex) ring is treated as **invalid**, never as a legitimate zero. Because this is exact integer arithmetic, term order is mathematically irrelevant (bigint addition is associative/commutative and lossless) — a genuine positive finding for section 13 (safe to reduce in any order, unlike a floating-point shoelace sum would be).
- `sheetDoubledAreaGrid2 = 2n * BigInt(sheetWidthGrid) * BigInt(sheetHeightGrid)` (`intrinsicCapacityPreflight.ts:94`) — exact.
- `scaledRatioCeilPpm(numerator, denominator) = (numerator * 1_000_000n + denominator - 1n) / denominator` (`intrinsicCapacityPreflight.ts:226-229`) — exact ceiling division for non-negative bigints (relies on both operands being `>= 0`, which holds here since numerator/denominator are always areas or grid spans/dimensions). BigInt division truncates toward zero; for non-negative operands this equals floor division, and the `+ denominator - 1n` idiom yields the mathematical ceiling exactly.
- `doubledGrid2ToMm2(doubledAreaGrid2) = Number(doubledAreaGrid2) / 2_000_000` (`intrinsicCapacityMaterial.ts:69-71`, constant `DOUBLED_GRID2_PER_MM2` at line 6) — this is the **one lossy conversion** in this cluster: `Number(bigint)` truncates/rounds to the nearest representable `f64` once the bigint exceeds `2^53`, which is realistically unreachable for physical sheet/piece areas but is a documented boundary (`Number.isSafeInteger` is *not* re-checked here — this function will silently produce an imprecise `number` for an extreme bigint rather than failing). This value (`placedMaterialAreaMm2`) is display/diagnostic-only, never fed back into the exact comparator (which uses the bigint field directly).

### Parts-per-million pressure metrics (`intrinsicCapacityPreflight.ts:195-229`)

`minimumRigidSpanPressurePpm` takes the **minimum** of the q0-pressure and q90-pressure for one transform (line 200-212: `q0 < q90 ? q0 : q90`); `maximumRatioPpm` takes the **maximum** of two axis-ratio pressures for one orientation (line 215-224: `first > second ? first : second`). All four comparisons are exact bigint comparisons on already-ceiling-rounded ppm values — no floating point involved after the initial `toGridMm` conversion. These pressure metrics are diagnostic-only (never gate `proven_impossible`; only `singletonInfeasiblePieceIds` non-emptiness and `minimumDoubledCollisionAreaSumGrid2 > sheetDoubledAreaGrid2` do, per lines 175-190).

### `transformedGridSpan` (`intrinsicCapacityPreflight.ts:236-254`)

Uses `Math.min`/`Math.max` accumulated over `toGridMm`-converted points, with `Number.POSITIVE_INFINITY`/`NEGATIVE_INFINITY` sentinels (lines 239-242) and a final `Number.isFinite`-on-all-four guard (line 252) that returns `undefined` for an empty `points` array or any non-finite bound — this never crashes, always fails soft into `IntrinsicCapacityError` upstream (`intrinsicCapacityPreflight.ts:121-128`).

### No `NaN`-producing paths found

`transforms.length === 0` and empty-`points` are both explicitly guarded (see above); no division by a value that could be zero was found unguarded (`scaledRatioCeilPpm`'s `denominator` is always a positive grid dimension, already validated `> 0` at `intrinsicCapacityPreflight.ts:81-93`).

## 9. Caches touched and the exact historical access sequence

Only one true cache exists in this cluster: `IntrinsicCapacityCavityCache = Map<string, IntrinsicCapacityCavityMetrics>` (`intrinsicCapacityEndpoint.ts:82`).

**`measureIntrinsicCapacityCavities(state, cache)` (`intrinsicCapacityEndpoint.ts:89-109`) — the complete access sequence, in order:**
1. Fast path: if `state.placedCollisionGeometries.length === 0`, return the constant `{ count: 0, totalAreaMm2: 0, totalDoubledAreaGrid2: '0' }` **without touching the cache at all** (lines 93-95).
2. Compute `occupiedKey = state.bottomLeftAnchoredCanonicalOccupiedGeometryKey()` (line 96) — a translation-independent canonical identity key (derivation is a different cluster's concern; this cluster only uses it as an opaque cache key). If `undefined`, return `undefined` immediately (line 97) — **no cache lookup, no cache write** for a state whose key cannot be computed.
3. `cache.get(occupiedKey)` — a lookup (line 98). On hit, return the cached value immediately (line 99) — **no recomputation, no re-validation of the cached value beyond object identity**; the migration prompt's "invalid or stale values are never published as valid hits" requirement is satisfied structurally here because nothing ever stores an invalid value (see step 5).
4. On miss, compute `measureCanonicalEnclosedCavities(state.placedCollisionGeometries)` (line 100) — expensive geometry, a different cluster's concern. If it returns `undefined` (geometrically invalid), return `undefined` **without writing anything to the cache** (line 101) — i.e., **invalid results are never cached**, matching migration-prompt section 13.2's explicit requirement.
5. On success, build a plain `{ count, totalAreaMm2, totalDoubledAreaGrid2 }` object (lines 102-106) and `cache.set(occupiedKey, metrics)` (line 107) — the sole write, always immediately followed by `return metrics` (line 108).

This is a strict **read-then-conditionally-write single-flight-free** cache (no locking needed in the current single-threaded TypeScript execution; a Rayon port would need either a per-job-owned single-threaded cache during this phase or an explicit concurrency policy per migration-prompt section 13.5, since two threads racing on the same `occupiedKey` today would, in TS, simply both recompute and both write the same value — safe only because recomputation is guaranteed to be deterministic and idempotent, i.e., "a cache hit and a recomputation must return the same canonical immutable value," which holds here by construction since the key is a canonical geometry fingerprint).

**Cache lifetime:** every `IntrinsicCapacityCavityCache` instance is freshly constructed per call site (`new Map()` at `intrinsicCapacityMode.ts:413,523,574,623,687,775,810,1097,1162,1252`, and inside `intrinsicCapacityPrefixes.ts`/`intrinsicCapacitySearch.ts` similarly, not exhaustively enumerated here as those are different-cluster call sites) — **there is no cross-job or cross-call persistence of this cache anywhere in this cluster.** Each `runIntrinsicCapacityColdSearch` invocation, each coordinator lane, and the top-level `runIntrinsicCapacityMode` call each get their own fresh cache instance, meaning the SAME occupied-geometry key can be recomputed independently by different lanes/searches within one job — this is a measured, accepted duplicate-computation cost in the current TypeScript implementation, not a bug, and the migration prompt's guidance to "measure duplicate count and wasted CPU" (section 13.5) applies directly here as an optimization opportunity for the Rust port (a job-scoped shared cavity cache keyed by canonical occupied-geometry identity would be a safe, semantics-preserving improvement — cache contents never decide algorithmic order per section 13.1, and this key is already translation/rotation-topology-invariant per the doc comment at `intrinsicCapacityEndpoint.ts:85-88`).

`areasByPieceId` (`Map<PieceId, bigint>`, produced once per `intrinsicCapacityMaterialAreas` call, `intrinsicCapacityMaterial.ts:56-65`) is not a "cache" in the reuse sense — it is a **complete precomputed table**, built once per job/search invocation and threaded through by value (`materialAreasByPieceId` parameter) to every endpoint-materialization call. It has no partial-hit/miss semantics; every `.get` on it during normal operation is expected to succeed (a miss during `sumMaterialAreas`, `intrinsicCapacityEndpoint.ts:271-272`, indicates a piece-id/state inconsistency bug, not a legitimate cache miss, and causes `materializeIntrinsicCapacityEndpoint` to return `undefined`).

## 12. JS-specific semantics hazards for a Rust port

1. **`String.prototype.localeCompare` without arguments, used three times as an ordering/tie-break key** (`intrinsicCapacityEndpoint.ts:201` for orientation selection; `intrinsicCapacityEndpoint.ts:342` for the primary hash tie-break in the capacity objective comparator; `intrinsicCapacityEndpoint.ts:345` for the `sourceRole` tie-break). `localeCompare` without an explicit locale uses the JS engine's default (ICU, in Node.js) collation, which is **not** guaranteed to equal byte/codepoint ordering in general. The compared strings here are: (a) lowercase hex SHA-256 digests (charset `[0-9a-f]`), and (b) short lowercase-hyphenated role identifiers (`'cold-search'`, `'canonical-grid'`, `'open-pocket-first'`, `'legacy-absolute-envelope'`, `'prefix-incumbent'`, `'warm-prefix-continuation'`, or `''`). For pure ASCII digit/lowercase-letter/hyphen strings, ICU root/en-US collation is very likely to coincide with simple byte ordering, but **this is an empirical claim that must be verified with a differential test against Node's actual ICU build before a Rust port substitutes a plain byte-wise `Ord` for `str`**, per migration-prompt section 9's explicit warning ("do not assume Rust byte ordering matches JavaScript ... `localeCompare`"). This is the single highest-value differential test to write for this cluster.
2. **Signed-zero grid coordinates possible from `toGridMm`** (see section 7) — `Math.sign(-0) === -0` combined with `-0 * 0 === -0` in JS means a slightly-negative-of-zero millimeter input can produce a `-0` grid integer. Confirmed unobservable *within this cluster's* subsequent bigint arithmetic (subtraction/multiplication treat `-0`/`0` identically once cast to `bigint` via `BigInt(gridValue)`, since `BigInt(-0) === 0n`), but flagged because the migration prompt requires an explicit audit, not an assumption.
3. **`Array.prototype.toSorted` stability reliance** — every sort in this cluster (`intrinsicCapacityEndpoint.ts:199`, `intrinsicCapacityMode.ts:497`, `intrinsicAnytimeArchive.ts:44`) relies on stable sort to preserve well-defined tie order among elements the comparator does not fully distinguish (e.g. same-depth prefix descriptors at `intrinsicCapacityMode.ts:495-497`). Rust's `slice::sort`/`sort_by` (used via `Vec`, not `sort_unstable_by`) **is** stable, so this is a straightforward requirement, not a hard problem — but it must be a conscious choice (`sort_by`, never `sort_unstable_by`) in the port.
4. **`Map`/`Set` insertion-order dependence** — as detailed in section 5: safe in the several dedup-then-resort cases (Rust `HashMap` acceptable there, given the same immediate full re-sort discipline), but **not** safe for `continuedLaneIndexes` (`intrinsicCapacityMode.ts:557,595,718,966`), which must become an explicit `Vec<usize>` (or equivalent ordered structure) in Rust, not a `HashSet`.
5. **`||`-chain comparator idiom relying on `0` being falsy** — the entire `compareIntrinsicCapacityObjectives` function (`intrinsicCapacityEndpoint.ts:328-346`) is one big `||` expression across 11 numeric sub-results. A literal Rust translation must use `Ordering::Equal` short-circuiting (`then_with`), not naive numeric `||`, but must preserve the *exact same 11-step order and exact same sign* per step (see section 6) — an easy place to introduce a silent sign inversion during translation, which the migration prompt explicitly forbids changing ("comparison signs," "ranking winners," "stable tie order").
6. **`bigint`-vs-`string`-encoded-bigint field split** on `IntrinsicCapacityEndpointMetrics`/`IntrinsicCapacityObjective` (section 3) — a Rust port must decide a single internal representation (e.g. `i128` or an arbitrary-precision type everywhere) but must still reproduce the **string round-trip exactly** if any byte-level boundary (checkpoint, trace JSON) currently observes the string form; this is flagged again here as a semantics hazard specifically because it is easy to "simplify" away during a naive port and thereby change canonical JSON bytes.
7. **Effect-generator-based cooperative sequencing** (`Effect.gen(function* () { ... yield* ... })`) throughout `intrinsicCapacityMode.ts`/`intrinsicCapacityPreflight.ts` gives the current implementation strictly serial, single-threaded execution with well-defined interleaving points exactly at `yield*` boundaries. A Rust/Rayon port introducing any real concurrency inside what is currently one Effect generator body must reconstruct the same "which checkpoint sees which partial state" chronology described in sections 4 and 10, per migration-prompt section 14.
8. **`Object.prototype.hasOwnProperty`-gated optional-field construction** on `IrregularPreparedPiece` (section 3) — a general TS/JS idiom (own-property presence vs. `undefined` value) that has no direct Rust analogue; this cluster happens not to be sensitive to the distinction (`?? piece.source.id` collapses both), but other clusters reading the same `IrregularPreparedPiece` type may be sensitive to it, so it is worth flagging for the orchestrator's cross-cluster awareness even though it is a "None" finding for capacity-core specifically.

## 13. Parallelism assessment

**Safe-to-investigate Rayon candidates within this cluster** (pure, independent, with a serial reduction that reproduces current chronology):

- **Per-transform geometry/area/span computation inside preflight's inner loop** (`intrinsicCapacityPreflight.ts:113-146`): for one piece, each transform's `geometryKernel.transformCollisionGeometry` call, `exactDoubledPolygonAreaGrid2`, and `transformedGridSpan` are independent of every other transform of the same piece (no shared mutable state read within the per-transform body other than write-only accumulation into per-piece `let`s that are pure min/max/or-reductions — all three of `minimumDoubledAreaGrid2` (min), `minimumSingletonSpanPressurePpm` (min), `singletonFits` (or) are associative/commutative reductions). **Condition for safety**: the `control.checkpoint('candidate-points')` call currently issued once per transform (line 114) determines *when*, mid-piece, a cancellation can interrupt work; a parallel batch-then-reduce implementation must still issue an equivalent checkpoint at a matching granularity (e.g. once before dispatching each piece's transform batch, or once per stable transform index before/after its unit of work) to avoid silently doing more or less speculative work before honoring cancellation than the current serial loop does, per migration-prompt section 14.1's explicit conditionality clause and section 15's "moving a check earlier/later can change what work occurs before termination."
- **Per-piece outer loop of preflight** (`intrinsicCapacityPreflight.ts:99-160`), similarly: `minimumDoubledCollisionAreaSumGrid2` (sum, associative for exact bigints), `maximumSingletonSpanPressurePpm` (max), and `singletonInfeasiblePieceIds` (append) could be computed per-piece in parallel and reduced serially by stable piece index — **except** `singletonInfeasiblePieceIds`'s *first* element is externally observable (`intrinsicCapacityPreflight.ts:175-182`, becomes the reported `pieceId` in the `'singleton-transform-set-does-not-fit'` outcome), so the reduction must explicitly re-sort/select by original prepared-piece index rather than by completion order — safe, but must not use "first array element pushed by whichever thread finished first."
- **`transformedGridSpan`'s point-bbox reduction** (`intrinsicCapacityPreflight.ts:236-254`) — trivial commutative min/max reduction over a small point set; not worth parallelizing at this grain (piece polygons are small, convex, typically well under a hundred points) but architecturally safe if ever needed.
- **`exactDoubledPolygonAreaGrid2`'s shoelace sum** (`intrinsicCapacityMaterial.ts:28-34`) — exact bigint arithmetic is associative and lossless, so summing shoelace terms in any order (including a parallel tree reduction) is mathematically exact, unlike an equivalent floating-point shoelace sum would be. Again, per-ring point counts are small; not a meaningful target on its own, but a genuinely safe property worth recording since it is the *opposite* of the usual floating-point-reduction-order caution.
- **The two orientation evaluations (`q0`/`q90`) inside `materializeIntrinsicCapacityEndpoint`** (`intrinsicCapacityEndpoint.ts:182-198`) — exactly two independent units of work (`withQuarterTurnBottomLeft(0)` and `withQuarterTurnBottomLeft(90)`, each followed by legality check, identity, and hashing), pushed into an array and only *afterward* resolved via a full sort (line 199-202) — there is no early-exit/first-wins logic here, so computing both concurrently and merging by stable index (`0` then `90`) is safe and requires no chronology changes.
- **Endpoint materialization across independent beam-frontier entries** (`intrinsicCapacitySearch.ts:939-968`, a different cluster's loop, but directly downstream of and dependent on this cluster's `materializeIntrinsicCapacityEndpoint`/`compareIntrinsicCapacityEndpoints`) — each `entry` in `beam` is processed independently (`materializeIntrinsicCapacityEndpoint` call, then a dedup-map write); this looks like a strong Rayon candidate for a future cross-cluster optimization (compute all beam entries' endpoints in parallel by stable index, then reduce into the dedup map and final `.toSorted` serially) — flagged here because this cluster's own functions are exactly the pure, parallelizable payload, even though the loop structure itself lives in the capacity-search cluster.

**Chronology-bound / must-stay-serial within this cluster:**

- **All of `runProtectedCapacityLaneCoordinator`** (`intrinsicCapacityMode.ts:467-999`) is explicitly sequential by design: the cold lane runs and (maybe) resumes first; only then do warm pilot lanes run (in `input.fittingDescriptors` order); only then does the single warm-resume `while` loop pick and repeatedly resume **one** lane based on a budget that is itself decremented by each prior lane's actual consumption; only then does the quality lane run and resume. Each step's budget/eligibility depends on the *actual measured* `consumedPlacementEvaluations` of every prior step (e.g. `basePlacementEvaluationCap - warmConsumedPlacementEvaluations` at line 670, `deepestQualityDescriptor`'s gating by `input.preparedPieces.length` compared against a piece-count constant that is independent of prior steps, but the quality lane's own resume loop still depends on its own accumulating `qualityResult.trace.consumedPlacementEvaluations`). This is the textbook "chronology-bound, scheduler ledger" case the migration prompt explicitly forbids racing (section 14.2: "cold versus warm lane races," "direct producer roles whose chronology affects scheduler traces," "checkpoint publication by completion order").
- **The warm-lane-resume `while` loop's single-winner selection** (`selectProtectedWarmSettlementLane`, `intrinsicCapacityMode.ts:1046-1075`, called once before the loop at line 667) explicitly picks **one** lane by a deterministic deepest-depth-then-fixed-source-priority rule and then that same lane is the only one ever resumed in the loop — this must never become "whichever lane happens to finish resuming first," which the migration prompt calls out by name (section 14.2: "Never let the first completed task win").
- **`runIntrinsicCapacityMode`'s three-way cold-search dispatch** (`intrinsicCapacityMode.ts:1180-1220`: coordinated vs. reused `scheduledColdStart` vs. fresh search) is a sequential decision tree, not a race — only one branch ever executes.
- **The final endpoint settlement** (`intrinsicCapacityMode.ts:1298-1345`: build `baseEndpoints` → dedup/rank → conditionally augment with the quality endpoint → dedup/rank again → pick `[0]` or fall back) must remain a deterministic, fully-materialized-then-sorted pipeline, not a "first candidate that satisfies X wins" race, matching migration-prompt section 14.2's "survivor selection as candidates finish" prohibition.
- **`intrinsicCapacityMaterialAreas`'s fail-fast first-invalid-piece semantics** (`intrinsicCapacityMaterial.ts:57-64`) — if parallelized across pieces, the reported failing `pieceId` must still be resolved by **stable index of the first piece in prepared order that is invalid/duplicate**, not by whichever thread detects a failure first; this is a narrow but real "first stable index, not first completion" requirement per migration-prompt section 14.3's deterministic parallel pattern.
