### `freeMaterialService.ts` — live, but only reached at most twice per completed job

Exports `FreeMaterialServiceLive` (an Effect `Layer`) and `createFreeMaterialService`. Confirmed wired into the production layer graph at `src/workers/nesting.worker.ts:25,394` (`Effect.provide(FreeMaterialServiceLive)`) and at `src/workers/irregular/infrastructure.ts:3,17`. The only production consumer of the `FreeMaterialService` context tag is `irregularLayoutScorer.ts:125` (`const freeMaterialService = yield* FreeMaterialService`), inside `IrregularLayoutScorer.Make`'s `scoreState`.

Per `search-scoring.md:92`: `IrregularLayoutScorer.Service.scoreState` is called from **exactly one of four mutually-exclusive `materialize*` functions** in `computeIrregularNesting.ts`, each executed **at most once per run**: `materializeIntrinsicCapacityResult` (line 1270), `materializeProductionResult` (line 1499), `materializeSharedArchiveResult` (line 1539), `materializeIntrinsicShortSideProfileResult` (line 1608).

This document adds one refinement verified by direct read of `computeIrregularNesting.ts:1000-1180`: when Compact Short Side is selected (`shortSideProfileRequested && pairFoldOutcome.trace.status === 'accepted'`), the coordinator **first** resolves Compact via one of the first three `materialize*` functions (one `.scoreState` call), **then reassigns** `selected` via `materializeIntrinsicShortSideProfileResult` (a **second** `.scoreState` call, `computeIrregularNesting.ts:1175-1180,1608`). So in a Compact Short Side job, `freeMaterialService`'s production entry points can be invoked **twice** in one job (once for the settled Compact result used as Short Side's input partition, once for the final Short Side directional result) — not "at most once" as a naive reading of `search-scoring.md`'s summary alone might suggest for the *whole coordinator*. Both calls still go through `deriveFreeMaterial`/`computeFreeMaterial` only (see next paragraph), so this refinement does not change which function bodies execute, only how many times.

**Verified: the `extendFreeMaterial` incremental path never executes in production.** `computeSnapshotWithParentFallback` (`irregularLayoutScorer.ts:159-190`) only calls `freeMaterialService.extendFreeMaterial(...)` when `parentSnapshot !== undefined`, which requires `input.state.parent !== undefined` (line 165, 168-171). Every `new IrregularBeamState({...})` construction at the four `materialize*` call sites in `computeIrregularNesting.ts` (lines ~1262-1267, ~1473-1499 vicinity, ~1524-1539 vicinity, and `materializeIntrinsicShortSideProfileResult` at lines 1597-1603) omits the `parent` field, so it is always `undefined` on the state passed to `.scoreState`. The only place in the codebase where `.extendFreeMaterial` could receive a parent-populated state is `windowedBeam.ts`'s incremental scoring loop, which `search-scoring.md` documents as **dead for production** (§1.1, confirmed independently here by checking that `IrregularLayoutScorer.Make`'s only production caller of `.scoreState` is `computeIrregularNesting.ts`). Consequently:
- `deriveExtendedFreeMaterial` (`freeMaterialService.ts:78-97`) and everything it alone reaches (`toMaterialPaths`, `toMaterialPath`, `canonicalizeWinding` in the material-path role) is **live in the public service contract and directly unit-tested** (`tests/unit/freeMaterialService.test.ts` "FreeMaterialService differential operations" describe block, lines 345+), but is **never invoked by the production job-execution path**.
- Only `deriveFreeMaterial` → `prepareOccupiedClip('union-then-difference', ...)` → `deriveSnapshotFromDifference` ever runs during a real nesting job, and it runs from a **cold** (per-job-fresh) `freeMaterialCache` each of the (at most two) times it is called, so the `MAX_FREE_MATERIAL_CACHE_ENTRIES = 256` eviction logic in `irregularLayoutScorer.ts:197-199` is never under real production pressure (257+ distinct `scoreState` calls never happen in one job today).
- `createFreeMaterialService('direct-difference')` (the other `FreeMaterialOperation` branch, skipping the union-first step at `freeMaterialService.ts:150`) has **no production caller at all** — grep confirms `createFreeMaterialService` is called with the literal `'union-then-difference'` only, at `freeMaterialService.ts:36`. `'direct-difference'` exists only for the differential test at `tests/unit/freeMaterialService.test.ts:384` ("keeps the live layer on union-then-difference").

This is a materially different liveness picture than "free-material computed on every candidate score" — it is a **once-or-twice-per-completed-job diagnostic/scoring snapshot**, not a per-search-node hot path. A Rust port's performance budget for this file should be sized accordingly (§13), while its **correctness** contract (including the never-executed `extendFreeMaterial`/`direct-difference` branches) must still be ported byte-for-byte because `tests/unit/freeMaterialService.test.ts` exercises them directly and the migration prompt (§3) forbids weakening or deleting existing tests.

## 3. Data in/out: exact types/shapes, optional-field presence/omission semantics

### `CanonicalGridPoint` (`canonicalGridMath.ts:3-6`)

```ts
export interface CanonicalGridPoint {
  readonly x: number
  readonly y: number
}
```
Both fields are plain `number`, expected (but not enforced by the type system) to be `Number.isSafeInteger` values — every function that consumes one checks this explicitly via the internal `isCanonicalGridCoordinate` predicate (`canonicalGridMath.ts:8-10`) and returns `undefined` on failure rather than throwing. There is no runtime distinction between "this point came from a `Path64`" (Clipper2's own point type, structurally identical: `{x:number,y:number}`) and "this is a `CanonicalGridPoint`" — the two are interchangeably used across the cluster (`Path64` from `clipper2-ts` is a `ReadonlyArray<{x:number,y:number}>`-compatible type used directly wherever a `CanonicalGridPoint[]` is needed, and vice versa).

### `CanonicalGridBoundaryContact` (`canonicalGridContact.ts:5-10`)

All four fields (`lengthMm`, `normalizedUnits`, `nearCompleteStructuralContactCount`, `nearCompleteStructuralContactSignatures`) are required, never optional. The zero-contact case (`canonicalGridContact.ts:79-86`) returns an object with `lengthMm: 0`, `normalizedUnits: 0`, `nearCompleteStructuralContactCount: 0`, `nearCompleteStructuralContactSignatures: []` — an explicit, fully-populated "empty" value, never `undefined` for the "no contact" case (only actual computation failure returns `undefined` for the whole function).

### `CanonicalGridBoundaryOverlapAxisUnitsResult` (`canonicalGridContact.ts:12-15`)

A three-variant discriminated union, no shared fields beyond `kind`:
- `{ kind: 'measured', score: bigint }` — the only variant carrying a payload.
- `{ kind: 'undecidable' }` — returned both for structural failure (unsafe-integer coordinates, degenerate path) **and** for the deliberate "positive diagonal contact is not comparable" case (`canonicalGridContact.ts:331`). These two very different causes are **not distinguished** in the return type — a Rust port that wants to preserve exact caller behavior does not need to distinguish them either, since the only production caller (`intrinsicShortSideContactStrip.ts:694-696`) treats `'undecidable'` uniformly as `continue` (skip this pair, do not abort the whole scan).
- `{ kind: 'aborted' }` — returned only when the optional `checkpoint` callback signals cancellation/deadline/budget expiry (§10).

### `IrregularPlacedPiece` inputs (from `@shared/irregular/domain.js`, consumed throughout this cluster)

`placedCollisionWorldGridPath` (`canonicalLayoutGeometry.ts:92-110`) reads exactly `entry.placement.transform.{translateX,translateY}` and `entry.collisionGeometry.polygon.points` — the **padded** collision polygon (per the doc comment at `freeMaterialService.ts:258-264`, `toPlacedPath` also reads `placed.collisionGeometry.polygon.points`, the padded polygon, confirming both files use the same padded-polygon field). `canonicalPlacedPolygons` (`canonicalLayoutGeometry.ts:501-517`) additionally reads `entry.placement.pieceId ?? entry.placement.sourcePieceId` — the same `??` fallback-to-source-id idiom documented for `intrinsicCapacityPreparedPieceId` in `capacity-core.md:89`.

### `CanonicalLayoutStructuralAnalysis` (`canonicalLayoutGeometry.ts:112-134`) — the richest output type in this cluster

Notable field: `largestHullGap: {path, areaMm2, aabb} | undefined`. The **producing** internal function `largestHullGapRegion` (`canonicalLayoutGeometry.ts:669-734`) has a genuinely **three-state** return type: `{...} | undefined | null`.
- The object payload means "a largest gap region was found."
- `undefined` means "the tree traversal succeeded but found no non-hole gap region" (`canonicalLayoutGeometry.ts:725`, `selectedPath === undefined` after a successful `visit`).
- `null` means "the computation itself failed" — either `hull.length < 3` producing a *different* early `undefined` at line 680 (not `null`; only the orientation failure at line 684, the boolean-op `catch` at line 695, the `visit` traversal failure at line 724, or the final aabb/area guard at line 728 produce `null`).

`analyzeCanonicalLayoutStructure` (`canonicalLayoutGeometry.ts:459-460`) collapses this: `if (largestHullGap === null) return undefined` (any failure aborts the whole structural analysis), then `largestHullGap: largestHullGap ?? undefined` (line 492) folds the remaining two states (found vs. not-found) into the single output field, where `undefined` in the **output** type means "no gap found," losing the distinction from "computation failed" (which instead aborted the entire function). ## 4. Algorithm state and every mutation point

None of the five files hold module-level mutable state. All mutation is local to a single function call (`let`, array `.push`, `Map.set`/`Set.add`), matching the pattern already documented for the capacity cluster (`capacity-core.md:141`). Enumerated exhaustively:

**`canonicalGridMath.ts`:**
- `canonicalGridSignedDoubledArea` (`:113`): `let doubledArea = 0n`, accumulated via `+=` once per path edge (line 127-128). Because this is exact `bigint` addition, term order is provably irrelevant to the final value (associative, commutative, lossless) — a genuine positive finding for parallel-reduction safety (§13), matching the identical observation `capacity-core.md:246` makes about `exactDoubledPolygonAreaGrid2`.

Iteration order: `firstEdges` outer, `secondEdges` inner (both in path-edge order, i.e., original vertex order — see §5).
- `measureCanonicalGridBoundaryContact` (`:58-109`): `segments: CanonicalGridBoundarySegment[] = []`, `.push` per positive-length edge-pair overlap (no early exit — computes **all** pairs, unlike `hasPositiveCanonicalGridBoundaryContact`). ## 5. Ordering sources: sorts, Map/Set insertion order, iteration order reaching output

### Explicit sorts (all `Array.prototype.toSorted`, non-mutating, spec-guaranteed stable — except `freeMaterialService.ts`'s two uses of mutating `.sort()` on freshly-spread copies, also spec-guaranteed stable since ES2019)

1. `canonicalGridMath.ts:141` — `[...new Map(points.map(p => [`${p.x},${p.y}`, p])).values()].toSorted((a,b) => a.x - b.x || a.y - b.y)` inside `canonicalGridConvexHull`. Numeric ascending by `x` then `y`, plain `Number` subtraction (see §7 for the precision caveat at extreme safe-integer magnitudes — sign is always correct, only tie-break stability among astronomically close-but-unequal values could theoretically be affected, and even then only beyond the practical coordinate range this system ever produces).
2. `canonicalLayoutGeometry.ts:149` — `identities.filter(...).toSorted()[0]` inside `canonicalCollisionLayoutIdentity`: **default** `Array.prototype.toSorted()` with no comparator, which per the ECMAScript spec coerces elements to strings and compares by UTF-16 code unit (i.e., exactly the same ordering as `<` on strings, **not** `localeCompare`). Picks the code-unit-lexicographically-smallest of the (at most 4) quarter-turn JSON identity strings. See §15 for the finding that the preceding `.some(id => id === undefined)` guard at line 147 is dead code.
3. `canonicalLayoutGeometry.ts:222-224` — `canonicalPlacedPolygons(placed)?.toSorted((a,b) => a.pieceId.localeCompare(b.pieceId))` inside `measureCanonicalLayoutContacts`. `localeCompare` with no explicit locale/options argument, i.e., default-locale-sensitive comparison — **not** code-unit. This directly determines the `firstIndex`/`secondIndex` pair-discovery order for that function's contact accumulation (§4), though since the accumulated scalars (`sharedBoundaryLengthMm`, `contactUnits`, etc.) are order-independent sums/maxes, the sort's only *externally observable* effect is on the `signatureCounts` Map's *insertion* order, which in turn is irrelevant since only `.values()` reduced via `Math.max` is read (§4). So this particular `localeCompare` sort does not change the final `IrregularLayoutScore`-visible numbers, only internal bookkeeping order — still worth preserving exactly per the migration prompt's "never assume equivalence" stance.
4. `canonicalLayoutGeometry.ts:474-479` — `wallOffenders = polygons.filter(...).map(({pieceId}) => pieceId).toSorted()` — **default** (code-unit) string sort, inside `analyzeCanonicalLayoutStructure`. This **is** externally observable: `wallOffenders` is a direct output field.
5. `canonicalLayoutGeometry.ts:491,493,494-496` — `positiveContactPairs.toSorted(comparePiecePairs)`, `positiveAreaConflicts.toSorted(comparePiecePairs)`, `positiveAreaConflictMeasurements.toSorted((a,b) => comparePiecePairs(a.pair,b.pair))` — all use `comparePiecePairs` (`localeCompare`-based, §6). 7. `canonicalLayoutGeometry.ts:565-573` — `components.toSorted((a,b) => second.length - first.length || compareBigInts(secondArea, firstArea) || first.join('|').localeCompare(second.join('|')))`. Three-key comparator: descending component size, then descending total doubled area (exact `bigint`), then `localeCompare` on the `|`-joined already-code-unit-sorted member list (from rule 6 above). This is `positiveContactComponents`, a direct output field of `analyzeCanonicalLayoutStructure`.
8. `freeMaterialService.ts:121` — `[...regions.regions].sort(compareRegions)` inside `deriveSnapshotFromDifference`. `compareRegions` delegates to `comparePolygons` (§6), a mixed numeric/`localeCompare` comparator.
9. `freeMaterialService.ts:129` — `[...region.holes].sort(comparePolygons)` — same comparator, per-region hole ordering.

### Maps used purely as O(1) lookup/dedup (iteration order not an observable ordering source)

- `canonicalGridMath.ts:139-140` — the dedup `Map` inside `canonicalGridConvexHull`: constructed from `points.map(p => [key,p])`, where the JS `Map` constructor keeps the **last** `[key,value]` pair for a repeated key (standard `Map` semantics — iterating the input array and calling `.set` in order). Because `CanonicalGridPoint` has no fields beyond `{x,y}`, which duplicate-key instance is retained is behaviorally inconsequential here — but the *fact* that "last wins" (not "first wins") is worth recording precisely for a Rust port using e.g. a `HashMap::insert` (also last-wins) or a `BTreeMap` (also last-wins on repeated insert) — both match.

- `canonicalLayoutGeometry.ts:399` — `uniqueIds = new Set(polygons.map(p => p.pieceId))` in `analyzeCanonicalLayoutStructure`: only `.size` is read (line 400, duplicate-id detection), never iterated.
- `canonicalLayoutGeometry.ts:401,534,846,861` — the various `Set<number>` adjacency/visited sets: iterated only inside DFS traversals whose *aggregate* output (component membership, counts) is proven order-independent by the immediate re-sort (§4) or by only-counting semantics.

- `freeMaterialService.ts:349` — `uniquePoints = new Set<string>()` in `validatePathStructure`: only `.has`/`.add`, never iterated.

### Plain array iteration order reaching output (not Map/Set-derived)

- `canonicalLayoutGeometry.ts:96` — `entry.collisionGeometry.polygon.points.map(...)` inside `placedCollisionWorldGridPath`: preserves the input polygon's own vertex order exactly (no reordering); this vertex order is what ultimately determines `canonicalRingDirection`'s rotation-offset search space (§6) and every edge-index-based structural-contact signature.
- `canonicalLayoutGeometry.ts:408-454,847-860` (double loops in `analyzeCanonicalLayoutStructure`/`measureContactGraph`) — outer `firstIndex` ascending, inner `secondIndex < firstIndex` ascending: this is the canonical "lower triangle, row-major" unordered-pair enumeration used **consistently** across this cluster (also in `measureCanonicalLayoutContacts`, `assertCanonicalGridLegalLayout`) — every unordered pair `{i,j}` with `i≠j` is visited exactly once, with `firstIndex` always the larger index. A Rust port must reproduce this exact enumeration order (not, e.g., `j` outer/`i` inner, and not `i<j` with `i` outer) whenever pair-discovery order is observable (it usually is not for the *sums*, but always is for any `.push`ed diagnostic array before an explicit re-sort).
- `freeMaterialService.ts:206-229` (`toMaterialPaths`) — `snapshot.regions` order then `region.holes` order, both preserved from the `FreeMaterialSnapshot` input (itself produced, when this function is used, by a prior `deriveSnapshotFromDifference` call whose `orderedRegions`/`holes` were already sorted per rule 8/9 above — so in practice `toMaterialPaths`' input is always already canonically ordered by the time it is (never, in production — see §1) invoked).

### Clipper2 `PolyTree64`/`PolyPath64` traversal order

Every recursive tree walk in this cluster (`largestHullGapRegion`'s `visit`, `measureEnclosedOccupiedCavities`'s `visit`, `largestNetRegionDoubledArea`'s `visit`, `collectTreeChildren`) uses the identical pattern: `for (let index = 0; index < parent.count; index += 1) { child = parent.child(index); ...; visit(child) }` — pre-order, child-index-ascending. `PolyPath64.count` is defined as `this.children.length` (`clipper2-ts@2.0.1-18` `Engine.js:357-359`), and `.child(index)` returns `this.children[index]` after a bounds check (`Engine.js:407-412`) — so this traversal order is exactly Clipper2's own internal child array order, which is itself determined by the boolean-operation algorithm's output order (opaque to this cluster; treated as a black-box but deterministic ordering source that a Rust Clipper2 binding must reproduce bit-for-bit per the migration prompt's §8.3 requirement to "reproduce the existing clipper2-ts operations... exactly").

## 6. Comparators and tie rules

This cluster is the single richest source of distinct string-comparison conventions in the codebase; the migration prompt's §9 explicitly warns "verify whether each TypeScript comparison is code-unit, lexical, locale-based, numeric, or custom" and "do not assume Rust byte ordering matches JavaScript UTF-16 or `localeCompare`." Cataloged exhaustively, by mechanism:

### Raw `<`/`<=` on strings (UTF-16 code-unit comparison, locale-independent)

- `canonicalLayoutGeometry.ts:520` — `orderedPiecePair(first, second)`: `first < second ? [first, second] : [second, first]`. Decides the **within-pair** element order (which `PieceId` comes first in a `readonly [PieceId, PieceId]` tuple) using raw code-unit `<` — **not** `localeCompare`, even though the very next helper (`comparePiecePairs`, below) sorts *between* pairs using `localeCompare`. This is a genuine, verified inconsistency between two adjacent functions operating on the same `PieceId` string type.
- `canonicalLayoutGeometry.ts:616` — `canonicalRing`: `forward < reverse ? forward : reverse`, comparing two already-fully-computed ring-direction keys (semicolon-joined `"x,y"` ASCII strings — see below).
- `canonicalLayoutGeometry.ts:627` — `canonicalRingDirection`: `if (best === undefined || key < best) best = key` — the O(n²) minimal-rotation search, raw `<` per candidate offset. **First-offset-wins-on-tie** is impossible by construction here since a tie can only occur between congruent rotations of a ring with rotational symmetry, in which case any of the tied offsets produces an identical key string, so which one "wins" is unobservable.
- `canonicalLayoutGeometry.ts:714` — `largestHullGapRegion`'s `visit`: `key < (selectedKey ?? key)` where `key`/`selectedKey` are `canonicalRing(...)` outputs — same raw `<` convention, first-in-pre-order-traversal wins ties (§4).
- `canonicalLayoutGeometry.ts:149` — the default (no-comparator) `.toSorted()` on `identities` (§5 rule 2) is defined by spec to coerce-to-string-then-compare, which for already-`string`-typed elements is exactly this same code-unit `<` ordering.
- `canonicalLayoutGeometry.ts:479,553` — default `.toSorted()` on `PieceId[]` arrays (`wallOffenders`, one component's members) — same code-unit convention, applied here to `PieceId` strings specifically (contrast with `comparePiecePairs`'s `localeCompare` on `PieceId`, immediately below).

### `String.prototype.localeCompare` (default locale, no explicit options — collation-sensitive, environment-dependent)

- `canonicalLayoutGeometry.ts:527` — `comparePiecePairs`: `first[0].localeCompare(second[0]) || first[1].localeCompare(second[1])`.
- `canonicalLayoutGeometry.ts:571` — `contactComponents`'s final sort: `first.join('|').localeCompare(second.join('|'))` (tertiary key, after descending size and descending bigint area).
- `canonicalLayoutGeometry.ts:223` — `measureCanonicalLayoutContacts`'s polygon-processing-order sort: `first.pieceId.localeCompare(second.pieceId)`.
- `convexPolygonContact.ts` and `canonicalGridContact.ts` do **not** use `localeCompare` anywhere — their structural-contact-signature construction uses only numeric `Math.round` keys and raw string `<=`/template-literal concatenation (below).

### Structural-contact-signature string construction and ordering (both `canonicalGridContact.ts` and `convexPolygonContact.ts`, near-identical implementations)

Both files build a per-edge "descriptor" string of the form `` `${edgeRatioKey}:${firstEndpoint}:${secondEndpoint}` `` where `edgeRatioKey`/`previousRatioKey`/`nextRatioKey` are `Math.round((lengthMm / longestEdgeMm) * 1000)` integer keys (`ratioSignatureKey`, `canonicalGridContact.ts:371-374` and `convexPolygonContact.ts:214-217`, identical formula, **independently duplicated** in each file rather than shared — see §12) and `startTurnKey`/`endTurnKey` are `Math.round(cosine * 1000)` (also duplicated). Two such descriptors are then combined into one pair-signature using a **raw `<=`** comparison (not `localeCompare`): `firstDescriptor <= secondDescriptor ? \`${a}|${b}\` : \`${b}|${a}\`` (`canonicalGridContact.ts:159-161`, `convexPolygonContact.ts:161-163`), and within each descriptor, the two endpoint sub-keys are similarly ordered with raw `<=` (`canonicalGridContact.ts:203-206`, `convexPolygonContact.ts:207-210`). This makes the signature string symmetric under swapping which polygon/edge is "first" — required for the signature to correctly dedup a contact regardless of iteration direction. All of these comparisons are on strings built purely from ASCII digits, `:`, `-`, and `|` characters (integer key `toString()` output plus fixed separators), so code-unit `<=` and byte comparison coincide exactly here — this is the one place in the cluster where the code-unit-vs-locale distinction is provably moot, because the operands are guaranteed ASCII by construction.

### Numeric comparators (exact `bigint`, exact-or-approximate `number`)

- `compareBigInts` (`canonicalGridMath.ts:12-14`): `first === second ? 0 : first < second ? -1 : 1` — exact, total order, no epsilon.
- `compareCanonicalGridRatios` (`canonicalGridMath.ts:16-27`): cross-multiplication comparison `firstNumerator * secondDenominator` vs `secondNumerator * firstDenominator`, **guarded** by `firstDenominator <= 0n || secondDenominator <= 0n` returning `undefined` (both denominators must be strictly positive) — this is the exact rational-number comparator the migration prompt's §8.2 calls "ratio comparisons." See §7 for the magnitude analysis of the cross-multiplication products.
- `canonicalLayoutGeometry.ts:565-573`'s `components.toSorted(...)`: `second.length - first.length` (plain `number` subtraction of component sizes — always small integers, no precision risk) then `compareBigInts(secondArea, firstArea)` (exact) then `localeCompare` (above).
- `canonicalGridMath.ts:141`'s hull-point sort: `first.x - second.x || first.y - second.y` — plain `Number` subtraction (§7 precision note).
- `freeMaterialService.ts:464-466` — `comparePolygons`: `firstPoint.y - secondPoint.y` then `firstPoint.x - secondPoint.x` — plain `Number` subtraction of already-`fromGrid`-dequantized mm coordinates (multiples of `0.001`), then falls back to `polygonKey(...).localeCompare(...)` (below) only when both points are undefined or exactly equal in `y` and `x`.

### `Number.prototype.toString()`-derived key strings (template-literal coercion, shortest-round-trip algorithm)

- `canonicalGridMath.ts:140` — `` `${point.x},${point.y}` `` (hull dedup key).
- `canonicalLayoutGeometry.ts:625` — `` `${point?.x},${point?.y}` `` (ring-direction key, joined with `;`).

## 7. Numeric semantics

### `toGridMm` / `fromGrid` (`clipper2OffsetPolicy.ts:44-58`) — the shared quantization boundary for the whole cluster

```
scaledAbsoluteValue = Math.abs(valueMm) * 1000
roundedAbsoluteValue = Math.floor(scaledAbsoluteValue + 0.5)
gridValue = Math.sign(valueMm) * roundedAbsoluteValue
return Number.isSafeInteger(gridValue) ? gridValue : undefined
```
Identical to the description already verified in `capacity-core.md:231-243`; re-derived here from direct read because it is load-bearing for every function in this cluster that converts millimeters to grid units (`placedCollisionWorldGridPath`, `assertCanonicalGridLegalLayout`'s sheet bounds, `toSheetPath`/`toMaterialPath`/`toPlacedPath` in `freeMaterialService.ts`). Key facts:
- Ties round away from zero on the **absolute** value before the sign is reapplied (`CLIPPER2_OFFSET_POLICY.rounding`, `clipper2OffsetPolicy.ts:13`).
- `Number.isSafeInteger` is the **only** magnitude guard enforced *inside* `toGridMm` itself — it does **not** enforce `CLIPPER2_OFFSET_POLICY.maxScaledCoordinate` (`1_000_000_000`, i.e. 1,000,000 mm). That stricter guard is enforced only in `clipper2OffsetAdapter.ts` (a different cluster, per `collision-prep.md:773-775`) and, within this cluster, only in `freeMaterialService.ts`'s `validateCoordinateGuard` (`:314-327`). **`canonicalGridMath.ts`, `canonicalGridContact.ts`, and `canonicalLayoutGeometry.ts` never check `maxScaledCoordinate` — their own admission gate is exclusively `Number.isSafeInteger` (`isCanonicalGridCoordinate`, `canonicalGridMath.ts:8-10`, and the equivalent inline checks in `canonicalGridPathEdges`, `canonicalLayoutGeometry.ts`'s own coordinate uses).** This means a canonical-grid coordinate as large in magnitude as `Number.MAX_SAFE_INTEGER` (2^53 − 1 ≈ 9.007199254740991×10^15 grid units ≈ 9.007×10^12 mm) is, in principle, syntactically acceptable to every function in `canonicalGridMath.ts`/`canonicalGridContact.ts` — and the unit tests in `tests/unit/canonicalGridMath.test.ts:148-166` deliberately exercise exactly this extreme (`Number.MAX_SAFE_INTEGER` used directly as a coordinate). See the BigInt-magnitude analysis below for why this matters to a Rust port.

### The `-0`-to-`0` fold — two independently-implemented, behaviorally-identical mechanisms

1. `canonicalLayoutGeometry.ts:100-101` — inside `placedCollisionWorldGridPath`:
   ```ts
   const x = toGridMm(point.x + translateX)
   const y = toGridMm(point.y + translateY)
   return { x: x === 0 ? 0 : x, y: y === 0 ? 0 : y }
   ```
   Uses the fact that in JavaScript `-0 === 0` evaluates `true`, so `x === 0 ? 0 : x` maps *both* `-0` and `+0` to the literal `+0`, leaving every other value (including `undefined`, which fails the `=== 0` test and passes through unchanged for the later `undefined`-filtering at line 104-109) untouched.
2. `freeMaterialService.ts:487-489` — `normalizeNegativeZero(value) { return Object.is(value, -0) ? 0 : value }`, applied at the two `toGridMm(...)` call sites that build Clipper2 `Path64` points (`:246`, `:289`). Uses `Object.is` to detect `-0` specifically (distinct from `===`, which cannot distinguish `-0`/`+0`) and replace it with `+0`.

Both idioms produce **identical output** for every possible `number` input (including `NaN`, `±Infinity`, and every finite value) — `x === 0` is `true` exactly when `x` is `+0` or `-0` (and false for `NaN` since `NaN !== NaN` and `NaN !== 0`), matching `Object.is(x, -0)` being `true` exactly for `-0`. The only case where the *codepaths* diverge is `+0` itself: `x === 0 ? 0 : x` explicitly rewrites `+0` to a **new** `0` literal (a no-op value-wise), while `Object.is(value, -0) ? 0 : value` leaves `+0` untouched (falls to the `: value` branch). Since `+0` and `+0` are the same value either way, this is a pure implementation-style difference with **zero observable effect** — but a Rust port must know both mechanisms exist and both are required (in their respective files) to reach the same normalized-zero contract, not that one file "forgot" the fold that the other "remembered." Why the fold matters at all: without it, `-0` could propagate into `Math.min`/`Math.max` calls elsewhere in this cluster (`gridPathAabb`, `envelopeAspectRatio`, `measureCanonicalLayoutEnvelope`'s `Math.min(...points.map(...))`), and per the ECMAScript spec `Math.min(-0, +0)` returns `-0` while `Math.max(-0, +0)` returns `+0` — so an un-folded `-0` coordinate sitting alongside a `+0` coordinate in the same point cloud could make an axis-aligned-bounding-box minimum silently become `-0` instead of `0` if the fold were removed, which would not change any `<`/`===` comparison result (since `-0 === 0` and `-0 < x` behaves identically to `0 < x`) but **would** change the `Number.prototype.toString()` output... except JS's `toString()`/template-literal coercion of `-0` is also `"0"` (identical to `+0`), and `JSON.stringify(-0)` is also `"0"` — so the only place a residual `-0` could ever be *observed* as different from `+0` in this cluster's own code is via `Object.is`-based equality checks used by a test framework's `toBe`/`toEqual` (Vitest's `toBe` uses `Object.is` and **does** distinguish `-0` from `0`) or via `1/x` sign inspection (not performed anywhere in this cluster). The fold is therefore best understood as a defensive normalization against `Object.is`-sensitive consumers (tests, and potentially downstream memoization keyed by `Object.is`/`SameValueZero`), not as a fix for any comparison bug within this cluster itself.

### `CANONICAL_GRID_EXACT_NUMBER_CROSS_LIMIT` (`canonicalGridMath.ts:63`) — full derivation, re-verified independently

`= 2**25 - 1 = 33,554,431`. The doc comment (`canonicalGridMath.ts:50-62`) derives: with every coordinate bounded by `L`, each difference (`first.x - origin.x`, etc.) is at most `2L` in magnitude, each product at most `4L²`, and the difference of two such products at most `8L²`. Substituting `L = 2^25 - 1`:
```
8L² = 8·(2^25 − 1)² = 8·(2^50 − 2^26 + 1) = 2^53 − 2^29 + 8
```
`Number.MAX_SAFE_INTEGER = 2^53 − 1`, so `2^53 − 2^29 + 8 = Number.MAX_SAFE_INTEGER − 2^29 + 9`, strictly below `Number.MAX_SAFE_INTEGER` — confirmed correct by direct arithmetic, not just trusted from the comment. In canonical grid units of `0.001 mm`, `L = 33,554,431` grid units = `33,554.431 mm ≈ 33.55 m`. `canonicalGridCrossSign`'s fast path (`canonicalGridMath.ts:97-105`) is only taken when **all three** points (`origin`, `first`, `second`) satisfy `Math.abs(x) <= L && Math.abs(y) <= L` (`withinExactNumberCrossLimit`, `:65-70`); outside that box, it unconditionally falls back to the exact `bigint` path (`canonicalGridCross`, `:106-108`). The unit test `tests/unit/canonicalGridMath.test.ts:137-146` ("detects a one-unit orientation difference at the extreme of the fast path") directly proves the bound is tight: a single grid-unit perturbation at exactly `±limit` still flips the fast-path sign correctly, with no rounding.

**BigInt magnitude bounds for the exact fallback, derived from the actual enforced coordinate ceiling (`Number.isSafeInteger`, since — as established above — this cluster does not itself enforce the smaller `maxScaledCoordinate` bound):**

Let `L_max = 2^53 − 1 ≈ 9.007199254740991×10^15` (the largest coordinate `isCanonicalGridCoordinate` admits).
- A single cross-product term (`canonicalGridCross`, `canonicalGridMath.ts:44-47`): each difference is bounded by `2·L_max ≈ 1.8014×10^16`; each product by `(2·L_max)² = 4·L_max² ≈ 3.246×10^32`; the term (a difference of two such products) by `8·L_max² ≈ 6.492×10^32`. This comfortably fits in a 128-bit signed integer (`i128::MAX ≈ 1.7014×10^38`), with roughly 5 orders of magnitude of headroom.
- The doubled-area **accumulation** over a path with `N` edges (`canonicalGridSignedDoubledArea`, `canonicalGridMath.ts:111-131`): each term (`x1·y2 − x2·y1`) is bounded by `2·L_max² ≈ 1.623×10^32`; the running sum after `N` terms is bounded by `N·2·L_max²`. This stays within `i128` range for any `N` up to roughly `1.7×10^38 / 1.623×10^32 ≈ 1.05×10^6` — i.e., over a million vertices — comfortably beyond any realistic polygon (including Clipper2 boolean-op output for complex gap/cavity regions), **but only if every coordinate is simultaneously near the `Number.isSafeInteger` extreme**, which never happens with real production geometry (see the practical bound below). A Rust port that chooses `i128` accumulators for these sums is safe under any *plausible* input, but is not proven safe under the literal `Number.isSafeInteger` ceiling this cluster's own guard admits for an adversarially large polygon — the migration prompt's §8.2 requirement ("Use checked arithmetic and a wider integer or arbitrary-precision fallback when required... Do not let release-mode integer overflow wrap silently") is best satisfied by either (a) checked/overflow-panicking `i128` arithmetic (safe for all realistic inputs, loud failure otherwise) or (b) an arbitrary-precision type (e.g. `num-bigint`) that mirrors JS `BigInt`'s literal unbounded-precision semantics exactly, with no magnitude assumption at all. Given JS `BigInt` genuinely never overflows, **(b) is the only representation that is provably byte-identical to the TypeScript original under every input the type system admits**; (a) is a documented, bounded approximation that must be justified against the smaller practical bound below if chosen. Flagged as a top port risk in §15.
- `compareCanonicalGridRatios`'s cross-multiplication (`canonicalGridMath.ts:23-26`) is a **second** squaring stage when its inputs are themselves already-squared magnitudes (its only production callers — `intrinsicShortSideObserver.ts:684`, `overlapRelaxation.ts:704`, `targetedExactLns.ts:636` — pass in `BigInt(...)`-parsed doubled-area-scale strings, i.e. values already on the order of `L²`). At the practical bound (`L ≈ 1×10^9`, see below), a doubled-area value is on the order of `2×10^18`; the cross-multiplication product is then on the order of `4×10^36` — still within `i128` (`≈1.7×10^38`) by two orders of magnitude, but with far less headroom than the single-cross-product case, and this is *before* accounting for envelope-area or cavity-area accumulation over many regions, which could push the pre-multiplication operand itself higher. This is the single most exposed BigInt computation in the cluster to a fixed-width-integer port.

**Practical bound, for context (not itself enforced by this cluster, but the realistic ceiling given the rest of the pipeline):** `CLIPPER2_OFFSET_POLICY.maxScaledCoordinate = 1_000_000_000` grid units (`= 1,000,000 mm = 1000 m`), enforced upstream by `clipper2OffsetAdapter.ts` (per `collision-prep.md:773-775`) on the **padded collision polygon** before translation, and independently by `freeMaterialService.ts`'s own `validateCoordinateGuard` (`:314-327`) on its own Clipper2 input paths. `placedCollisionWorldGridPath` (`canonicalLayoutGeometry.ts:92-110`) does **not** re-check `maxScaledCoordinate` after adding `translateX`/`translateY`, so a translated world-grid coordinate could in principle exceed `1e9` if the sheet/placement geometry were large enough — but real production sheets (`SheetSpec.width`/`height`, `Schema.Int` with only a positivity check, no explicit upper bound in `shared/domain/geometry.ts:17`) are practically bounded to at most a few meters to tens of meters, so `L ≈ 1×10^9` (1000 m) is a very generous practical ceiling, not a schema-enforced one. At this practical `L`, a single cross-product term is bounded by `8·L² = 8×10^18` — **within roughly 15% of `i64::MAX` (`9.223×10^18`)**, meaning a naive `i64` (not even `i128`) implementation would be perilously close to overflow for a single term alone, before any accumulation. This confirms `i64` is never an acceptable choice anywhere in this cluster's exact-arithmetic paths, and reinforces that `i128` (with explicit overflow checks) or arbitrary precision is required.

### `turnCosine` (both `canonicalGridContact.ts:356-369` and `convexPolygonContact.ts:224-239`, independently duplicated implementations)

Computes a dot-product-over-magnitude cosine, explicitly clamped: `Number.isFinite(cosine) ? Math.max(-1, Math.min(1, cosine)) : undefined`. This clamp exists because floating-point dot-product/hypot computation can produce a cosine magnitude fractionally above `1` or below `-1` due to rounding, which would otherwise later feed `Math.round(cosine * 1000)` and could, without the clamp, produce `1001` or `-1001` instead of `1000`/`-1000` — the clamp is exactness-adjacent (protects the signature-key integer range) even though the underlying cosine computation itself is ordinary floating-point, not exact-arithmetic.

### `Math.hypot` usage

`canonicalGridContact.ts:352,365`, `convexPolygonContact.ts:220,233,270,291` all use `Math.hypot(dx, dy)` for Euclidean edge lengths (never a manual `Math.sqrt(dx*dx+dy*dy)`) — `Math.hypot` is specified to avoid intermediate overflow/underflow for extreme magnitudes, which matters less for this cluster's typical millimeter-scale inputs but is still the literal operation a Rust port must reproduce (`f64::hypot`, not a manual sqrt-of-sum-of-squares) for bit-identical results, since the two algorithms can differ in their last-bit rounding.

### `doubledGridAreaToMm2` vs. `doubledGrid2ToMm2` — a genuine cross-file divergence in guard behavior

`canonicalGridMath.ts:198-201` (this cluster):

## 8. Serialization and hashing

### `canonicalCollisionLayoutIdentity` → SHA-256: the cluster's most consequential hash preimage

`canonicalCollisionLayoutIdentity` (`canonicalLayoutGeometry.ts:139-150`) is the **direct preimage** of a production SHA-256 identity. Traced precisely at `intrinsicCapacityEndpoint.ts:190`:
```ts
const identity = canonicalCollisionLayoutIdentity(oriented.placedCollisionGeometries)
...
hash: createHash('sha256').update(identity).digest('hex'),
```
`node:crypto`'s `Hash.update(data)` with a `string` `data` argument and no explicit `inputEncoding` uses Node's default string-to-bytes encoding, which is `'utf8'`. The exact byte sequence hashed is therefore the UTF-8 encoding of the JS string `identity`. A Rust port must produce byte-identical UTF-8 bytes from the equivalent canonical-identity string before feeding them to a SHA-256 implementation (e.g. the `sha2` crate) — this requires the *string itself* (not just its "meaning") to be byte-identical, which is why every ordering/formatting rule in §5/§6/§7 above (ring-origin normalization, winding, quarter-turn selection, JSON.stringify's exact separator/escaping conventions, `Number.prototype.toString()` for integer coordinates) is directly load-bearing for this hash.

The exact construction, traced end-to-end:
1. `canonicalPlacedPolygons(placed)` (`:501-517`) builds `{pieceId, path}` pairs from `placedCollisionWorldGridPath` (one rounding pass, translation-then-round, `-0`-folded — §7), rejecting the whole computation (returns `undefined`) on any degenerate/zero-area/undersized ring.
2. For each of the 4 quarter-turn rotations `[0,90,180,270]` (`:144`), `identityAtQuarterTurn(paths, rotationDeg)` (`:592-611`):
   - Rotates every point of every path by the quarter turn (`rotateGridPoint`, `:632-643`, exact integer negation/swap — no floating-point trig, so this step is exact by construction).
   - Computes one **global** translation (`minX`,`minY` over the flattened, rotated point cloud — a single translation applied to all pieces together, not per-piece) via `Math.min` (order-independent, §4).
   - Translates every point by `(x - minX, y - minY)` (plain `Number` subtraction — see §7's precision caveat for adversarial extreme-magnitude inputs, which this specific line does **not** guard against with any `Number.isSafeInteger` check on the result, unlike the exact-arithmetic functions elsewhere in the same file).
   - For each path, computes `canonicalRing(translatedPath)` (`:613-617`): tries both the forward and reverse vertex order via `canonicalRingDirection` (`:619-630`, the O(n²) minimal-rotation search producing a semicolon-joined `"x,y"` ASCII key, raw `<` comparison — §6), and keeps whichever of forward/reverse is code-unit-smaller — this is simultaneously the **ring-origin normalization** and the **winding normalization** the migration prompt's §9 requires preserving.
   - Sorts the resulting per-path key strings with **default** `.toSorted()` (code-unit, §6) — this is the **piece-order normalization** (so which physical piece is "piece 1" in the placement input does not affect the identity, only the *set* of ring shapes at their placed positions does).
   - `JSON.stringify(sortedRingKeyArray)` — standard JSON array-of-strings encoding (each ring key already contains only digits, `,`, `;`, `-`; `JSON.stringify` additionally wraps each in `"..."` and comma-separates the array, with **no** internal whitespace since `JSON.stringify(value)` with no `space` argument produces the most compact form).
3. `canonicalCollisionLayoutIdentity` picks the code-unit-lexicographically-**smallest** of the 4 per-rotation JSON strings (`.filter(...).toSorted()[0]`, `:147-149`) — this is the **quarter-turn equivalence rule**: two placements that are exact 90°-multiple rotations of each other produce the identical final identity string, because whichever of the 4 candidate encodings happens to be smallest is chosen for both.

**Dead-code finding, verified precisely:** `identityAtQuarterTurn`'s declared return type is `string | undefined`, but tracing every `return` statement in the function body (`:592-611`) shows it returns **either** the literal `'[]'` (only when `points[0] === undefined`, i.e. the placed-pieces array is empty) **or** the `JSON.stringify(...)` result — there is no code path that returns `undefined`. Consequently the guard at `canonicalCollisionLayoutIdentity`'s `:147` (`identities.some(identity => identity === undefined) ? undefined : ...`) can **never** be `true` in practice; `canonicalCollisionLayoutIdentity` returns `undefined` only when `canonicalPlacedPolygons(placed)` itself fails (`:143`), never because of `identityAtQuarterTurn`. This is exactly the kind of "TypeScript oddity that IS the spec" the migration prompt (§2) requires preserving rather than "fixing" — a Rust port's equivalent function may reproduce the dead branch verbatim (harmless) or omit it with an explicit code comment recording that it is provably unreachable (per the same prompt's stance that dead branches may be omitted only with that kind of explicit, evidenced justification, not silently).

**Distinct sentinel identity, not derived from this cluster's own empty-input behavior:** `intrinsicCapacityEndpoint.ts:16` defines `INTRINSIC_CAPACITY_EMPTY_LAYOUT_IDENTITY = 'intrinsic-capacity-empty-layout-v1'`, a hardcoded string used (with its own SHA-256 hash, `intrinsicCapacityEndpoint.ts:244-246`) for the "all pieces unplaced" endpoint — this is **not** the same string `canonicalCollisionLayoutIdentity([])` would itself produce (which would be `'[]'`, per the dead-code analysis above, since an empty `placed` array makes `points[0] === undefined` for every rotation, all four candidate strings equal `'[]'`, and the smallest of four identical strings is `'[]'`). Both are valid, independent identity spaces for their respective callers; this is not a bug, just a fact a Rust port must know precisely (do not assume the capacity cluster's empty-layout sentinel and this cluster's own empty-input output coincide).

**A second SHA-256 consumer of this cluster's output**, outside the capacity cluster: `intrinsicStrictDecoder.ts:1050-1055` feeds `canonicalCollisionLayoutIdentity(input.frozenPlaced) ?? ''` (note: the `?? ''` fallback here means a `canonicalPlacedPolygons` failure is **not** propagated as a hashing failure in this call site — it silently becomes an empty string inside a larger JSON object, unlike the capacity cluster's `undefined` short-circuit) as one field of a larger object that is itself `JSON.stringify`'d and hashed — full construction is out of scope for this cluster (belongs to `strict-decoder-gap-family.md`), but the dependency is recorded here because the *identity string itself* originates in this cluster.

### JSON.stringify semantics relied on throughout

- Compact form (no `space` argument) is used everywhere in this cluster that calls `JSON.stringify` (`canonicalLayoutGeometry.ts:606-610` only — this is the **only** `JSON.stringify` call in all five files).
- `undefined` array elements are never present in the arrays being stringified here (every element is a `string`), so the "undefined omitted from objects, `null`-ified in arrays" JSON.stringify quirk is not exercised by this specific call site.
- String escaping: ring keys contain only `-0123456789,;` characters (integers, comma, semicolon, optional leading minus), none of which require JSON escaping, so `JSON.stringify`'s escaping rules (`\"`, `\\`, control characters) are never actually exercised by the values this cluster produces — a Rust port's JSON encoder does not need general-purpose escaping correctness for this specific call site, only correct quoting and comma-separation, though it should still implement full escaping for defensiveness/future-proofing since the migration prompt requires byte-identical behavior even for currently-unreachable inputs.

## 10. Cancellation / deadline / budget / evaluation-cap observation points

**Exactly one function in this entire cluster accepts a cancellation/deadline hook:** `measureCanonicalGridBoundaryOverlapAxisUnits` (`canonicalGridContact.ts:302-337`), via its optional `checkpoint: (() => boolean) | undefined` parameter, threaded down into `canonicalGridPathEdges(path, checkpoint)` (`:210-234`, checked once per edge during path construction, `:217`) and then checked again **once per outer-loop edge** and **once per inner-loop edge-pair** during the overlap scan itself (`:322-325`). The wrapping logic (`:307-312`) converts a `checkpoint() === false` signal into `aborted = true` and a `{kind: 'aborted'}` result, distinguishing it from the `{kind: 'undecidable'}` result used for ordinary structural failure. `tests/unit/canonicalGridContact.test.ts:58-88` directly verifies both a "deadline checkpoint" and an "RSS/memory checkpoint" style caller can interrupt mid-scan, and that the number of `checkpoint()` invocations strictly exceeds the path-construction-only count (proving the scan itself, not just construction, is checked).

**Every other function in all five files runs to completion once invoked, with no internal cancellation/deadline/budget observation point.** This includes:
- `hasPositiveCanonicalGridBoundaryContact` and `measureCanonicalGridBoundaryContact` (`canonicalGridContact.ts`) — both call `canonicalGridPathEdges` **without** a checkpoint argument (defaults to `undefined`), so even though the underlying helper *supports* a checkpoint, these two call sites do not use it.
- Every function in `canonicalLayoutGeometry.ts`, including the Clipper2-boolean-op-driven ones (`assertCanonicalGridLegalLayout`, `analyzeCanonicalLayoutStructure`, `largestHullGapRegion`, `measureEnclosedOccupiedCavities`) — these can involve `O(n²)` pairwise Clipper2 intersection calls (`analyzeCanonicalLayoutStructure`'s lower-triangle loop) with no way to abort mid-computation from within this cluster's own code.
- All of `convexPolygonContact.ts` and `freeMaterialService.ts` — no checkpoint parameter anywhere.

The only production caller that ever supplies a real checkpoint is `intrinsicShortSideContactStrip.ts:689-693`, whose closure calls `boundedStatus(runtime)` (a different cluster's deadline/memory-cap check) and captures which specific bound (`'deadline' | 'memory-cap'`) fired into `boundedDuringScan` for later reporting. This is a **Compact Short Side**-specific cancellation integration; the migration prompt's §12 rule 8 ("Do not return partial geometry after deadline, cancellation, memory cap, trace cap, or evaluation cap") is enforced by that caller, not by this cluster's own code, which merely provides the abortable primitive.

For a Rust port targeting true multithreading (§13), this means: only `measureCanonicalGridBoundaryOverlapAxisUnits`'s call sites can safely be time/memory-bounded mid-computation without changing behavior; every other function in this cluster must be treated as an atomic (uninterruptible, by this cluster's own contract) unit of work from a scheduling perspective — any deadline/cancellation enforcement around them must happen **before** or **after** the call, never by injecting a new mid-computation checkpoint (which the migration prompt's §14.2 explicitly forbids: "cancellation or deadline checks at new eager positions").

## 11. Error paths: tagged error classes, categories, context fields, propagation

### `canonicalGridMath.ts`, `canonicalGridContact.ts`, `canonicalLayoutGeometry.ts`, `convexPolygonContact.ts` — no typed errors; `undefined`/`false`/`null` sentinels only

None of these four files import or construct any `Data.TaggedError` class, throw any exception intentionally, or return an `Effect`. Every failure mode is a plain sentinel:
- `T | undefined` is by far the dominant convention (nearly every exported function in `canonicalGridMath.ts`, `canonicalGridContact.ts`, and most of `canonicalLayoutGeometry.ts`/`convexPolygonContact.ts`).
- `boolean` with `false` meaning "illegal/failed" (`assertCanonicalGridLegalLayout`, `hasPositiveCanonicalGridBoundaryContact` returning `false` for "no contact found" — note this second one conflates "definitely no contact" with nothing else, since `undefined` is its actual failure sentinel and `false` is a genuine negative *answer*, not a failure).
- The one genuine three-state case: `largestHullGapRegion`'s `T | undefined | null` (§3).

**Failure propagation is uniformly "poison on first failure, fail the whole computation"** — there is no partial-result reporting anywhere in these four files (matching the fail-fast convention already documented for the capacity cluster in `capacity-core.md`). A caller receiving `undefined`/`false`/`null` from any of these functions has no way to distinguish *why* without separately re-deriving the failure (none of these files carry a message/reason string on failure) — callers that need a diagnosable reason (e.g. `intrinsicStrictDecoder.ts`, `intrinsicCapacityEndpoint.ts`) construct their **own** typed errors (out of scope for this cluster) only after receiving the bare sentinel.

**Every "impossible" defensive branch uses the same silent-sentinel convention, including around exceptions from the Clipper2 wrapper:**
- Every `try { booleanOpWithPolyTree(...) } catch { return undefined/false/null }` in `canonicalLayoutGeometry.ts` (`:372-374,430-432,663-665,694-696`) swallows **any** exception the Clipper2 wrapper might throw (not just a specific error type) and converts it to the function's ordinary failure sentinel — no error message, category, or original exception is preserved or logged anywhere in this cluster.
- Every `try { child = parent.child(index) } catch { return false/undefined/null }` wrapping a `PolyPath64.child()` call (`canonicalLayoutGeometry.ts:704-706,758-760,810-812,828-830`) guards against `Engine.js`'s `"Index out of range"` `Error`, which — as verified directly against `PolyPath64.count`'s definition (`Engine.js:357-359`, `get count() { return this.children.length }`) — **can never actually throw** given these call sites' own `for (index = 0; index < parent.count; ...)` loop bounds, since `count` and `children.length` are definitionally identical at every point in a single synchronous call. This is defensive dead code in practice, preserved as-is per the migration prompt's mandate.

### `freeMaterialService.ts` — the cluster's one typed-`Effect`-error boundary

Uses `Effect.fail(new IrregularGeometryInputError({ operation, message }))` (`:496-501`), constructed **only** by the single `failInvalidGeometry` helper, called from 5 distinct sites (`:52,62,67,82,85,89,115,119` — 8 call expressions, all routed through the same helper). `IrregularGeometryInputError` (`services.ts:42-45`, `{operation: string, message: string}`) is fully documented cross-cluster in `docs/planning/rust-irregular-backend/characterization/errors-protocol.md:141` as construction site "2" of "15... spread across geometry kernel, transform generator, NFP/IFP service, placement validation, clipper2 adapter, collision geometry builder, free-material service, windowed beam..." — this cluster owns exactly this one file's worth of those 15 sites.

The `operation` field passed is always the literal string `'computeFreeMaterial'` or `'extendFreeMaterial'` (matching the public method name, `:47-97`), never a finer-grained sub-operation name — so error `operation` alone cannot distinguish, e.g., "sheet path invalid" from "occupied union failed" from "output path malformed"; that distinction lives only in the free-text `message` field (which is **not** part of the tagged-error's structural identity, only its diagnostic text — per `errors-protocol.md`'s broader documentation of how `operation`/`message` are consumed downstream).

Internally, before reaching that one boundary, the file uses the untagged `{payload} | {message: string}` union pattern (§3) exclusively — a Rust port should model this internal layer as a plain `Result<T, String>` (or a small internal enum of causes if finer diagnostics are desired for logging, provided the final mapped `operation`/`message` pair at the `Effect`/`Result` boundary remains byte-identical to what TypeScript produces, since `message` strings can appear in test assertions).

Also possible in the interface signature (but never actually constructed by this file's own code): `IrregularNestingNotImplementedError` — only `FreeMaterialServiceUnimplemented` (`services.ts:430-433`, a stub layer used elsewhere, not by this cluster) constructs it; `freeMaterialService.ts`'s real implementation never does.

## 12. JS-specific semantics hazards for a Rust port

1. **`localeCompare` vs. raw `<` vs. default `Array.prototype.toSorted()` (no comparator), used inconsistently on the *same* `PieceId` string type within the *same file*.** `orderedPiecePair` (`canonicalLayoutGeometry.ts:520`) uses raw code-unit `<`; `comparePiecePairs` (`:527`) uses `localeCompare`; `wallOffenders`/component-member sorts (`:479,553`) use the default (code-unit) `.toSorted()`. A Rust port must implement **both** an exact UTF-16-code-unit string comparator (matching Rust's native `str`/`String` `Ord`, which compares by Unicode scalar value / UTF-8 byte sequence — provably equivalent to JS code-unit ordering only for the BMP, i.e. no surrogate pairs, which is true for all-ASCII `PieceId`s but must be verified, not assumed, if `PieceId` generation ever admits non-ASCII) **and** a locale-aware collator equivalent to V8's default `Intl.Collator`/`localeCompare` (e.g. the `icu` crate or a pinned ICU version), and must route each specific call site to the matching one — never substitute one for the other, per migration prompt §9's explicit warning.
2. **`Math.min(-0, +0) === -0` / `Math.max(-0, +0) === +0`** — the ECMAScript-spec-mandated asymmetric signed-zero behavior of `Math.min`/`Math.max` is why the `-0`-fold (§7) exists at the coordinate-construction boundary rather than being deferred to every later `Math.min`/`Math.max` call in the file (`gridPathAabb`, `envelopeAspectRatio`, `measureCanonicalLayoutEnvelope`). Rust's `f64::min`/`f64::max` have their **own** distinct (and non-identical to JS) NaN/signed-zero propagation rules (per IEEE 754-2008 `minNum`/`maxNum` semantics, which Rust's `f64::min` follows) — a Rust port must not assume `f64::min(-0.0, 0.0)` matches `Math.min(-0,0)` bit-for-bit without checking (Rust's `f64::min` returns `-0.0` for `min(-0.0, 0.0)` too, per current stable-library behavior, but this should be verified against the exact Rust version pinned, not assumed to remain stable across compiler versions).
3. **JS `Map` "last insertion wins" on duplicate keys** (`canonicalGridMath.ts:139-140`'s hull dedup) — behaviorally inconsequential here (§5) but a general pattern to watch for elsewhere in a Rust port using `HashMap::insert`/`BTreeMap::insert` (both also last-wins), so this specific instance is low-risk, flagged only for completeness.
4. **`robust-predicates@3.0.3`'s adaptive-precision `orient2d`** (`geometryPredicates.ts:1,21-28`, the sole numeric authority for `convexPolygonContact.ts`'s `collinearOverlapSegment`) is a JS port of Jonathan Shewchuk's adaptive-precision exact geometric predicates. Porting or binding to an equivalent Rust implementation (candidates include the `robust` crate or `geo`'s predicate kernels) requires proving **bit-for-bit** agreement with this specific JS package's expansion/summation strategy, not just "also adaptive precision" — different adaptive-precision implementations can legitimately disagree on which of two nearly-collinear-but-not-exactly-collinear inputs is classified as "exactly zero" versus "epsilon positive/negative" if their fast/exact-path thresholds or summation order differ, even though both are individually "correct" in the sense of never misclassifying a true sign. This is explicitly the kind of substitution the migration prompt's §8.3 forbids ("Do not substitute a geometrically reasonable but behaviorally different library").
5. **`stripDuplicates(path, isClosedPath)`** (`clipper2-ts@2.0.1-18`, `Clipper.js:622-639`, used at `freeMaterialService.ts:249,452`) removes only **consecutive** duplicate points (via `Point64Utils.equals`, an exact integer-coordinate equality, not epsilon-based) plus one trailing point equal to the first when `isClosedPath` is `true` — it does **not** deduplicate non-adjacent repeated points anywhere else in the ring (intentional, per the doc comment at `freeMaterialService.ts:333-337`: "A non-adjacent repeated point is preserved because it can encode a valid point contact"). A Rust Clipper2 binding/reimplementation must reproduce this exact consecutive-only, exact-equality dedup, not a more aggressive "remove all duplicate points" pass.
6. **`Number(bigint)` silently rounds/saturates to `Infinity` for out-of-`f64`-range `bigint` values, with no exception** — `doubledGridAreaToMm2` guards this (`Number.isFinite` check, §7), but the sibling `doubledGrid2ToMm2` in a different cluster does not; a Rust port converting `i128`/arbitrary-precision values to `f64` (e.g. via `as f64` or a checked conversion) must replicate each call site's specific guard-or-no-guard behavior individually, not assume a single shared conversion policy.
7. **`Array.prototype.sort`/`toSorted` stability** — every multi-key comparator in this cluster (§6) relies on JS's ES2019+ guaranteed-stable sort to make later keys act as true tie-breakers only among elements that compare equal on earlier keys; Rust's `slice::sort`/`sort_by` (stable) and `sort_unstable`/`sort_unstable_by` (not stable) are **not** interchangeable here — a Rust port must use only the stable sort family for every comparator ported from this cluster, per migration prompt §9's explicit reminder that JS sorting is stable.
8. **Recursive `PolyPath64`/`PolyTree64` traversal without an iteration budget** — every `visit(...)` closure in `canonicalLayoutGeometry.ts` (§4/§5) is unbounded recursion depth-first over Clipper2's output tree; pathological Clipper2 output (deeply nested holes-within-islands-within-holes) could in principle cause a stack-depth issue in either language, but this cluster's TypeScript does not itself guard against it (no explicit depth cap) — a Rust port should preserve this "trust the tree depth is bounded by realistic geometry" assumption rather than silently imposing a new depth cap that could reject inputs TypeScript would have accepted (per prompt §2, changing acceptance behavior is forbidden even if well-intentioned).

## 13. Parallelism assessment

### Pure/independent — plausible safe Rayon candidates (with the caveats below)

- **Convex-hull dedup + sort + monotone-chain build** (`canonicalGridConvexHull`, `canonicalGridMath.ts:138-171`) is a pure function of its input point list; multiple independent calls (e.g. one per candidate placement/state being evaluated) are trivially parallelizable across calls, though the algorithm's own internal `buildHalf` loop is inherently sequential (each step depends on the mutable `half` stack built so far) and should not itself be parallelized.
- **Per-piece/per-pair canonical-grid path construction and edge extraction** (`canonicalGridPathEdges`, `canonicalGridContact.ts:210-234`) is pure given one path; computing edges for many independent placed pieces in parallel and then combining results serially matches the migration prompt's §14.3 "deterministic parallel pattern" (construct ordered input vector → assign ordinals → evaluate in parallel → store by ordinal → reconstruct ordered result).
- **The lower-triangle pairwise contact/intersection scans** in `measureCanonicalLayoutContacts`, `assertCanonicalGridLegalLayout`, `analyzeCanonicalLayoutStructure`, `measureContactGraph` (`canonicalLayoutGeometry.ts`) are, **per individual pair**, pure and independent of each other (each Clipper2 intersection call only reads its own two polygons). The migration prompt's §14.1 explicitly lists "independent pairwise relative NFP computations after key deduplication" and "read-only spatial-index queries" as good candidates; this cluster's analogous pairwise geometry scans are structurally similar. **Caveat:** `assertCanonicalGridLegalLayout` currently short-circuits on the **first** wall-overrun point or first positive intersection found in its deterministic lower-triangle order (`:352-384`) — a naive parallel version that evaluates all pairs and only *then* checks "did any fail" preserves the **boolean result** exactly (legal iff no pair is illegal, order-independent for a boolean AND-reduction) but changes **how much work is done** (no early exit) and, if any per-pair diagnostic beyond the boolean were ever surfaced (currently none is), could change *which* failure is reported. Since today's function returns only `boolean` with no failure detail, full parallel evaluation-then-AND-reduce is safe for **this** function specifically; `analyzeCanonicalLayoutStructure`'s equivalent loop, by contrast, **does** accumulate ordered diagnostic arrays (`positiveContactPairs`, `positiveAreaConflicts`, etc.) that are explicitly re-sorted before return (§5) — because they are re-sorted with a total-order comparator (`comparePiecePairs`), the final *content* of these arrays is order-independent of discovery order too, so parallel discovery followed by the existing serial sort is also safe here, **provided** the final sort is still applied serially in the exact TypeScript order/comparator afterward.
- **`sharedConvexPolygonBoundarySegments`/`measureSharedConvexPolygonBoundaryContact`** (`convexPolygonContact.ts`) and their canonical-grid analogs are pure given two already-translated polygons; the outer loop over "all currently-placed pieces vs. one newly-added piece" (`irregularBeamState.ts`'s `sharedBoundaryWithEntries`, a different cluster) is a natural map-then-sum-reduce candidate, since the accumulated `lengthMm`/`normalizedUnits`/`nearCompleteStructuralContactCount` are all associative/commutative sums (`Number` addition — see the note below on why this is *not* fully order-independent for floats) and `dominantNearCompleteStructuralContactCount` is a `Map`-then-`Math.max` reduction (provably order-independent, §4).
- **`freeMaterialService.ts`'s per-region/per-hole path construction and validation** (`toMaterialPaths`, `:204-232`) is embarrassingly parallel across regions/holes given they are independent pure transforms — but see §1: this function has **zero production call sites**, so parallelizing it has no production performance benefit; only test-suite runtime would improve, which is not a goal of this migration.

### Must stay serial (chronology-bound, or floating-point-reassociation-sensitive)

- **Every plain `Number` (not `bigint`) summation in this cluster that feeds a value ever compared, ranked, or serialized "as if exact"** — e.g. `measureCanonicalGridBoundaryContact`'s `segments.reduce((sum,segment) => sum + segment.lengthMm, 0)` (`canonicalGridContact.ts:77`), `measureCanonicalLayoutContacts`'s `sharedBoundaryLengthMm += contact.lengthMm` accumulation (`canonicalLayoutGeometry.ts:238`) — must **not** be reassociated (parallel tree-reduction instead of the current strictly-sequential left-to-right fold) because binary64 addition is not associative; the migration prompt's §8.1 explicitly forbids compiler/runtime transformations "that reassociate floating-point expressions or otherwise change accepted results," and §14.3's deterministic pattern requires "exact serial reduction" for exactly this reason. A Rust port may compute the **individual** `lengthMm` terms in parallel (pure, independent per edge-pair) but must fold them into the final sum **serially, in the same left-to-right order** as the TypeScript `for`/`reduce` loop.
- **`identityAtQuarterTurn`'s 4-rotation computation followed by a code-unit-smallest selection** (`canonicalLayoutGeometry.ts:144-149`) — the 4 per-rotation identity strings are independently computable in parallel (pure, no shared mutable state across rotations), but the final `.toSorted()[0]` selection is a trivial serial reduction over exactly 4 elements; parallelizing this specific 4-way fan-out has essentially no performance benefit given the tiny fixed fan-out width, and any parallel implementation must still apply the exact same code-unit comparator serially at the end.
- **`largestHullGapRegion`'s / `measureEnclosedOccupiedCavities`'s / `largestNetRegionDoubledArea`'s recursive `PolyTree64` tree walks** — these are chronology-bound in the specific sense that the "first-in-pre-order-wins-ties" rule (§4, `largestHullGapRegion`'s `netDoubledArea === selectedDoubledArea && key < (selectedKey ?? key)`) is defined *relative to* pre-order traversal order; a parallel tree walk that reduces subtree results out of pre-order (e.g. a work-stealing traversal) must still apply the tie-break rule as if pre-order, meaning the reduction step needs to carry positional/ordinal information rather than naively taking "whichever parallel task finishes first" — this matches the migration prompt's §14.2 "High-risk boundaries" item "checkpoint publication by completion order" in spirit, even though it is not literally a checkpoint here.
- **`canonicalGridConvexHull`'s monotone-chain `buildHalf`** — inherently sequential (stack-based, each push/pop depends on the accumulated stack state); do not parallelize the algorithm's own inner loop, only independent *calls* to the whole function.
- **`freeMaterialService.ts`'s `deriveFreeMaterial`/`deriveExtendedFreeMaterial` control flow** — each is a short, mostly-sequential pipeline (build paths → one Clipper2 union → one Clipper2 difference → walk result tree) with limited internal parallelism opportunity beyond the already-noted per-region parallel construction; given §1's finding that this function runs at most twice per job, parallelizing its internals is very unlikely to matter for overall throughput and is not a profitable target.
- **The `measureCanonicalGridBoundaryOverlapAxisUnits` checkpoint-observing scan** (§10) must remain serial specifically *because* it is the one cancellation-aware loop in the cluster — parallelizing it would either lose the ability to abort mid-scan (violating the caller's deadline/memory-cap contract) or require re-deriving a new, currently-nonexistent parallel-safe cancellation protocol, which the migration prompt's §14.2 forbids introducing ad hoc ("cancellation or deadline checks at new eager positions").

## 15. Open questions and ambiguities

1. **No contradiction of the migration prompt's own summary was found; one claim was actively confirmed by source.** The prompt's §12 statement "diagonal and axis-aligned contacts both contribute to positive-contact count; only axis-aligned overlap contributes to projected-length tie-breaking" is precisely implemented by `hasPositiveCanonicalGridBoundaryContact` (any collinear direction counts for contact) vs. `measureCanonicalGridBoundaryOverlapAxisUnits` (explicitly `'undecidable'` on positive diagonal contact, `canonicalGridContact.ts:296-300,331`), both called together from the cluster's one Compact-Short-Side production caller (`intrinsicShortSideContactStrip.ts:680-693`). Recorded here as a positive, source-verified confirmation rather than a contradiction.
2. **`canonicalGridPointOnSegment` (`canonicalGridMath.ts:173-186`) has no production caller anywhere in `src/`.** Grepping the whole repository (excluding this cluster's own definition) finds no import of this exported symbol, in test or production code. Either it is genuinely dead exported code (candidate for the migration prompt's stance that dead code may be omitted only with an explicit ruling, not silently) or it is intended for a not-yet-written caller. **Needs an explicit ruling before Stage 2**: port it faithfully as unreachable, or obtain confirmation it may be dropped.
3. **`identityAtQuarterTurn`'s `string | undefined` return type is provably never `undefined`** (§8), making `canonicalCollisionLayoutIdentity`'s `.some(id => id === undefined)` guard (`:147`) dead code. Low risk either way (reproducing dead code is always safe), but worth an explicit acknowledgment in the Rust port's code comments so a future reviewer does not "helpfully" delete the guard's Rust equivalent while leaving behavior technically unchanged but the intent undocumented — or, per the prompt's standard for proven-unreachable code, an explicit ruling could permit omitting it with a citation to this document.
4. **`extendFreeMaterial`/`createFreeMaterialService('direct-difference')` are confirmed unreachable from any current production job** (§1), yet both are required for `tests/unit/freeMaterialService.test.ts` byte-for-byte parity per the migration prompt's §3 test-immutability rule. This creates a real prioritization question for Stage 2: both must still be ported with full correctness (not stubbed), but neither should be assumed relevant to the Stage 4 parallelism/cache-architecture work in §13, since they never execute under real load. Flagged so the performance-contract work (`docs/planning/rust-irregular-backend/...` performance docs, not read for this cluster) does not accidentally budget time against a codepath that cannot be reached.
5. **Unguarded `Number` subtraction of two canonical-grid safe integers in `identityAtQuarterTurn`'s translation step** (`canonicalLayoutGeometry.ts:608`, `x - minX`/`y - minY`) has no `Number.isSafeInteger` result check, unlike the cluster's exact-`bigint` functions. As derived in §7, IEEE-754 subtraction of two values within `±(2^53−1)` can lose up to 1 unit of exact integer precision when their difference exceeds `2^53` in magnitude — a scenario only reachable at the extreme edge of what `Number.isSafeInteger` (not `maxScaledCoordinate`) admits, i.e., far beyond any coordinate this system's practical geometry pipeline produces (§7's practical-bound discussion). This is recorded as a precise, source-derived correctness edge case, not a practical concern: **the TypeScript original itself has this latent imprecision**, so a byte-identical Rust port must reproduce the same unguarded `f64` subtraction (not "fix" it with an exact/checked path) to stay faithful to the migration prompt's "the TypeScript behavior IS the specification" rule.
6. **`doubledGridAreaToMm2` (this cluster) vs. `doubledGrid2ToMm2` (capacity cluster) implement the identical formula with different finiteness-guard policies** (§7). Confirmed by direct read of both files. A Rust port must keep these as two distinct functions with their own distinct guard behavior at their own call sites, not unify them — flagged prominently since "obviously the same, just merge them" is exactly the kind of simplification the migration prompt's §2 forbids without proof of unobservability.
7. **BigInt-to-fixed-width-integer representation choice for the exact cross-product/area/ratio computations is not yet decided** (§7) — this document derives concrete magnitude bounds (both the `Number.isSafeInteger`-extreme theoretical bound and the `maxScaledCoordinate`-based practical bound) but does not itself choose between checked `i128` and arbitrary-precision (`num-bigint` or equivalent) for the Rust implementation. Given `compareCanonicalGridRatios`'s cross-multiplication of already-squared magnitudes is the most exposed computation (within roughly two orders of magnitude of `i128::MAX` even at the practical bound), this decision should be made explicitly and justified in the Stage 2 implementation notes, not left implicit.
8. **`Number.prototype.toString()`/template-literal shortest-round-trip formatting equivalence between V8 and Rust's default `f64` `Display`** (§6) is asserted plausible but **not proven** for the `freeMaterialService.ts` mm-scale float keys (`polygonKey`, `comparePolygons`'s fallback). This is lower-stakes than the SHA-256-feeding integer-coordinate case (which is proven safe, §6) because these specific keys do not feed a hash in this cluster, only an internal sort order for `FreeMaterialSnapshot.regions`/`holes` — but if any downstream consumer (outside this cluster) ever serializes free-material region order into a parity-gated artifact, this equivalence should be verified with a differential test before relying on it.
