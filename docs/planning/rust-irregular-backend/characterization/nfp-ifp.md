## 1. Purpose and role in Compact / Compact Short Side execution

This cluster is the geometry engine that turns already-transformed collision polygons into legal candidate placement points for both Compact and Compact Short Side. It has three responsibilities:

1. **NFP (no-fit polygon) construction** (`nfpBoundaryCore.ts`): given a fixed placed piece's local collision polygon and a moving piece's local collision polygon, compute the relative Minkowski-difference boundary, cache it, then translate it into sheet space using the fixed piece's current placement.
2. **IFP (inner-fit / sheet bounds) construction** (`ifpBoundsCore.ts`): given a moving piece's transformed polygon and a rectangular sheet, compute the axis-aligned translation-bounds rectangle that keeps the polygon inside the sheet, with cache validation that never trusts a stale cached rectangle over the live polygon bounds.
3. **Candidate point generation and legality filtering** (`nfpIfpService.ts`): combine IFP corners, NFP vertices, antiparallel-edge support points, and IFP/NFP and NFP/NFP intersection points into one canonical point set, snap each point to the canonical grid, and keep the first grid-legal alternative per raw point that also passes an exact convex-overlap legality check (`placementValidation.ts`).

`nfpIfpTelemetry.ts` is a passive, opt-in counter module with no imports and no effect on control flow (self-documented at `nfpIfpTelemetry.ts:1-15`); it is read by nothing that participates in canonical output.

## 3. Data in/out: exact types/shapes, optional-field presence/omission semantics

### Inputs (from `services.ts`)

- `ComputeNfpInput` (`services.ts:126-132`): `{ fixed: IrregularPlacedPiece, moving: TransformedCollisionGeometry, settings: IrregularNestingSettings['geometry'] }`. No optional fields.
- `ComputeIfpBoundsInput` (`services.ts:134-137`): `{ sheet: SheetSpec, moving: TransformedCollisionGeometry }`. No optional fields.
- `GeneratePlacementCandidatesInput` (`services.ts:177-189`): `sheet`, `placed: ReadonlyArray<IrregularPlacedPiece>`, `moving: TransformedCollisionGeometry`, `settings: IrregularNestingSettings`, and five **optional** fields:
  - `placedCollisionIndex?: PlacedCollisionSpatialIndex` — when present *and* `matches(input.placed)` returns true (`nfpIfpService.ts:308-311`), the spatial index is consulted instead of a per-candidate linear scan; a stale index (`matches` false) is silently discarded, not an error.
  - `candidateDomain?: 'sheet' | 'contact-only' | 'sheetless-nfp'` — **absence is treated identically to `'sheet'`** everywhere except the memo key (`geometryCacheKeys.ts:104`, `input.candidateDomain ?? 'sheet'`) and `emitCandidateProvenance` (n/a); the runtime branch conditions (`nfpIfpService.ts:279,357`) use `=== 'sheetless-nfp'` / `!== undefined && !== 'sheet'`, which are equivalent to treating `undefined` as `'sheet'`.
  - `candidateMemoScope?: IrregularNfpIfpCandidateMemoScope` — absence bypasses the whole memo layer (`nfpIfpService.ts:631-639`, recorded as `NfpIfpTelemetry.recordMemoBypass()`).
  - `onCandidateProvenance?: (provenance) => void` — absence skips provenance accumulation entirely (`makeCandidateProvenance()` is only called when this is defined, `nfpIfpService.ts:277-278`); this changes the returned `emitCandidateProvenance` no-op guard at `nfpIfpService.ts:950` but never changes the returned `candidates` array.
  - `control?: IrregularNfpIfpControl` — absence makes every `nfpCheckpoint` call an immediate `Effect.void` that cannot fail or suspend (`nfpIfpService.ts:1074-1076`).
- `CoreNfpInput` (`nfpBoundaryCore.ts:90-108`) and `InnerFitBoundsKeyInput` (`geometryCacheIdentity.ts:24-31`) are the "core" (domain-model-free) mirrors of the above, built from plain `Internal*` shapes (`internalGeometry.ts`) so the pure core modules do not depend on `@shared/irregular/domain.js` classes.

### Outputs

- `IrregularNfp` (`domain.ts:793-807`): `{ fixedPieceId: PieceId, movingPieceId: PieceId, boundary: IrregularPolygon }`. Constructed at `nfpIfpService.ts:121-125`; `fixedPieceId` comes from `input.fixed.placement.sourcePieceId`, `movingPieceId` from `input.moving.sourcePieceId`.
- `IrregularIfpBounds` (`domain.ts:817-831`): `{ sheet: SheetSpec, movingPieceId: PieceId, bounds: IrregularBounds }`.
- `IrregularPlacementCandidate` (`domain.ts:766-783`): `{ pieceId: PieceId, transform: IrregularTransformCandidate, point: IrregularPoint, diagnostics: ReadonlyArray<CollisionGeometryDiagnostic> }`. In this cluster `diagnostics` is always `[]` at construction time (`nfpIfpService.ts:518-523`, `1279-1288`); nothing in this cluster appends to it.
- `CoreNfpResult` (`nfpBoundaryCore.ts:110-121`) carries `{ ok: true, boundary, key: GeometryCacheKey }` on success. **The `key` field is part of the tested public contract of the core module** (`tests/unit/nfpBoundaryCore.test.ts:35-38` asserts on `miss.key`), but both `nfpIfpService.ts` wrapper call sites (`computeNfpBoundaryCached` at `nfpIfpService.ts:136-140`, `resolveNfpBoundaryFromServiceStore` at `nfpIfpService.ts:148-150`) discard `.key` — it never reaches a consumer in production. Same pattern for `CoreIfpBoundsSuccess.key` (`ifpBoundsCore.ts:16-23`).
- `NfpIfpCandidateProvenance` (`services.ts:161-175`): an **observer-only** snapshot, explicitly documented as unable to alter admission (`services.ts:157-160`). Two of its fields (`phaseIncompatible`, `canonicalChecked`, `canonicalLegal`) are hard-coded to the literal string `'not-evaluated'` by this cluster (`nfpIfpService.ts:973-977`) — this cluster never computes them; they exist for a different observer (outside this cluster) to fill in.

### Optional-field omission in constructed objects

`IrregularPlacement` (`domain.ts:694-715`) uses `declare readonly pieceId?` / `declare readonly placementReference?` with `Object.prototype.hasOwnProperty.call` guards in its constructor so that omitted fields are truly *absent* keys, not `undefined`-valued keys. This cluster does not construct `IrregularPlacement` itself but reads `fixed.placement.transform.translateX/Y` (`nfpBoundaryCore.ts:471-472`, `nfpIfpService.ts:853-856`) and `fixed.placement.sourcePieceId` (`nfpIfpService.ts:122`) — a Rust port must preserve that `IrregularPlacedPiece.placement` always carries a `transform` and `sourcePieceId` for any piece passed into this cluster (both are non-optional in `IrregularPlacement`).

## 4. Algorithm state and every mutation point

`ifpBoundsCore.ts` and `nfpBoundaryCore.ts`'s exported hull/canonicalization functions are pure with respect to their own arguments; the only mutation is through the injected `GeometryCacheStore` (`cache.get`/`cache.set`/`cache.remove`).

### `nfpBoundaryCore.ts`

- `validatedRings` (`nfpBoundaryCore.ts:31-37`) — a **module-level `WeakMap<object, {fingerprint, validation}>`**, keyed by the exact `points` array object identity. `validateStrictBoundaryOnce` (`nfpBoundaryCore.ts:39-55`) reads it, and on a fingerprint mismatch or an unfingerprintable ring, `validatedRings.delete(points)` (line 50) then `validatedRings.set(points, {...})` (line 52) on success. This is a transparent memoization: it always returns exactly what a direct call to `ConvexPolygonValidation.validateStrictBoundary(points)` would return (verified by tracing: every branch either returns the memo or falls back to a fresh `validateStrictBoundary` call). **A Rust port may omit this cache entirely with zero semantic effect** (see §12), because it exists only to avoid re-running `O(n²)` self-intersection checks in the JS process's GC-scoped lifetime; it never influences which value is returned, only how fast.
- `resolveNfpBoundary` (`nfpBoundaryCore.ts:125-167`) mutates the caller-supplied `cache` in exactly one of two ways per call: (a) on a valid cache hit, no mutation; (b) on a miss or stale hit, `cache.remove(key)` (only if `cached !== undefined`, line 154) followed by `cache.set(key, computed)` (line 162) — but **only if `computeRelativeNfpBoundary` succeeds** (line 160 returns early on failure, before any `cache.set`).

### `ifpBoundsCore.ts`

- `resolveIfpBounds` (`ifpBoundsCore.ts:37-59`) mutates `cache` identically in shape: `cache.remove(key)` only when a previously-present-but-invalid entry existed (line 54), `cache.set(key, computed.value)` only on a **successful** compute (line 57; the `'infeasible'`/`'invalid'` failure branch at line 56 returns before any `cache.set`).

### `nfpIfpService.ts`

- `generatePlacementCandidatesUncached` (`nfpIfpService.ts:267-560`) is one large function-scoped mutation:
  - `nfpBoundaries: NfpBoundary[]` (line 312) — pushed once per placed piece, in placed-array order (line 341-351).
  - `points: CanonicalPointSet` (`makeCanonicalPointSet()`, line 358) — three internal collections (`keys: Set<string>`, `points: InternalPoint[]`, `sourceMasks: Map<string, number>`), mutated only through `addPoint` (line 1201-1228).
  - `acceptedGridKeys: Set<string>` (line 493) — membership-only; grows monotonically as legal candidates are accepted (line 549).
  - `legalCandidateSourceMasks: Map<string, number>` (line 494) — grows/updates (bitwise-OR) for every grid key that passes legality, whether or not it was the *first* acceptance for that key (lines 544-547).
  - `candidates: IrregularPlacementCandidate[]` (line 491) — pushed exactly once per unique accepted grid key, in the traversal order of `sortedPoints` (line 550).
  - All of the above are local to one call; an abort (`IrregularNfpIfpControlAbortError`) at any `yield*` checkpoint discards them wholesale (Effect-gen short-circuit), and none of them alias into the shared `GeometryCacheStore`.
- `makeGeneratePlacementCandidates` (`nfpIfpService.ts:606-695`) closes over one **per-Layer-instantiation** `candidatesByScope: WeakMap<IrregularNfpIfpCandidateMemoScope, Map<string, CachedLegalCandidateEntry>>` (line 611-614). Mutation: `candidatesByScope.set(scope, new Map())` on first use of a scope (lines 643-646, get-or-create), then `candidatesByGeometry.set(key, {...})` (lines 685-688) **only inside `Effect.tap`, i.e. only after `generatePlacementCandidatesUncached` succeeds** — a failed/aborted computation never populates the memo.
- Because `IrregularNfpIfpCandidateMemoScope` instances are created fresh per decoder invocation at every production call site (confirmed by `grep -n "new IrregularNfpIfpCandidateMemoScope"` across `intrinsicStrictDecoder.ts:471`, `windowedBeam.ts:367`, `intrinsicCapacitySearch.ts:450`, `intrinsicQueueBeamDiscriminator.ts:675,1087`, `intrinsicDetachedPieceReinsertion.ts:109`, `intrinsicExactProjection.ts:300`), each scope's `Map` is naturally bounded to one decode/search invocation and becomes eligible for GC once the caller's local `candidateMemoScope` variable goes out of scope — this is the JS analogue of the "job-local, bounded" cache lifetime the migration prompt requires (§13.6).
- `GeometryCache`/`GeometryCacheLive` (`services.ts:433-446`) is built with `Layer.sync`, so its backing `Map` (`geometryCacheStoreLive.ts:10`) is instantiated once per `Effect.provide(NfpIfpServiceLive)` build — in production this happens once per nesting job (`nesting.worker.ts:377-398`), confirming this cluster's caches are **job-local**, not process-global or cross-job.
- **Dead/defensive branch**: `candidateNfpBoundaries`'s ternary (`nfpIfpService.ts:362-370`) includes an `ifpBounds === undefined ? [] : ...` arm that is unreachable when `!sheetlessNfp`, because the function already returned `[]` earlier (line 303-306) whenever `ifp === undefined` in that case. A Rust port does not need to reproduce this as reachable, but should preserve the same *value* (`[]`) if it chooses to keep the defensive check.

## 5. Ordering sources: sorts, Map/Set insertion order, iteration order reaching output

- **`sortedPoints = [...points.points].sort(comparePoints)`** (`nfpIfpService.ts:492`) — the single most important ordering source: it fixes the traversal order over which candidate legality is tested and thus the order of the returned `candidates` array (first-accepted-per-grid-cell wins, see §6). `comparePoints` (`nfpIfpService.ts:1234-1237`) is `y` ascending then `x` ascending.
  - Because `points.points` only ever contains **exactly-distinct** `(x, y)` pairs (deduplicated by `addPoint`'s `points.keys.has(key)` check, `nfpIfpService.ts:1221`, keyed by the exact string `pointKey` = `` `${x}:${y}` ``), `comparePoints` can never actually return `0` for two different array elements — every pair of distinct points differs in `y` or, when `y` ties, in `x`. **This sort therefore has no observable ties and does not rely on `Array.prototype.sort` stability for correctness**, even though V8's sort is stable. This still matters as a documented invariant, not an accident.
  - The *insertion* order of `points.points` (i.e. the order corners/vertices/support points/intersections were discovered) is irrelevant to the final `candidates` order because of the subsequent full re-sort — a Rust port may build the equivalent point set in any internal order as long as it re-sorts by `(y, x)` before the candidate loop.
- **`canonicalPlacementPointAlternatives`** (`nfpIfpService.ts:569-593`) returns its 9 grid-snapped alternatives `.toSorted(compareCanonicalCandidatePoints)` (line 592), where the comparator (`nfpIfpService.ts:595-604`) orders by `squaredDistance` from the raw point, then `gridX`, then `gridY`. This order determines **which** of up to 9 alternatives is tried first for each raw point (see §6).
- **`BoundsIndex`** (`nfpIfpService.ts:737-769`) sorts its entries once at construction via `.toSorted(compareBoundsIndexEntries)` (line 744), a comparator that finishes with an explicit `sourceIndex` tiebreak (`nfpIfpService.ts:791`) attached at construction time (`entries.map((entry, sourceIndex) => ({...entry, sourceIndex}))`, line 743) — this makes the sort's result independent of whether the underlying JS engine's sort is stable, and its `query()` results preserve this same total order because it linearly scans the sorted array (`nfpIfpService.ts:760-765`), never inserting into an unordered structure.
- **`CanonicalPointSet.keys: Set<string>`** and **`acceptedGridKeys: Set<string>`** are used only for membership tests (`.has`), never iterated for output. **`points.sourceMasks: Map<string,number>`** and **`legalCandidateSourceMasks: Map<string,number>`** are mutated with insertion-order-dependent `Map` semantics internally, but every place their contents reach an externally observable value re-sorts explicitly before use:
  - `uniqueBySourceMask` (`nfpIfpService.ts:951-954,965-967`) is derived from `points.sourceMasks.values()` (Map iteration order) but the final snapshot field is `[...uniqueBySourceMask].map(...).toSorted((a,b) => a.sourceMask - b.sourceMask)`.
  - `legalCandidateSources` (`nfpIfpService.ts:955-962,978`) is derived from `[...legalCandidateSourceMasks]` (Map iteration order = discovery order during the candidate loop) but is explicitly `.toSorted((first, second) => first.gridY - second.gridY || first.gridX - second.gridX)`.
  - `rawBySource: Record<NfpIfpCandidateSource, number>` (`makeCandidateProvenance`, `nfpIfpService.ts:928-941`) is a **plain object literal** whose key order is fixed lexically at that call site (`ifpCorner, nfpVertex, antiparallelEdgeSupport, ifpNfpIntersection, nfpNfpIntersection`), matching `NFP_IFP_CANDIDATE_SOURCE_MASK`'s declaration order (`services.ts:140-146`). Object key enumeration order for these string keys (none are array-index-like) follows ES2015+ insertion order, so this is deterministic but is an *object property order* concern, not a `Map`/`Set` concern — a Rust `struct` with named fields naturally reproduces it without needing to think about ordering at all.
  - **All of the above provenance fields are observer-only** (`services.ts:157-160`) and are never fed into a hash, cache key, or the returned `candidates` array — a Rust port can pick any convenient ordering, though preserving the exact order is cheap and recommended for differential trace tooling.
- **`nfpIfpTelemetry.ts`**'s `Map<string, ...>` state (`namespaces`, `checkpointsByPhase`, `nfpIfpTelemetrySnapshot()` at lines 142-169) explicitly re-sorts both maps lexically (`.toSorted(([first],[second]) => first < second ? -1 : first > second ? 1 : 0)`, lines 146-148 and 152-154) before building the returned plain-object snapshot — again neutralizing Map iteration order, and using **JS default `<`/`>` string comparison** (UTF-16 code-unit order), which a Rust port must reproduce with a code-unit (not locale, not byte-for-byte-UTF8) comparator if telemetry snapshots are ever compared byte-for-byte (they are explicitly not parity-gated per the migration prompt §13.7, so this is low severity).
- **`Map` iteration order used as a genuine ordering source (not neutralized) for cache identity**: none found in this cluster — `GeometryCacheStore`'s backing `Map<string, unknown>` (`geometryCacheStoreLive.ts:10`) is used purely for `get`/`set`/`remove`/`clear`, never iterated.

## 6. Comparators and tie rules: exact comparison chains, signs, tie-breakers

- `comparePoints(first, second)` (`nfpIfpService.ts:1234-1237`): `first.y - second.y || first.x - second.x`. Ascending `y`, then ascending `x`. No further tiebreak needed (see §5 — no ties possible on distinct points).
- `compareCanonicalCandidatePoints(first, second)` (`nfpIfpService.ts:595-604`): `first.squaredDistance - second.squaredDistance || first.gridX - second.gridX || first.gridY - second.gridY`. This is the tie rule for **which of the 9 canonical-grid neighbors of a raw point is preferred**: nearest squared Euclidean distance to the raw (unsnapped) point wins; on a distance tie, lower `gridX` wins; on a further tie, lower `gridY` wins. Because the 9 candidates are `{centerX + dx, centerY + dy} for dx,dy in {-1,0,1}`, a distance tie can genuinely occur (e.g. `dx=-1,dy=0` vs `dx=0,dy=-1` when the raw point sits exactly between two grid steps) — the `gridX` then `gridY` tiebreak is load-bearing, not defensive.
- `compareBoundsIndexEntries(first, second)` (`nfpIfpService.ts:775-792`): lexicographic on `(minX, maxX, minY, maxY, sourceIndex)`, each compared with `!==` before subtracting (avoiding `NaN`-from-subtraction ambiguity, though inputs are already validated finite). The final `sourceIndex` tiebreak makes the sort a total, deterministic order matching original-array position for bounds-identical entries.
- **Legality tie rule for candidate acceptance** (`nfpIfpService.ts:495-554`, the core "which point wins" algorithm):
  1. Outer loop over `sortedPoints` in `(y, x)` order.
  2. For each raw point, inner loop over its 9 canonical-grid alternatives in `(squaredDistance, gridX, gridY)` order.
  3. Skip an alternative if (`!sheetlessNfp` and it is outside `ifpBounds`, or strictly inside any candidate NFP boundary) (`nfpIfpService.ts:501-516`) — `isStrictlyInside` (`nfpIfpService.ts:1264-1277`) requires **every** edge turn to equal the boundary's own winding and be non-zero (an on-boundary/touching point is *not* "strictly inside", i.e. touching is legal — consistent with `assessPlacement`'s closed-boundary convention documented at `placementValidation.ts:32-33`).
  4. Otherwise assess placement legality (`assessPlacement`, synchronous, `placementValidation.ts:70-144`); if illegal, try the next alternative.
  5. **The first alternative (in the fixed 9-neighbor order) that is inside IFP bounds (or sheetless), not strictly inside any NFP, and legal wins**; the candidate loop then `break`s out of the alternatives loop and moves to the next raw point (`nfpIfpService.ts:552`).
  6. A winning alternative is only pushed to `candidates` if its `gridKey` (`` `${gridX},${gridY}` ``, `nfpIfpService.ts:543`) has not already been accepted by an *earlier* raw point in the outer traversal (`nfpIfpService.ts:548-551`); the source-mask bit-OR still updates even on a repeat (`nfpIfpService.ts:544-547`).
- `boundariesForPoint.some(...)` (`nfpIfpService.ts:508-512`): short-circuits on the first matching NFP boundary — order-independent for a boolean "any" test, but note it uses the (pruned or full) NFP boundary set in whatever order `BoundsIndex.query`/array iteration returns it; since this is only used for a boolean OR, order is provably immaterial here.
- `GeometryPredicates.orientation` (`geometryPredicates.ts:16-35`) is the base comparator for every turn/winding/collinearity decision in this cluster and its callees (`convexPolygonValidation.ts`, `convexHullCore.ts`, `placementValidation.ts`, `nfpBoundaryCore.ts`). It wraps `orient2d` from `robust-predicates@3.0.3` (`package.json:47`) and **flips its sign**: "robust-predicates uses a y-down screen convention, while DXF geometry uses y-up coordinates" (`geometryPredicates.ts:30-31`). Result convention in this codebase: **`+1` = left/CCW turn, `-1` = right/CW turn, `0` = collinear**, in the app's y-up coordinate system.
- `buildHullHalf` (`convexHullCore.ts:28-41`) pops the hull stack while `GeometryPredicates.orientation(previousPoint, lastPoint, point) <= 0` (i.e. keeps popping on a right turn or collinear triple; stops — keeps the point — on a strict left/CCW turn, `> 0`, line 35). Points are pre-sorted by `(x, y)` ascending (`convexHullCore.ts:6-9`) with exact-duplicate adjacent points removed by `deduplicateSortedPoints` (`convexHullCore.ts:18-26`) before the hull halves are built.
- `compareEdgeDirections` (`nfpBoundaryCore.ts:420-429`), used only by the non-production `'linear-edge-merge'` NFP algorithm: buckets edges into an upper/lower half-plane via `edgeDirectionHalf` (`nfpBoundaryCore.ts:431-433`, `edge.y > 0 || (edge.y === 0 && edge.x >= 0)` → half `0`, else half `1`), compares half first, then uses `orientation(ORIGIN, firstEdge, secondEdge)` to order directions within a half (`> 0` → `-1`, `< 0` → `1`, else `0`). This is a standard angular sort by polar half-plane + cross-product, present for completeness though not on the production path.
- `rotateToStableStart` (`nfpBoundaryCore.ts:494-505`) rotates a ring so it starts at the point with the smallest `(y, x)` (found via a linear scan preferring the *first* occurrence on ties, since the comparison is strict `<`, line 500) — this is the canonical starting-vertex rule applied after every NFP boundary construction path (`computeRelativeNfpBoundaryReference`, `computeRelativeNfpBoundaryLinear`, `canonicalizeTranslatedConvexRing`, `canonicalizeTranslatedConvexRingWithHullFallback`).
- `canonicalPolygonDigest` (`nfpCacheKey.ts:59-74`) computes both the forward and reverse cyclic point-digest strings starting from the lexicographically-smallest-`(x,y)` vertex, and **returns whichever string compares smaller** (`forward < reverse ? forward : reverse`, line 73) — this makes the pairwise-NFP cache key **invariant to the stored winding direction** of the input polygon (see §9 for why this is provably safe for the NFP math itself).

## 7. Numeric semantics: BigInt, Number arithmetic order, Math.*, rounding, signed zero, NaN/Infinity, safe-integer, grid conversion

No `BigInt` usage anywhere in this cluster (`grep -n "BigInt" nfpIfpService.ts nfpBoundaryCore.ts ifpBoundsCore.ts nfpIfpTelemetry.ts` → empty). All coordinates are IEEE-754 `number` (binary64).

- **Grid conversion (`clipper2OffsetPolicy.ts:44-58`)**, imported directly into `nfpIfpService.ts:42` and used only in `canonicalPlacementPointAlternatives` (`nfpIfpService.ts:572-573,581`):
  - `toGridMm(valueMm)`: `undefined` if `!Number.isFinite(valueMm)`; else `scaledAbsoluteValue = Math.abs(valueMm) * 1000`; `undefined` if that is not finite; `roundedAbsoluteValue = Math.floor(scaledAbsoluteValue + 0.5)` (this is **"round half away from zero" applied to the absolute value**, not a library round call — a Rust port must replicate this exact three-step formula, not assume `f64::round()` matches bit-for-bit in every case); `gridValue = Math.sign(valueMm) * roundedAbsoluteValue`; `undefined` unless `Number.isSafeInteger(gridValue)` (`|gridValue| <= 2^53 - 1` and integral).
    - **Signed-zero note**: `Math.sign(-0) === -0` in JS. If `valueMm` is `-0` (or rounds to an absolute value of `0`), `gridValue = -0 * 0 = -0` (IEEE `-0`), and `Number.isSafeInteger(-0)` is `true`, so `toGridMm` **can return `-0`**. This does not currently leak into visible output from `canonicalPlacementPointAlternatives`, because `gridX = centerX + deltaX` for `deltaX ∈ {-1,0,1}`: `-0 + 0 = +0` (not `-0`, per IEEE-754 addition), `-0 + (-1) = -1`, `-0 + 1 = 1` — so the sum is never `-0` regardless of whether `centerX` was `-0`. A Rust port using `f64` must confirm this same cancellation holds (Rust's `f64` addition follows IEEE-754 identically, so it will).
  - `fromGrid(value)`: `value / 1000`, no further rounding.
- **Signed-zero normalization** is applied explicitly and repeatedly at specific, load-bearing points, always via the same idiom `Object.is(value, -0) ? 0 : value`:
  - `normalizeNegativeZero` in `nfpIfpService.ts:1290-1292`, applied to every point added to the canonical point set (`addPoint`, `nfpIfpService.ts:1211-1214`).
  - `normalizeNegativeZero` in `ifpBoundsCore.ts:129-131`, applied to all four IFP bound coordinates (`ifpBoundsCore.ts:74-77`).
  - `numberIdentity` in `nfpBoundaryCore.ts:86-88` (ring fingerprinting) and `numberKey` in `nfpCacheKey.ts:104-106` / `geometryCacheIdentity.ts:139-141` / `geometryCacheKeys.ts:158-160` (cache key digests) all use the identical pattern.
  - **A Rust port must normalize `-0.0` to `0.0` at exactly these points and nowhere additionally**, since the migration prompt forbids introducing new tolerances/behavior; over-normalizing (e.g. at every arithmetic step) would still be observably different only if it changed a value that currently survives as `-0` somewhere externally visible — auditing showed no such surviving case in this cluster, but a Rust implementer should not assume that and should differential-test both directions.
- **`Number.isFinite` / `Number.isSafeInteger` guards** appear before nearly every arithmetic result is trusted: `nfpBoundaryCore.ts:76-77` (ring fingerprint precondition), `nfpBoundaryCore.ts:412,442,473` (edge vectors, Minkowski sums, translation), `nfpIfpService.ts:580` (grid alternative safe-integer check), `nfpIfpService.ts:874,884,911` (antiparallel support point arithmetic), `nfpIfpService.ts:1113-1123,1129-1131,1141-1147,1156-1163` (segment intersection arithmetic, in three separate finite-checked stages — direction vectors, the primary Cramer's-rule solve, and the near-parallel fallback), `ifpBoundsCore.ts:78-85` (IFP bound arithmetic), `placementValidation.ts:262-263,271-279` (interior-point weighted average). None of these guards silently clamp; every failure returns a typed `{message: string}`/`GeometryFailure` that propagates to `IrregularGeometryInputError` (§11).
- **NaN handling**: no explicit `Number.isNaN` checks; NaN is excluded implicitly because every consuming site first checks `Number.isFinite`, and `NaN` fails that check (`Number.isFinite(NaN) === false`). A Rust `f64::is_finite()` check has identical semantics (excludes both NaN and ±Infinity) and is the correct one-to-one substitute.
- **Segment-intersection numeric strategy** (`intersectSegments`, `nfpIfpService.ts:1086-1186`) is the most numerically delicate function in the cluster:
  1. Uses `GeometryPredicates.orientation` (exact-sign robust predicate) to classify a *proper* crossing first (`firstStartTurn !== firstEndTurn && secondStartTurn !== secondEndTurn`, all four turns non-zero, lines 1096-1103).
  2. Computes a floating-point `denominator = firstDirectionX * secondDirectionY - firstDirectionY * secondDirectionX` (line 1108) and, if it is finite and non-zero, solves via `parameter = numerator / denominator` and returns the single computed point (lines 1125-1133).
  3. **If the exact predicate says "proper crossing" but the floating determinant rounds to exactly `0`** (comment at `nfpIfpService.ts:1135-1136`: "exact predicates prove a strict crossing, but near-parallel direction products can still round the floating denominator to zero"), it falls back to a **signed-area ratio** (`startArea`, `endArea`, lines 1139-1140) computed along the *first* segment's direction, requires `oppositeSigns` (strict `>0`/`<0` on both sides, line 1152 — a tie/zero here is treated as "no fallback point", not a crash), computes `fallbackParameter = startArea / (startArea - endArea)` and rejects it unless strictly inside `(0, 1)` (line 1159) and the resulting point is within both segments' bounding boxes (`pointIsWithinSegmentBounds`, lines 1167-1172). This fallback exists specifically to keep a result *finite and boxed* when the naive linear solve is numerically degenerate despite being classified as an exact crossing — **a Rust port must implement this exact three-stage fallback, not simplify to a single linear solve**, or it will silently drop legitimate contact points in near-parallel cases.
  4. Collinear/touching case (`firstStartTurn === 0` etc., lines 1176-1183) adds each endpoint that both the zero-orientation test and `pointIsWithinSegmentBounds` (inclusive `>=`/`<=`, lines 1188-1195) agree lies on the other segment.
- **`strictConvexInteriorPoint`** (`placementValidation.ts:258-283`) computes the unweighted vertex centroid as `1/n` times each vertex, summed in **array (ring) order** — this is a plain left-to-right floating-point summation whose exact binary64 result depends on iteration order; a Rust port must sum in the same `points` array order (not, say, pairwise/tree reduction) to bit-match.
- **`toGridMm`/`fromGrid` and `Math.floor(x+0.5)`, `Math.sign`, `Math.abs`, `Math.min`, `Math.max`** are the only `Math.*` calls in this cluster; `Math.max`/`Math.min` appear in `segmentBounds` (`nfpIfpService.ts:1020-1027`), `intersectionBounds` (`nfpIfpService.ts:1243-1253`), and `pointIsWithinSegmentBounds`/`pointIsOnSegment` (bounding checks) — all standard IEEE binary64 min/max with no NaN-propagation concerns given upstream finiteness guards.
- **String rendering used by keys**: `numberKey`/`numberIdentity` (see above) all resolve to plain `String(value)` for any value that is not `-0`. JS `Number.prototype.toString()` (the ECMA-262 `Number::toString` algorithm) produces the shortest decimal string that round-trips to the same binary64 value, switching to exponential notation outside roughly `[1e-6, 1e21)`. **This is a top parity risk** — see §12/§15.

## 8. Serialization and hashing

This cluster's serialization is **entirely internal, ephemeral, and job-scoped**. It never feeds a persisted canonical hash: `grep -rn "IrregularGeometryCacheKey" src --include="*.ts"` (excluding this cluster's own files and `domain.ts`) returns nothing — no decision trace, history frame, or checkpoint file ever carries one of this cluster's cache keys. This bounds the severity of any serialization mismatch to *in-process cache-hit-rate correctness*, not cross-language byte parity of persisted artifacts.

- `serializeGeometryCacheKey(key)` (`geometryCacheStore.ts:13-15`): `JSON.stringify([key.namespace, key.parts])`. This is the literal string used as the JS `Map<string, unknown>` key in `makeGeometryCacheStore` (`geometryCacheStoreLive.ts:13-24`). Two `GeometryCacheKey`s with the same `namespace`/`parts` array (element-wise, in order) always serialize identically because `JSON.stringify` on an array of strings is a fixed, order-preserving encoding (each string individually escaped per JSON string-escaping rules: `"`, `\`, control characters `< 0x20`, `U+2028`/`U+2029` are **not** escaped by `JSON.stringify` — plain UTF-16 passthrough otherwise).
- `makePairwiseNfpCacheKey` (`nfpCacheKey.ts:31-47`) builds `parts` as an ordered array of `key=value` strings: `fixed-polygon=<digest>`, `moving-polygon=<digest>`, `fixed-transform=<digest>`, `moving-transform=<digest>`, then `geometrySettingsParts` (`nfpCacheKey.ts:49-57`: `flattening-sag`, `clearance-margin`, `backend`, `backend-version`, and the **literal constant string** `'offset-policy=clipper2-offset-v3-sharp-miter-scale-1000'`), then the literal `'nfp-algorithm=convex-fixed-plus-negated-moving-relative-v3'`, then `` `nfp-construction=${constructionAlgorithm}` ``. Namespace is the module constant `'pairwise-nfp-relative-v3'` (`nfpCacheKey.ts:4`).
- `makeInnerFitBoundsCacheKey` (`geometryCacheIdentity.ts:51-62`) builds `parts` as `sheet=<w>,<h>,<label>`, `moving-piece=<id>`, `moving-transform=<digest>`, `moving-polygon=<digest>`, `ifp-operation=rectangular-sheet-vertex-bounds`. Namespace `'sheet-ifp-v1'` (`geometryCacheIdentity.ts:14`).
- `canonicalPolygonDigest` (`nfpCacheKey.ts:59-74`) is the only non-trivial digest: it picks the lexicographically-smallest-`(x,y)` starting vertex (line 61-69), computes the cyclic point-list digest **forward and reverse** from that start (`cyclicPolygonDigest`, lines 76-89, joining `` `${x},${y}` `` per point with `;`), and keeps whichever plain-string comparison (`<`) is smaller. Empty point arrays digest to `''` (line 60). This function is **rotation- and winding-direction-invariant by construction** — see §9 for why that is semantically safe here.
- `legalPlacementCandidateMemoKey` (`geometryCacheKeys.ts:77-106`) builds a `JSON.stringify([...])` array of: the namespace literal `'legal-placement-candidates-v1'`, a sheet identity string (`'sheet=deferred'` for `candidateDomain === 'sheetless-nfp'`, else `` `sheet=${w},${h}` `` — **height/width only, sheet `label` is not part of this key**, unlike the IFP key above), a `|`-joined list of `` `${polygonDigest}@${translationDigest}` `` per placed piece **in `input.placed` array order** (not sorted — order-sensitive by design, since candidate legality genuinely depends on placed-piece order for tie-breaking downstream, though the *set* of legal points does not), the moving polygon digest, the moving bounds digest, geometry settings parts, `` `nfp-construction=${constructionAlgorithm}` ``, `` `candidate-pruning=${candidatePruningMode}` ``, `` `candidate-domain=${input.candidateDomain ?? 'sheet'}` ``. **This key intentionally omits `moving.sourcePieceId` and `moving.transform`** — see §9's "two-layer sharing" note.
- `pointKey(point)` (`nfpIfpService.ts:1230-1232`): `` `${x}:${y}` `` — an in-function-only dedup key for the `CanonicalPointSet`, never a cache key, never externally visible.
- **BigInt string encoding, `undefined` omission in canonical JSON, object-key sorting for checkpoint bytes** — none of these apply to this cluster; the migration prompt's §9 requirements about canonical checkpoint JSON govern a different subsystem (decision-trace/checkpoint serialization, outside this cluster's four files). This cluster's only `JSON.stringify` calls are `serializeGeometryCacheKey` and `legalPlacementCandidateMemoKey`, both plain-array encodings with no `undefined` fields and no object key ordering concerns (arrays only).

## 9. Caches touched and the exact historical access sequence

Three distinct caches/memos are touched by this cluster, each with a different scope and a different validate → lookup → stale-evict → recompute → publish sequence. **Preserving the exact sequence per cache is a named requirement of the migration prompt (§13.2).**

### A. Pairwise relative-NFP cache (`nfpBoundaryCore.ts:125-167`, namespace `pairwise-nfp-relative-v3`)

Exact sequence inside `resolveNfpBoundary`:

1. **Validate fixed** (`validateStrictBoundaryOnce(input.fixed.collisionGeometry.polygon.points)`, line 130) — fail immediately (before any key construction or cache access) if invalid.
2. **Validate moving** (line 135) — same.
3. **Build key** (`makePairwiseNfpCacheKey`, line 138-147) from the **local (untranslated)** fixed/moving polygons, their transform candidates, geometry settings, and construction algorithm.
4. **Lookup** (`cache.get<InternalPolygon>(key)`, line 148).
5. **Validate the cached value** (`isValidCachedNfpBoundary(cached)`, line 151 → `nfpBoundaryCore.ts:249-253`: checks `points.length >= 3` and re-runs `validateStrictBoundaryOnce` on the cached points). A structurally-fine-looking but geometrically-invalid cached polygon is treated as a miss.
6. **On valid hit**: use directly as `relativeBoundary` (no recompute, no cache write).
7. **On miss or invalid hit**: if `cached !== undefined` (i.e. something was present but failed validation), **stale-evict first** (`cache.remove(key)`, line 154); *then* recompute (`computeRelativeNfpBoundary`, line 155-159).
8. **Recompute failure**: return the failure immediately — **the cache is never written** (line 160).
9. **Recompute success**: `cache.set(key, computed)` (line 161-162) — **publish only after success**.
10. **Translate**: `translateNfpBoundary(input, relativeBoundary)` (line 165) applies `input.fixed.placement.transform.translateX/Y` to every relative-boundary point and re-canonicalizes (`canonicalizeTranslatedConvexRing`, with a convex-hull fallback `canonicalizeTranslatedConvexRingWithHullFallback` if the fast canonicalization fails, `nfpBoundaryCore.ts:479-482`).
11. **Translation/canonicalization failure happens *after* the cache was already published** in step 9 — the relative (untranslated) cache entry remains valid and reusable even when this particular caller's fixed-piece translation turns out to be unrepresentable (non-finite) or the translated ring degenerates; only *this call* fails.

**Relative-NFP sharing across canonically equivalent copies** (the migration prompt's explicit focus item): the cache key's polygon digests (`canonicalPolygonDigest`, `nfpCacheKey.ts:59-74`) are invariant to (a) which vertex the ring starts at and (b) which of the two traversal directions (winding) the array happens to store — see §6/§8. This means **any two placed pieces that share the same local collision-polygon shape and the same transform candidate, regardless of where they are currently translated on the sheet, hit the same relative-NFP cache entry**; step 10 then re-applies *this specific* fixed piece's own placement translation on every call, so the cache never returns a wrongly-translated NFP. This is provably safe because the relative-NFP math itself (`computeRelativeNfpBoundaryReference`, `nfpBoundaryCore.ts:255-276`) is order/winding-independent: it builds the Minkowski-sum point set via a nested loop over `fixedPoints × negatedMovingPoints` (the resulting *set* is identical regardless of the arrays' traversal order) and feeds it to `computeConvexHull`, which internally sorts by `(x, y)` before building the hull (`convexHullCore.ts:6-9`) — so hull construction does not depend on input order either. `computeRelativeNfpBoundaryLinear` (non-production) explicitly normalizes to CCW via the *validated* winding sign before merging edges (`counterClockwiseStablePoints`, `nfpBoundaryCore.ts:392-398`), so it too is invariant to the array's original stored order.

### B. Rectangular IFP-bounds cache (`ifpBoundsCore.ts:37-59`, namespace `sheet-ifp-v1`)

1. **Validate** (`ConvexPolygonValidation.validateStrictBoundary(input.moving.polygon.points)`, line 45) — fail before any key/cache access.
2. **Build key** (`makeInnerFitBoundsCacheKey`, line 48).
3. **Lookup** (line 49).
4. **Validate cached** (`isValidCachedIfpBounds`, line 50 → `ifpBoundsCore.ts:100-123`): re-derives `movingBounds` from the **live** `input.moving.polygon.points` (not from anything cached) and checks the cached `bounds` exactly equal `{-movingBounds.minX, -movingBounds.minY, sheet.width - movingBounds.maxX, sheet.height - movingBounds.maxY}` plus `movingPieceId`/`sheet.width`/`sheet.height` equality and finiteness. This is the concrete mechanism behind the doc comment at `nfpIfpService.ts:216-217`: *"`TransformedCollisionGeometry.bounds` is derived cache data and is not trusted at this legality boundary; a stale cache must not enlarge the IFP."* — the cache is validated against **freshly recomputed** bounds every time, never trusted blindly.
5. **On valid hit**: return directly.
6. **On miss or invalid hit**: stale-evict if present (line 54), then recompute (`computeIfpBounds`, line 55).
7. **Recompute failure** (`'invalid'` or `'infeasible'`): return immediately, **no cache write**.
8. **Recompute success**: `cache.set(key, computed.value)` (line 57).

### C. Legal-candidate memo (`nfpIfpService.ts:606-695`, namespace `legal-placement-candidates-v1`, held in a `WeakMap` outside `GeometryCacheStore`)

1. If `input.candidateMemoScope === undefined`, **bypass entirely** — `NfpIfpTelemetry.recordMemoBypass()` then call `generatePlacementCandidatesUncached` directly (no lookup, no publish) (`nfpIfpService.ts:631-639`).
2. Otherwise, get-or-create the scope's inner `Map` (`nfpIfpService.ts:642-646`).
3. Build `key` via `legalPlacementCandidateMemoKey` (line 647).
4. **Lookup** (`candidatesByGeometry.get(key)`, line 648).
5. **Cache-hit acceptance rule is provenance-aware, not just presence-aware**: a hit is only used if `cached !== undefined && (input.onCandidateProvenance === undefined || cached.provenance !== undefined)` (lines 649-652) — i.e. a caller that wants provenance cannot be served by an entry that was cached *without* provenance capture; that case is explicitly logged as `'provenance-miss'` (line 664) and treated as a miss for control flow, even though `cached` is technically present.
6. **On accepted hit**: still runs exactly one `nfpCheckpoint(input.control, 'candidate-points')` (line 654) before mapping to the result — a cooperative cancellation/deadline check is preserved even on a full memo hit. Then `restoreCachedLegalCandidates` (`nfpIfpService.ts:716-729`) rebuilds `IrregularPlacementCandidate` objects from the cached `{point, diagnostics}` pairs but **re-stamps `pieceId`/`transform` from the *current* `input.moving`**, not from whatever call originally populated the cache entry.
7. **On miss/provenance-miss**: call `generatePlacementCandidatesUncached` (with a provenance-observing wrapper if needed, lines 666-676), then `Effect.tap` publishes to the memo **only on success** (`Effect.tap` never runs on the failure channel) via `cacheLegalCandidates` (`nfpIfpService.ts:707-714`, a plain deep-ish copy of `{point, diagnostics}` pairs, preserving array order).

**Two-layer sharing, not one**: cache A (relative NFP) and cache C (legal candidates) both implement a "canonically equivalent copies share a cache entry" pattern, but at different levels and with different invariance properties:
- Cache A is invariant to ring rotation/winding but **specific to one (fixed-local-polygon, moving-local-polygon, fixed-transform, moving-transform, settings, algorithm)** tuple, and requires a **translation step after retrieval** (§A.10) to become sheet-space.
- Cache C's key (`legalPlacementCandidateMemoKey`, `geometryCacheKeys.ts:77-106`) is keyed on **exact ordered polygon digests** (not rotation/winding-canonicalized) for the moving polygon and every placed piece's polygon+translation, and **omits `moving.sourcePieceId`/`moving.transform` entirely** — so a cache C hit can be re-labelled with a *different* piece identity/transform metadata on retrieval (`restoreCachedLegalCandidates`) as long as the actual local polygon points and bounds are bit-identical to a previous call. This is correct because candidate *points* are pure geometry and do not depend on which `pieceId`/`transform` index produced that geometry — but a Rust port must not conflate this with cache A's rotation-invariant canonicalization; cache C requires **exact** point-array equality (via `polygonDigest`, a plain ordered `x,y;x,y;...` join), not canonicalized equality.

### D. `GeometryCacheStore` itself

`makeGeometryCacheStore()` (`geometryCacheStoreLive.ts:9-30`) is the single shared backing `Map` for caches A and B (they use different `namespace` prefixes within the same physical store, so key collisions across namespaces are impossible by construction — `serializeGeometryCacheKey` embeds `namespace` as the first array element). It records telemetry on every `get`/`set`/`remove` (§13.7 requirement) but telemetry never influences the returned value.

## 10. Cancellation / deadline / budget / evaluation-cap observation points (exact positions in loops)

All cancellation/deadline observation in this cluster flows through `IrregularNfpIfpControl.checkpoint(phase)` (`services.ts:85-89`), wrapped by `nfpCheckpoint` (`nfpIfpService.ts:1070-1084`), which is a **no-op, non-failing `Effect.void`** when `control === undefined` (telemetry-recorded as `'inert'`), or delegates to `control.checkpoint(phase)` when present (telemetry distinguishes `'direct-void'` vs `'composed'` by reference-equality against the `Effect.void` singleton, purely for diagnostics, `nfpIfpService.ts:1079-1082`).

Exact call sites in `generatePlacementCandidatesUncached` (`nfpIfpService.ts:267-560`), in execution order:

1. `nfpIfpService.ts:280` — phase `'ifp'`, **before** any IFP resolution or cache access. An abort here means zero cache interaction happens for this call (confirmed by the differential test `tests/unit/nfpIfpService.test.ts:1108-1119`).

## 11. Error paths: tagged error classes, categories, context fields, propagation

Three tagged Effect errors are declared in `services.ts` and used by this cluster (`Data.TaggedError`, giving each a `_tag` discriminant):

- `IrregularGeometryInputError` (`services.ts:42-45`): `{ operation: string, message: string }`. Raised by:
  - `failInvalidGeometry` helper in `nfpIfpService.ts:1294-1299`, called with `operation` values `'computeNfp'` (`nfpIfpService.ts:139,326`), `'computeIfpBounds'` (`nfpIfpService.ts:248,297`), `'generatePlacementCandidates'` (`nfpIfpService.ts:332,336,403,422,445,485`).
  - Every failure surfaced by `resolveNfpBoundary`/`resolveIfpBounds` (structural invalidity, non-finite arithmetic, degenerate rings) ultimately becomes this error type once it crosses back into `nfpIfpService.ts`; the core modules themselves return plain `{message}`/`{kind, message}` shapes (`CoreNfpFailure`, `nfpBoundaryCore.ts:116-119`; `CoreIfpBoundsFailure`, `ifpBoundsCore.ts:25-29`) and do not construct Effect errors directly (keeping the core pure-function modules Effect-free).
  - Also raised directly by `assessPlacement`'s failure channel when it returns `{failure: IrregularGeometryInputError}` (`placementValidation.ts` — invalid translated polygon, non-finite translation), re-raised via `Effect.fail(assessment.failure)` at `nfpIfpService.ts:536`.
- `IrregularGeometryInfeasibleError` (`services.ts:47-52`): `{ operation: string, message: string }`. Raised **only** by `computeIfpBoundsCached` (`nfpIfpService.ts:241-247`), i.e. the public Effect-wrapped `computeIfpBounds` API, for the `'infeasible'` kind (`ifpBoundsCore.ts:86-88`: `minX > maxX || minY > maxY`, meaning the moving polygon's own extent already exceeds the sheet). **This error is never raised by the internal fast path** used inside candidate generation — see below.
- `IrregularNfpIfpControlAbortError` (`services.ts:70-75`): `{ reason: 'deadline' | 'cancelled', message: string }`. Not constructed anywhere inside this cluster's four files; it only flows *through* `nfpCheckpoint` from a caller-supplied `control`, and is a possible failure channel of `generatePlacementCandidates` (both overload signatures at `services.ts:302-310,317-324`) and of `addBoundaryIntersections` (`nfpIfpService.ts:1039`, which itself only forwards it from `nfpCheckpoint`).

**Key asymmetry — "infeasible" is swallowed, not failed, on the production fast path**: inside `generatePlacementCandidatesUncached` (`nfpIfpService.ts:287-306`):

```
if (ifpResult === undefined) { ifp = undefined }
else if ('kind' in ifpResult) {
  if (ifpResult.kind === 'invalid') return yield* failInvalidGeometry('computeIfpBounds', ifpResult.message)
  ifp = undefined   // 'infeasible' falls through here, NOT a failure
} else { ifp = ifpResult }
if (!sheetlessNfp && ifp === undefined) { emitCandidateProvenance(input, provenance); return [] }
```

So an `'invalid'` IFP (structurally broken moving polygon) fails the whole candidate-generation call with `IrregularGeometryInputError`, but an `'infeasible'` IFP (a geometrically valid polygon that simply cannot fit inside the sheet at all) **silently produces an empty candidate list** (`return []`) — it is treated exactly like "no legal candidates found", not like an error. This is confirmed by the differential test `tests/unit/nfpIfpService.test.ts:1096-1106` (`infeasible.outcome` is `{_tag: 'Right', right: []}`, not a failure). **A Rust port that unifies the internal fast path with the public `computeIfpBounds` API's error semantics would silently change production behavior** (turning a currently-successful-with-empty-result call into an error) — flagged again in §15.

**Propagation to the worker boundary** (outside this cluster, traced for completeness): `src/workers/nesting.worker.ts:403-449`'s `toIrregularWorkerFailure` switch maps `'IrregularGeometryInputError'` → `WorkerResponseFailureError{code: 'irregular_geometry_invalid'}`, and `'IrregularNfpIfpControlAbortError'` → `code: error.reason === 'cancelled' ? 'worker_cancelled' : 'worker_timeout'`. **`'IrregularGeometryInfeasibleError'` has no case in this switch** — consistent with §1's finding that the public `computeIfpBounds` API (the only source of this error) has zero production callers; if it were ever reached in production it would fail a TypeScript exhaustiveness check (the switch's parameter type is a union including it) or fall through unmatched at runtime, which is itself worth flagging to whoever owns that switch (out of this cluster's scope to fix, but the Rust port's error taxonomy must account for the fact that this error is real, tested, and currently unrouted).

Beyond this cluster, dozens of algorithm-layer files (`intrinsicPeriodicFamilyPortfolio.ts:338,1130`, `intrinsicPeriodicSmallFillE3.ts:185`, `intrinsicPlaceDeferCompleteShadow.ts:247,253`, `intrinsicGlobalSqueezePortfolio.ts:241,322`, `intrinsicStrictFamilyPortfolio.ts:301`, `computeIrregularNesting.ts:852`) catch and reclassify `IrregularNfpIfpControlAbortError` by `_tag`/`reason` for their own internal control-flow purposes (e.g. distinguishing a caught abort from a "no result" outcome) — all of that reclassification logic lives outside this cluster and is not this document's concern, but a Rust port must ensure the abort error's `_tag`/`reason` discriminants survive intact across the FFI boundary so those call sites keep working.

## 12. JS-specific semantics hazards for a Rust port

1. **`Number.prototype.toString()` shortest-round-trip formatting** — every cache-key digest function (`numberKey` in `nfpCacheKey.ts:104-106`, `geometryCacheIdentity.ts:139-141`, `geometryCacheKeys.ts:158-160`; `numberIdentity` in `nfpBoundaryCore.ts:86-88`) relies on `String(value)` producing exactly V8's ECMA-262 `Number::toString` output (shortest decimal that round-trips, switching to exponential notation outside `[1e-6, 1e21)`, `-0` special-cased away by the surrounding `Object.is` check). Rust's default `f64` `Display`/`{}` formatting does **not** match this algorithm out of the box (different exponential thresholds, different digit-count minimization strategy). A Rust port needs a JS-compatible float-to-string routine (e.g. a `ryu`/Grisu-based implementation tuned to ECMA-262's exact switch-over thresholds and digit selection) verified by exhaustive differential testing against `String(x)` for edge magnitudes, or these caches will simply produce different (but internally self-consistent) keys — low risk for *correctness* (job-local, non-hashed caches, §8/§9) but real risk for **cache hit-rate parity and any differential test that inspects raw key strings** (e.g. `tests/unit/nfpBoundaryCore.test.ts:35-38` asserts on the literal serialized key).
2. **`orient2d` sign convention** (`geometryPredicates.ts:16-35`) — the entire convexity/winding/legality stack (this cluster, plus `convexPolygonValidation.ts`, `convexHullCore.ts`, `placementValidation.ts`) depends on `robust-predicates@3.0.3`'s documented y-down convention being correctly flipped to y-up. A Rust `orient2d`/`robust` crate substitute must be verified (empirically, not assumed) to use the *opposite* sign convention that this code expects, or the flip in `geometryPredicates.ts:32-33` must be adjusted accordingly — getting this wrong flips every winding/convexity/collinearity decision in the whole geometry stack simultaneously and would likely still "work" internally (self-consistent) while producing wrong output relative to the TypeScript baseline. The *sign of the zero test* (exact collinearity) is a mathematical invariant across correct adaptive-precision implementations, so differential testing against the existing test corpus should catch a wrong flip quickly, but it must be tested before any geometry code is trusted.
3. **`Array.prototype.sort`/`toSorted` stability** — used in `computeConvexHull`'s pre-sort (`convexHullCore.ts:6-9`, ties collapse via dedup immediately after, so stability is moot there), `BoundsIndex`'s construction sort (`nfpIfpService.ts:744`, explicit `sourceIndex` tiebreak makes stability moot there too), `sortedPoints` (`nfpIfpService.ts:492`, provably tie-free, §5), and `canonicalPlacementPointAlternatives`'s `.toSorted` (`nfpIfpService.ts:592`, comparator ends in a full `(gridX, gridY)` tiebreak, so also tie-free for distinct grid coordinates, and the 9 alternatives always have distinct `(gridX,gridY)` pairs since they are `centerX+dx, centerY+dy` for 9 distinct `(dx,dy)`). **Net finding: every sort in this cluster has an explicit or provable total order and does not actually depend on stability** — worth stating positively so a Rust port using `sort_unstable_by` is safe everywhere in this cluster specifically (contrast with other clusters, which this document does not characterize).
4. **`Map`/`Set` insertion order** — used pervasively for O(1) dedup/lookup (`CanonicalPointSet.keys/sourceMasks`, `acceptedGridKeys`, `legalCandidateSourceMasks`, the legal-candidate memo `Map`s, the `GeometryCacheStore` backing `Map`, `nfpIfpTelemetry.ts`'s counters), but §5 shows every place that order could leak into an externally-observable value is explicitly re-sorted first. A Rust `HashMap`/`HashSet` (even with randomized hashing) is a safe substitute *everywhere in this cluster* as long as the same explicit re-sorts are preserved verbatim — this cluster does not need `IndexMap`/`BTreeMap`-style insertion-order preservation to stay correct, only to stay equally fast (an incidental, non-semantic concern).
5. **`WeakMap`-based, GC-lifetime-scoped memoization** (`validatedRings` in `nfpBoundaryCore.ts:31-37`; `candidatesByScope` in `nfpIfpService.ts:611-614`) — both are transparent caches (proven equivalent to "always recompute" by tracing every branch) whose *only* purpose is avoiding repeated `O(n²)`/`O(edges²)`/`O(sheet-search)` work within one JS object's garbage-collected lifetime. Rust has no direct GC-scoped-WeakMap equivalent; the correct port strategy is an explicit, deterministically-scoped cache (e.g. `Arc`-keyed by decode invocation for `candidatesByScope`'s role, or simply recomputing every time for `validatedRings`'s role, since `ConvexPolygonValidation.validateStrictBoundary` is cheap enough per call that a Rust implementer may choose not to memoize it at all without any semantic risk).
6. **JS object literal key order vs `Record`** — `rawBySource` (`nfpIfpService.ts:928-936`) is a `Record<NfpIfpCandidateSource, number>` object literal; its enumeration order matches declaration order for these non-numeric-string keys. This translates trivially to a Rust `struct` with named fields (no ordering concern at all, unlike a `HashMap`).
7. **Effect-generator short-circuit semantics** — every `yield*` in `generatePlacementCandidatesUncached`/`addBoundaryIntersections` immediately aborts the whole generator on failure, discarding all local mutable state built so far with no explicit cleanup (§4). A Rust port using `Result`/`?` (or an equivalent early-return combinator) reproduces this precisely as long as no Rust code accidentally commits partial state to a *shared* structure before the equivalent of a "checkpoint" — which, per §10's trace, never happens in the current code (checkpoints always sandwich whole atomic cache transactions).
8. **IEEE-754 arithmetic order dependence** — `strictConvexInteriorPoint`'s left-to-right centroid summation (`placementValidation.ts:258-283`) and every Minkowski-sum/edge-vector computation must be summed/subtracted in the exact same operand order and the exact same left-to-right grouping as the TypeScript source (binary64 addition is not associative); a Rust port must not "helpfully" reorder or vectorize these sums.

## 13. Parallelism assessment: safe Rayon candidates vs chronology-bound work

### Provisionally safe (pure, input-fully-known, indexable/reducible) candidates *within this cluster*

- **Per-placed-piece NFP resolution** (`nfpIfpService.ts:314-352`, the `for (const placed of input.placed)` loop): each iteration's `resolveNfpBoundaryFromServiceStore` call is a pure function of `(placed, input.moving, input.settings.geometry)` plus one shared cache. If the cache access itself is made a safe concurrent structure (§13.4/13.5 of the migration prompt, out of scope for this Stage-0 document to design), the *pure geometry* part of each iteration (boundary construction, validation, bounds/segments derivation) is embarrassingly parallel by stable placed-piece index. **But** the current code observes a `'placed-nfp'` checkpoint immediately before and after each iteration (§10, checkpoints 3-4) — a parallel version must still evaluate cancellation/deadline in a way that preserves "no lookup occurs relative to a semantic checkpoint differently than today" (migration prompt §13.2's closing sentence), which likely means: gather the checkpoint decision serially at fixed points, and only parallelize the pure computation *between* two serially-evaluated checkpoint boundaries, or check cancellation once *before* dispatching the parallel batch and once *after* collecting it, reconstructing the exact same number of logical checkpoint observations only if that count is not itself parity-gated (it currently is not — checkpoint counts are explicitly non-canonical, §13.7 — but *checkpoint failure timing relative to partial cache mutation* still is).
- **Candidate-point legality assessment across raw points** (`nfpIfpService.ts:495-554`) is tempting to parallelize by point, but is **not a good candidate as currently structured**, because the algorithm is not "evaluate N independent candidates and merge" — it is "walk `sortedPoints` in order, and the *set of already-`acceptedGridKeys`* mutates as you go", so a later point's outcome (whether it's a "new" grid key) genuinely depends on which earlier points (in the fixed `(y,x)` traversal order) already claimed that grid cell. A parallel-safe reformulation would need to (a) compute each raw point's legality-and-grid-key result independently (this inner part *is* pure and parallelizable, by stable `sortedPoints` index), then (b) serially reduce over the exact `sortedPoints` order to decide first-acceptance-per-grid-key — i.e. exactly the migration prompt's §14.3 "deterministic parallel pattern" (construct ordered input vector, parallel-evaluate pure per-item work, reconstruct by ordinal, then serially apply tie-breaking/admission).
- **Pairwise NFP-NFP boundary intersection search** (`nfpIfpService.ts:427-489`) is a pure function of the already-built `candidateNfpBoundaries`/`candidateNfpIndex` for each `(first, second)` pair with `second.index > first.index`; each pair's `addBoundaryIntersections` call only *adds* points into a shared `CanonicalPointSet` via commutative, associative operations (`addPoint`'s Set-membership-then-push and Map bit-OR, §5/§9) — this is a strong candidate for a parallel map that collects per-pair point lists and merges them with a stable reduction (again per §14.3), since `addPoint`'s eventual output is provably order-independent (§5).
- **The 9-alternative grid-snap search per raw point** (`canonicalPlacementPointAlternatives`, `nfpIfpService.ts:569-593`) is pure and tiny; no meaningful parallelism opportunity by itself, but is naturally swept up in whichever parallel-per-point restructuring is chosen for the outer loop.

### High-risk / chronology-bound (must stay logically serial)

- **The legal-candidate memo** (`makeGeneratePlacementCandidates`, `nfpIfpService.ts:606-695`) is a per-decode `WeakMap`/`Map` structure with get-or-create semantics; concurrent decode invocations sharing one `NfpIfpServiceLive` instance (they do not today — §4 shows the cache is job-local — but a future multithreaded job might run several decode/search branches concurrently against one shared service instance) would need this memo to become a genuinely concurrent single-flight structure per the migration prompt §13.3/13.5, which this document does not design (Stage 3/4 concern, not Stage 0).
- **`acceptedGridKeys`/`legalCandidateSourceMasks`/`candidates` accumulation** (§4) is inherently sequential *by the traversal order itself* — this is the "chronology bound" that the migration prompt's §14.2 warns about ("survivor selection as candidates finish" is exactly this shape: first-acceptance wins). Any parallel restructuring must still serially reduce in `sortedPoints` order to decide which grid key was accepted "first" (§13's safe-candidate note above already covers the correct pattern).
- **Cache A/B publish-after-success ordering** (§9) must not change under parallel execution: if two threads race to resolve the same relative-NFP key, the migration prompt's single-flight-vs-duplicate-computation policy (§13.5) governs which one "wins" the publish, but **the winner must have no semantic effect** — this cluster's current code already guarantees that property today (whichever caller successfully computes first publishes an interchangeable canonical value, since `computeRelativeNfpBoundary` is a pure function of its inputs), so this is a good candidate for either single-flight *or* bounded duplicate computation, to be decided with real measurements in a later stage, not here.
- **Checkpoint observation itself** must remain a serial decision point relative to any cache mutation it "brackets" (§10) — this is the concrete instance of migration prompt §13.2's "if parallel execution changes when a lookup occurs relative to a semantic cancellation or deadline checkpoint, the parallel design is not yet valid" warning, specific to this cluster.
