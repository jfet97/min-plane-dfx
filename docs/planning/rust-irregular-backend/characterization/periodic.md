## 1. Purpose and role in Compact / Compact Short Side execution

`CELLS` enumerates a bounded, exact catalog of **periodic base cells** for every "repeated collision family" present in a nesting job: shapes that recur (same interchangeability key + same collision polygon under cyclic-key comparison, `FAMILYGROUP:124-130`). For each eligible family it derives:

- **P1 cells**: single-member lattices — one placed representative plus a two-vector lattice basis `(v1, v2)` such that translating the member by integer combinations of `v1`/`v2` tiles the plane without collision (`CELLS:426-444`, `deriveCells` role `'P1'`, `CELLS:1028-1148`).
- **P2 cells**: two-member lattices — a fixed representative plus a second, pairwise-NFP-placed member, again with a derived basis (`CELLS:446-502`, role `'P2'`).

`PORTFOLIO` turns each retained cell into one or more **finite crops** (`enumerateIntrinsicPeriodicCellCrops`, `CELLS:707-809`) — bounded rows×columns tilings of the base cell, Pareto-selected (`selectIntrinsicPeriodicSeedFront`, `CELLS:917-922`) — and feeds each crop as a **frozen seed** into the unchanged strict decoder (`constructIntrinsicStrictState` / `finalizeIntrinsicStrictState`, imported from `DECODER`) in `candidateMode: 'pure-growth'` (`PORTFOLIO:316-328`). Each run's completed metrics compete in the shared archive alongside the three "direct" roles (`canonical-grid`, `legacy-absolute-envelope`, `open-pocket-first`).

## 3. Data in/out: exact types/shapes, optional-field presence/omission semantics

### `IntrinsicPeriodicCell` (`CELLS:116-137`)

All fields `readonly`. Notable shape/omission facts:

- `role: 'P1' | 'P2'`.
- `v1`, `v2: IntrinsicPeriodicVector` (`{x:number, y:number}` in floating millimeters, reconstructed from exact grid `bigint` via `fromGridPoint`, `CELLS:2347-2349`).
- `determinantGrid2`, `memberDoubledAreaGrid2: string` — **exact** grid-unit `bigint` values serialized via `.toString()` (base-10, no separators). These are the load-bearing exact quantities; `density: number` (line 1130) is a **derived float diagnostic only** — grep confirms `.density` is never read anywhere else in either file, i.e. it does not participate in any comparator, dedup key, or gate. Do not let it silently become load-bearing in the Rust port (e.g. by accidentally using it in a comparator) — the exact bigint cross-multiplication in `compareCells` (`CELLS:2314-2317`) is what actually orders cells by density.
- `basisProvenance?: IntrinsicPeriodicBasisProvenance` — **optional and frequently absent.** `deriveCells` always constructs it when a cell is emitted (`makeBasisProvenance`, `CELLS:1181-1212`), so in practice every `IntrinsicPeriodicCell` produced by `deriveCells` has one; but downstream code (`periodicCellFront`, `CELLS:660`) explicitly handles the `undefined` case by mapping to the literal string `'legacy'` for the source-kind grouping key, so the type contract treats absence as meaningful, not accidental.
  - Within `IntrinsicPeriodicBasisProvenance` (`CELLS:66-79`), `axis?: 'x' | 'y'` is present **only** for `sourceKind === 'axis-union'` (constructed with the spread-omission idiom `...(candidate.axis === undefined ? {} : { axis: candidate.axis })`, `CELLS:1194`) and `contactRelations?` is present **only** for `sourceKind === 'edge-contact-pair'` (`CELLS:1208-1210`). A later helper, `completeBasisProvenance` (`PORTFOLIO:963-973`), backfills a missing `axis` field for `axis-union` provenance by inspecting the `sourceKey` prefix (`'x:'`/`'y:'`) — this exists because some code paths (replay reconstruction) do not always have `axis` populated and it must be reconstructed byte-identically from the string prefix, not re-derived from geometry.
- `canonicalKey: string` — always present, the dedup/ranking identity (§6, §8).

### `IntrinsicPeriodicCatalog` (`CELLS:139-148`) and `IntrinsicPeriodicFamilyCatalog` (`CELLS:180-199`)

- Top-level `cells: ReadonlyArray<IntrinsicPeriodicCell>` is a **cross-family, canonicalKey-deduplicated, re-ranked** view (`CELLS:312,325,335`) that, per repo-wide grep, **no production code ever reads** (only `catalog.families[...]` is read downstream, `SHARED:528-551`, `PORTFOLIO:698`). It is effectively diagnostic/output-surface only, but its construction (last-write-wins `Map` keyed by `canonicalKey` across *all processed families in family-processing order*, `CELLS:312,325`) must still be reproduced exactly because it is part of the exported result type and may be consumed by tests, scripts, or a future caller.
- `IntrinsicPeriodicFamilyCatalog.sourceAuditCells?: ReadonlyArray<IntrinsicPeriodicCell>` — present **only when `captureSourceSurvivalAudit` is true** (`CELLS:507-509,529`); this is the *pre-front-truncation* rank of `[...p1, ...p2]` for that family, retained so the survival audit can compare "cells that existed" vs "cells that survived the front" (§5). When absent, all downstream consumers fall back to `family.cells` (`PORTFOLIO:748,1084,1228`).

### `IntrinsicPeriodicSeed` (`CELLS:223-241`)

- `exactEnvelope?: { maximumSideGrid: number; areaGrid2: string; spanGrid: number }` — optional; present whenever `measureCanonicalLayoutEnvelope` succeeds during crop enumeration (`CELLS:796-800`), which is the normal case. `exactEnvelopeForSeed` (`CELLS:849-861`) falls back to **re-deriving** the envelope from `seed.placements` when `exactEnvelope` is `undefined`, and if that *also* fails, every Pareto/rank comparator that depends on it falls back further to the plain-float `maximumSideMm`/`envelopeAreaMm2`/`envelopeSpanMm` fields (§6). This is a real three-tier fallback chain (exact-grid → re-derived-exact-grid → float) that a Rust port must replicate exactly, including which comparator terms it feeds.
- `placements: ReadonlyArray<IrregularPlacedPiece>` — always the **bottom-left-normalized** (`normalizePlacedBottomLeft`, `CELLS:978-997`) full crop, i.e. bounds-translated so `minX === 0, minY === 0` in the crop's own local frame (not the family's or job's global frame).
- `remainingFamilyMembers: ReadonlyArray<IrregularPreparedPiece>` — `familyMembers.slice(q * memberCount)` (`CELLS:789`), i.e. exactly the **tail slice** of the family's member array beyond however many complete `q` copies of the base cell were placed. This is a plain array-index slice, not a set-difference — the order and identity of "remaining" members is whatever the family's own member order left over, not filtered by which pieces were actually used (all of the first `q*memberCount` members are always used by construction).

### `IntrinsicPeriodicContinuation` (`PORTFOLIO:48-55`)

- `sourceId: string` — synthesized as `` `${family.familyKey}:${cell.role}:${cell.canonicalKey}:${cropIndex}` `` for ordinary continuations (`PORTFOLIO:793`) or `` `raw-witness:${seed.role}:${source.sourceKey}:${seed.canonicalKey}` `` for admitted witness continuations (`PORTFOLIO:844`). This string is later used as a **tie-break and dedup-preference key** (§6) — it embeds `family.familyKey`, which itself embeds `JSON.stringify(interchangeabilityKey)`, which can contain arbitrary user-controlled Unicode (piece interchangeability key or, if unset, `piece.source.id`). This is a genuine cross-language hazard (§12).
- `basisSourceKey: string | undefined` — `cell.basisProvenance?.sourceKey`, `undefined` whenever the cell somehow lacks provenance.

### `IntrinsicPeriodicFamilyPortfolioResult` (`PORTFOLIO:132-151`)

- `phaseTimings?: IntrinsicPeriodicPortfolioPhaseTimings` — present **only when `capturePhaseTimings === true`** (`PORTFOLIO:500`, spread-omission idiom). Production callers (`SHARED:192-204`) never set `capturePhaseTimings`, so in production this field is always absent and `runtimeMs` falls back to `performance.now() - startedAt` (`PORTFOLIO:501`) rather than the phase-timing total. **Do not treat phase-timing fields as parity-relevant for production output** — they are wall-clock telemetry (`performance.now()` deltas), explicitly non-deterministic across machines/runs, and out of scope for byte-exact Rust parity per the migration prompt's cache-telemetry rules (§13.7 of the prompt). They are, however, exercised by `tests/unit/intrinsicPeriodicFamilyPortfolio.test.ts` (`'fails phase coverage when unclassified residual exceeds one percent'`), so the *structure and coverage-completeness arithmetic* (not the timing values) must still be ported.
- `sourceAuditReplayRejectionReason?: string` — present only when validation actually rejected a supplied envelope (`PORTFOLIO:479-481`); absent both when there was no envelope and when validation succeeded.
- `sourceAuditReplayEnvelope?: IntrinsicPeriodicSourceAuditReplayEnvelope` — present only when the caller explicitly requests `captureSourceAuditReplayEnvelope: true` (`PORTFOLIO:482-496`); never set in production (§1).

### Domain classes with constructor-conditional optional fields

`IrregularPlacement.pieceId` and `IrregularPreparedPiece.pieceId`/`interchangeabilityKey`/`priorityOrderKey` are declared with `declare readonly x?: T | undefined` and assigned **only when `Object.prototype.hasOwnProperty.call(fields, 'x')`** is true in the constructor (`src/shared/irregular/domain.ts:694-712`, similar pattern at 644-661). This means these are **true own-property omissions**, not `undefined`-valued properties — `Object.keys`/`Object.entries`/`JSON.stringify` will not see the key at all when omitted. The cluster relies on this via the `piece.pieceId ?? piece.source.id` idiom used pervasively (`CELLS:2101,1203,1494,2118`; `PORTFOLIO:1309,1459,1479`) and via the custom `canonicalJson` encoder's explicit `fieldValue !== undefined` filter (`PORTFOLIO:1285-1293`, §8) — the filter is defensive/redundant given the omission pattern but both mechanisms must independently produce the same result in Rust (an `Option<T>` skipped by a custom serializer, not a `null`/`None` field written out).

## 4. Algorithm state and every mutation point

This cluster is expressed almost entirely as pure functions over immutable inputs plus **local, function-scoped mutable accumulators** built during a single pass — there is no persistent cross-call algorithm state (no module-level `let`/cache). Enumerated mutation points:

### `CELLS`

- `enumerateIntrinsicPeriodicCells` (`CELLS:282-338`): `families: IntrinsicPeriodicFamilyCatalog[]` (push per processed family, `CELLS:324`) and `globalCells: Map<string, IntrinsicPeriodicCell>` (last-write-wins `.set`, `CELLS:325`) — both local to the call, discarded per invocation.
- `enumerateIntrinsicPeriodicFamily` (`CELLS:379-535`): `transformedByCanonicalKey: Map<string, {...}>` (first-write-wins via `if (!has(key)) set(...)`, `CELLS:400`); `rejected: Map<string, number>` and `rejectedSamples: IntrinsicPeriodicCellRejection[]` (accumulated across both P1 and P2 phases via the shared `addDerived` closure, `CELLS:413-424`); `p1`/`p2: IntrinsicPeriodicCell[]` (push-only); `enumeratedPairCount`/`pairCoverageComplete`/`runtimeCoverageComplete` (local flags flipped once and never reset within the call, only ever `true → false`).
- `deriveCells` (`CELLS:1041-1147`): `forbidden: ForbiddenBoundary[]` (push per fixed×moving member pair, in nested-loop order — this order feeds Clipper2 union input order, §5); `result: IntrinsicPeriodicCell[]`, `rejected: Map`, `rejectedSamples: IntrinsicPeriodicCellRejection[]` (bounded to 8 samples via early return at `CELLS:1090`, **not** a global cap — each call to `deriveCells` gets its own fresh 8-sample budget, and the caller then further caps the family-level `rejectedSamples` to 32 via `appendRejectedSamples`, `CELLS:1159-1179`, with **de-duplication by `(role, stage, v1.x, v1.y, v2.x, v2.y)`**, not by full identity).
- `deriveEdgeContactBasisCandidates` (`CELLS:1246-1407`): `relations: Map<string, EdgeContactRelation>` keyed by `"${vector.x},${vector.y}"`, replaced in-place only when a *new* candidate has strictly greater `lengthMm`, or equal `lengthMm` with a lexicographically (via `edgeContactProvenanceKey(...).localeCompare(...)`) smaller provenance key (`CELLS:1298-1307`) — i.e. this is a **max-by-length-then-min-by-key reduction**, not first/last-write-wins.
- `diagnoseLattice` (`CELLS:1962-2022`): `placed: IrregularPlacedPiece[]` built incrementally across the 3×3×members nested loop (order matters — later placements are validated against all earlier ones in the same 3×3 sweep, `CELLS:1979-1986`); `center: Set<number>` (indices into `placed` corresponding to the `(n,m)=(0,0)` tile); `contactedCenter: Set<number>` and `sharedBoundaryLengthMm` accumulator (`CELLS:1990-2015`, float sum — order-dependent, see §7).
- `unionForbiddenBoundaries` (`CELLS:1785-1810`): builds a fresh Clipper2 `Path64[]` and `PolyTree64` per call; no persistent geometry cache.

### `PORTFOLIO`

- `runIntrinsicPeriodicFamilyPortfolio` (`PORTFOLIO:236-503`): `runs: IntrinsicPeriodicContinuationResult[]` (push per continuation, in **execution order** — see §5); several `constructionMs`/`constructionCandidateGenerationMs`/... float accumulators gated behind `capturePhaseTimings` (telemetry only, §3).
- `selectIntrinsicPeriodicContinuations` (`PORTFOLIO:632-960`) is the most stateful function in the cluster:
  - `familyMembers: Map<string, ...>` — built once from `groupIntrinsicCollisionFamilies(pieces)`.
  - `perFamily: Map<string, IntrinsicPeriodicContinuation[]>` — accumulated per family in `catalog.families` iteration order, then later witness continuations are `.push`ed onto whichever family bucket they belong to (`PORTFOLIO:860-864`) — **mutates a `Map` value array in place after the main per-family loop has already finished**, meaning witness continuations are appended *after* all ordinary continuations for that family, never interleaved.
  - `seenOrdinaryFutures: Set<string>` — first-write-wins global continuation dedup by `periodicContinuationFutureKey` (`PORTFOLIO:798-803`); **only mutated in the ordinary-cell loop**, not when admitting witness continuations (those use a *separate* dedup mechanism — `preferredByFuture`, below).
  - `sourceCropSurvival: Map<string, {...}>` — per-`(role,sourceKey)` mutable counters (`retainedCellCount`, `directValidCropCountBeforeFront`, `directValidCropCount`, `cropFrontCount`, `uniqueSeedCount`, `selectedContinuationCount`), incremented at five distinct points across the function (`PORTFOLIO:684-696` init/lookup, `755` `directValidCropCountBeforeFront`, `780` `retainedCellCount`, `789-790` `directValidCropCount`/`cropFrontCount`, `804` `uniqueSeedCount`, `899` `selectedContinuationCount`). This is a genuine multi-phase accumulator whose final values depend on **all five mutation sites executing in their documented order** — a Rust port must not "helpfully" fold these into a single derived formula, because `directValidCropCountBeforeFront` and `directValidCropCount` are computed at *different phases* (`'source-audit'` vs `'retained'`) and can diverge when `directValidCropsByCanonicalCell` caching (see next bullet) causes one phase to reuse the other phase's already-computed crop list.
  - `directValidCropsByCanonicalCell: Map<string, {crops, attemptCount}>` — a **memoization cache keyed by `cell.canonicalKey`**, shared between the `'source-audit'` and `'retained'` phases within one family (`enumerateCrops` closure, `PORTFOLIO:708-746`). When the source-audit phase already computed crops for a canonical cell, the retained phase's `directValidCropsByCell.get(periodicSourceCellKey(cell))` lookup (`PORTFOLIO:781`) can still miss (different key: `periodicSourceCellKey` embeds `role:sourceKey:canonicalKey`, not just `canonicalKey`), causing `enumerateCrops` to be invoked again — which **then** hits the `directValidCropsByCanonicalCell` cache and returns the same crop array without recomputation, but *does* re-increment `sourceAuditCanonicalCellReplayCount`/`sourceAuditLogicalCropAttemptCount` diagnostics (`PORTFOLIO:718-722`) without re-incrementing `sourceAuditPhysicalCropAttemptCount`/`sourceAuditUniqueCanonicalCellCount`. This double-keying (by `canonicalKey` alone at one cache, by `role:sourceKey:canonicalKey` at another) is subtle and must be reproduced exactly, including which counters increment on a cache hit vs a cache miss.
  - `sourceAuditWitnesses: Map<string, {...}>` keyed by `periodicContinuationFutureKey(pieces, seed)` — first-write-wins **by `provenance.sourceKey` minimality**, not simple first/last-write: `if (current === undefined || provenance.sourceKey < current.sourceKey)` (`PORTFOLIO:761`, plain JS `<` string comparison — **not** `localeCompare** here, i.e. this one comparison uses raw UTF-16 code-unit ordering, unlike almost every other string comparison in this cluster; see §12).
  - `omissions: IntrinsicPeriodicContinuationOmission[]` — push-only, accumulates reasons `'insufficient-seed'` (`< 4` placements, `PORTFOLIO:794-797,845-847`), `'duplicate-canonical-seed'` (`PORTFOLIO:800-802,876`), `'continuation-cap'` (`PORTFOLIO:902`).
  - `preferredByFuture: Map<string, IntrinsicPeriodicContinuation>` — built by iterating **all** per-family continuation arrays flattened (`[...perFamily.values()].flat()`, `PORTFOLIO:866`), replacing the stored value only when `preferPeriodicContinuation` (§6) prefers the new one; the loser is always recorded as a `'duplicate-canonical-seed'` omission, even when the loser is the one already stored (`PORTFOLIO:873-876` — `duplicate` can be either `current` or `continuation` depending on preference, and the *stored* map entry is always the winner regardless of which one physically triggered the `.set` call).

No shared/global mutable cache, no cross-invocation memoization anywhere in either file — every mutable structure above is allocated fresh per top-level call and discarded at return. This is a favorable property for a Rust port (no hidden global state to reason about) but the **within-call reduction/memoization order** above is intricate and load-bearing for the diagnostic/audit fields that gate production validity (§1).

## 5. Ordering sources

Every sort, insertion-order-observable `Map`/`Set`, and iteration order that reaches output, keys, traces, or selection. "Stable" below means JS `Array.prototype.toSorted`/`.sort` are spec-guaranteed stable (ES2019+); this cluster relies on that guarantee in several places noted explicitly.

1. **Family selection order** (`CELLS:288-297`): `groupIntrinsicCollisionFamilies(pieces)` returns families in **first-appearance order** within the job's `pieces` array (Map insertion order, `FAMILYGROUP:98-107`), filtered to `members.length >= 2`, then `.toSorted(...)` by `members.length` desc, then `members.length * collisionAreaMm2` desc, then `key.localeCompare` asc (stable tie-break only on true ties of both numeric keys). `selectedFamilies = eligibleFamilies.slice(0, maximumFamilyCount)` — **families past the cap are silently dropped**, never processed, never appear in `families[]`.
2. **Per-representative transform order within a family** (`CELLS:389`): `[...representative.transforms].sort(transformOrder)` where `transformOrder = Order.combineAll([index asc, rotationDeg asc, mirrored asc])` (`CELLS:48-52`, using `effect`'s `Order` combinators — pure numeric/boolean comparison, no locale involvement). Note: `.sort()` here, not `.toSorted()` — but it is applied to a freshly spread array (`[...representative.transforms]`), so it does not mutate the caller's array; behaviorally identical to `.toSorted()` for porting purposes.
3. **Canonical-transform dedup** (`CELLS:399-400`): `transformedByCanonicalKey: Map<string, {...}>`, **first-write-wins** (`if (!has) set`) keyed by `canonicalTransformedPolygonKey` (min-corner-normalized canonical cycle string, `CELLS:2145-2152`). Iteration order of `[...transformedByCanonicalKey.values()]` (`CELLS:403`) is therefore insertion order = the order transforms were processed in step 2, filtered to first-occurrence-per-shape.
4. **Transform representative selection** (`selectPeriodicTransformRepresentatives`, `CELLS:603-622`): re-sorts by `transformOrder` again (redundant with step 2's order but explicit), builds a `reserved: Map<string, candidate>` keyed by `periodicTransformReservationKey` (mirror/rotation-quadrant family, `CELLS:624-628`) — **first-write-wins**, guaranteeing at least one representative per reservation bucket survives the cap — then appends remaining `ordered` candidates (skipping ones already in `result` via `Array.prototype.includes`, an **O(n) identity/structural-equality scan per candidate**, not a Set) until `maximumTransforms` is reached, then hard-slices to `maximumTransforms`. The "reserve one per bucket, then fill in rank order" pattern reappears at the continuation level (step 11) — **this is a recurring, intentional selection idiom in this cluster, not a coincidence; preserve it structurally in Rust rather than re-deriving an equivalent-looking flat top-K.**
5. **P1 cell derivation order** (`CELLS:426-444`): iterates `transformed` (step 4's final order) in array order; each representative's `deriveCells` call appends its emitted cells to `p1` in that order.
6. **P2 pair enumeration order** (`CELLS:448-502`): nested `firstIndex < secondIndex` loop over `transformed` (i.e. all unordered pairs, `firstIndex` strictly less than `secondIndex`, so no self-pairs and each unordered pair visited once) in index order; for each pair, `boundaryCandidatePoints(pairNfp.boundary.points, second)` (`CELLS:2052-2078`) is itself an **ordering-sensitive** function: it dedups candidate points into a `Map` keyed by `"${x},${y}"` (first-write-wins) sourced from (a) the NFP boundary's own point order, then (b) x-axis line intersections, then (c) y-axis line intersections — and finally **re-sorts** the deduped values via `compareGridPoints` (x asc, then y asc, exact `bigint` compare, `CELLS:2351-2353,2077`) before returning. So candidate-point iteration order for P2 legality checks is **not** NFP-boundary order — it is exact-grid lexicographic order after Map-dedup.
7. **Basis-candidate construction order within `deriveCells`** (`CELLS:1076-1081`): a single flat array built by **concatenation** in this fixed order: `deriveAxisBasisCandidates(forbidden, swapAxes=false)`, then `deriveAxisBasisCandidates(forbidden, swapAxes=true)`, then `deriveNfpBoundaryVertexBasisCandidates(forbidden)`, then `contact.candidates` (edge-contact). This concatenation order determines which candidate is "first" for any downstream first-write-wins structure that iterates `bases` in order (there is none inside `deriveCells` itself — each candidate independently produces a cell pushed to `result` — but the order does determine `rejectedSamples` ordering, capped at 8 per call, §4).
   - `deriveAxisBasisCandidates` (`CELLS:1558-1631`) internally: Clipper2-unions the (possibly axis-swapped) `forbidden` boundaries (`unionForbiddenBoundaries`, order of `boundaries` array = the fixed nested-member-pair order from `deriveCells`, `CELLS:1043-1044,1072`); finds the minimal positive x-axis crossing (`boundaryLineIntersections(...).filter(x>0).toSorted(x asc)[0]`, `CELLS:1568-1571`, **ties broken by pre-sort array order**, itself a `Map` values() iteration over `boundaryLineIntersections`'s internal dedup Map — see next line); for each of up to 3 "canonical grid alternatives" of that x value (`canonicalGridAlternatives`: rounded/floor/ceil, deduped via `Set`, `.toSorted(compareBigInt)`, `CELLS:1887-1892,1574`), searches for the minimal-`(y asc, x asc)` second point satisfying axis-parallelogram constraints, again via `.toSorted(...)[0]` (`CELLS:1597-1601`), and finally emits a `result: Map<string, candidate>` keyed by the exact-grid basis pair string, iterated in insertion order (`[...result.values()]`, `CELLS:1630`) — insertion order here is `axisX` outer loop order (itself sorted) × `secondX` × `secondY` nested loop order (both sorted via `canonicalGridAlternatives`).
   - `boundaryLineIntersections` (`CELLS:1726-1767`) dedups into `Map<string, RationalPoint>` keyed by `rationalPointKey` (exact rational `"num/den,num/den"` string) — **iterates `boundaries` array in order, and within each boundary, edges in polygon-index order** (`CELLS:1732-1734`); this is the one place where Clipper2's `PolyTree64` child-traversal order (via `collectForbiddenTree`, `CELLS:1812-1829`, a depth-first `parent.child(index)` walk) becomes observable in tie-break behavior for candidate basis selection — **a Rust Clipper2 binding must reproduce not just the same polygon set but the same child/ring traversal order**, or basis-candidate ties (and hence which exact basis vector is chosen when multiple are geometrically valid) can diverge.
   - `deriveNfpBoundaryVertexBasisCandidates` (`CELLS:1634-1677`): dedups all forbidden-boundary points with `y>0 || (y===0 && x>0)` into a `Map` (first-write-wins by `"${x},${y}"`), sorts by squared length asc then `compareGridPoints` (`CELLS:1645-1649`), then double-loops `firstIndex < secondIndex` over the sorted vector list, emitting into a `Map<string, candidate>` (keyed by the basis-pair string) capped at `MAXIMUM_NFP_BOUNDARY_VERTEX_BASIS_CANDIDATES = 64` via an **early return mid-loop** (`CELLS:1673`, not a post-hoc slice — the exact 64th-found-in-this-nested-loop-order candidate is the cutoff, order-sensitive).
   - `deriveEdgeContactBasisCandidates` (`CELLS:1246-1407`): builds `relations: Map<string,EdgeContactRelation>` (max-by-length reduction, §4) over a 4-level nested loop (`fixedMemberIndex × movingMemberIndex × fixedEdge × movingEdge`, plus 2 candidate points per edge pair), then `retainedRelations = [...relations.values()].toSorted(compareEdgeContactRelations).slice(0, 64)` (§6 for the comparator), then all-pairs `firstIndex < secondIndex` over `retainedRelations` (bounded to `64 choose 2 = 2016` pairs) building `candidates`, sorted via a 4-key comparator (§6) and **sliced to the first 256** (`MAXIMUM_EDGE_CONTACT_PAIR_VALIDATION_ATTEMPTS_PER_DERIVATION`) before attempting lattice validation in that exact order, admitting up to 64 (`MAXIMUM_EDGE_CONTACT_BASIS_CANDIDATES_PER_DERIVATION`) via an early `break` (`CELLS:1390`) — again order-sensitive truncation, not post-hoc top-K.
8. **Per-family cell ranking and front selection** (`CELLS:504-511,653-680`): `p1`/`p2` (accumulated in step 5/6 order) are each passed through `periodicCellFront(cells, maximumCellsPerFamilyRole)`: dedup into `unique: Map<canonicalKey, cell>` (**last-write-wins**, `CELLS:657`), grouped by `basisProvenance?.sourceKind ?? 'legacy'` into a `Map<string, cell[]>` (**insertion order = `unique.values()` iteration order = last-write-wins-map insertion order**, `CELLS:658-664`), then **within each source-kind group**, `rankIntrinsicPeriodicCells` (density-first comparator, §6) selects the top `maximumCellsPerFamilyRole`, and finally all retained `(sourceKind, cell)` pairs across groups are `.toSorted(sourceKind.localeCompare, then compareCells)` (`CELLS:673-677`) — i.e. **the final per-role front is grouped and independently capped per basis-source-kind before being globally re-sorted**, so a family with many `'edge-contact-pair'` cells cannot starve out `'axis-union'` cells from the front (each kind gets its own `maximumCellsPerFamilyRole` allowance).
9. **Family-level `cells` assembly** (`CELLS:506,530`): `[...p1Front.cells, ...p2Front.cells]` (P1 before P2, unconditionally) then `rankIntrinsicPeriodicCells(cells)` (re-sorted globally by density-first comparator — the P1-before-P2 concatenation order only matters as a stable tie-break input, since `rankIntrinsicPeriodicCells` is a stable sort and ties are broken lexicographically by `canonicalKey` anyway at the comparator's last term, so P1-first-in-array is only observable when **every** comparator term including `canonicalKey` string-ties, which given `canonicalKey` embeds the role prefix `${role}:...` (`CELLS:2200`) cannot actually tie between a P1 and a P2 cell — so this concatenation order is provably inert for final ranking, but still observable for anyone iterating pre-sort or for the source-survival audit's raw pre-front counts).
10. **`rejected` reason maps** (`CELLS:531,689,1144`; `PORTFOLIO` has none of its own): `Object.fromEntries([...rejected.entries()].toSorted())` — **bare `.toSorted()` with no comparator**. Per the JS spec, elements (here `[string, number]` tuples) are stringified (`Array.prototype.toString` → `"key,count"`) and compared by **UTF-16 code-unit order**, not locale. This is a different ordering algorithm from the `localeCompare`-based sorts used everywhere else for user-facing/dedup keys (§6, §12) and must be replicated as plain byte/codepoint ordering in Rust (`str::cmp`), not through any locale-aware collation.
11. **Continuation selection** (`selectIntrinsicPeriodicContinuations`, `PORTFOLIO:632-960`) — the most order-sensitive function in the cluster:
    - Families iterated in `catalog.families` array order (= step 1's order) for the main audit/selection loop (`PORTFOLIO:698`).
    - Within a family, source-audit phase iterates `family.sourceAuditCells ?? family.cells` in that array's order (`PORTFOLIO:748`); the ordinary-selection phase separately iterates `family.cells` in its own order (`PORTFOLIO:775`) — **these can be different arrays with different orders** when `sourceAuditCells` is present (it is the pre-front-truncation rank, §3), even though both ultimately derive from the same underlying cell set.
    - `rawAuditFront = nonDominatedIntrinsicPeriodicSeeds([...sourceAuditWitnesses.values()].map(seed))` — Map values() iteration order here is **witness-insertion order**, which for the non-replay path is the order cells were visited in the source-audit loop (family order × cell order × crop order) with later same-`futureKey` entries able to overwrite earlier ones only when `provenance.sourceKey <` the stored one (§4, plain `<`, not localeCompare).
    - `witnessContinuations`: `rankIntrinsicPeriodicSeeds(rawAuditFront).slice(0, 16)` (**hard cap of 16**, `PORTFOLIO:840`) — order here is the seed-rank comparator (§6), not insertion order.
    - `preferredByFuture` built by iterating `[...perFamily.values()].flat()` — `perFamily`'s `Map` iteration order is family-processing order (families visited during the main loop, **plus** any families first touched only by witness continuations being pushed at `PORTFOLIO:862-863`, which would insert a *new* key at that later point if a witness belongs to a family with zero ordinary continuations — this is possible and would place that family's `Map` entry **after** all families that had at least one ordinary continuation, altering `perFamily`'s iteration order relative to `catalog.families` order for that edge case).
    - `rankedPerFamily = [...perFamily].toSorted(([firstKey],[secondKey]) => firstKey.localeCompare(secondKey))` — **re-sorts families by family-key text**, discarding the `catalog.families`/`perFamily`-insertion order used everywhere else in this function. This is a deliberate, explicit re-ordering — do not "simplify" by reusing the earlier family order.
    - `reserved = rankedPerFamily.flatMap(cs => cs.slice(0,1))` — **one reservation slot per family**, in family-key-sorted order.
    - `fill = rankContinuations(rankedPerFamily.flatMap(cs => cs.slice(1)))` — every family's remaining continuations pooled and **globally re-ranked** by seed rank then `sourceId.localeCompare` (§6).
    - `all = [...reserved, ...fill]`; `selected = all.slice(0, maximumContinuationCount)` (production: 8). Continuations beyond the cap become `'continuation-cap'` omissions in `all`'s order (`PORTFOLIO:901-903`).
12. **Execution order** (`continuationsForExecution`, `PORTFOLIO:594-601`, called at `PORTFOLIO:288-291`): when `maximumCandidateEvaluationCount !== undefined` (**always true in production**, since `SHARED:197-198` always sets it), the `selected` continuation order from step 11 is **discarded** and replaced by `orderPeriodicContinuationsForExecution` (`PORTFOLIO:582-591`): `.toSorted(compareIntrinsicPeriodicSeedEnvelopeAreaFirst, then placements.length desc, then sourceId.localeCompare)`. **This reordered list is what the result's `continuations` field, `runs` field, and hence the `archive`-construction input order are built from** (`PORTFOLIO:288-291,301,394-396`) — i.e. in production, the exposed continuation/run order is cost-based execution order, not selection-priority order. This has a load-bearing consequence: `winner = runs.find(run => run.result?.metrics?.canonicalGeometryHash === winningHash)` (`PORTFOLIO:398-402`) uses **first-match-in-array-order** semantics; if two different continuations converge to byte-identical `canonicalGeometryHash` (a legitimate possibility — different seeds/growth paths can decode to the same final geometry), **which one is reported as `winner` depends on execution order**, i.e. on the cost-based reordering in this step. See §13/§14 — this is exactly the "checkpoint publication by completion order" / "archive admission as tasks finish" hazard class the migration prompt calls out as high-risk to parallelize.
13. **Crop enumeration order** (`enumerateIntrinsicPeriodicCellCrops`, `CELLS:707-809`): `for (rows = 1..q) for (traversal of ['row','column']) for (corner of [0,1,2,3])` — fixed, deterministic triple loop, **not** sorted after the fact. Within one `(rows, traversal, corner)` combination, `cropCoordinates` (`CELLS:811-831`) computes a fixed row-major or column-major coordinate list (stable-sorted by `(row,column)` or `(column,row)`, `CELLS:822-826`) then applies a corner reflection. The **first successful crop for a given `canonicalKey`** (via `identities: Set<string>`, first-write-wins skip, `CELLS:780-784`) is the one retained in `candidates`; later `(rows, traversal, corner)` combinations that would regenerate an identical canonical placement are **silently dropped, not deduplicated-by-preference** — whichever triple loop iteration reaches that canonical identity first (in `rows` outer, `traversal ∈ {'row','column'}`, `corner ∈ {0,1,2,3}` order) wins, and this determines which `crop: {rows, columns, traversal, corner}` provenance ends up attached to that seed. **This exact triple-loop order is load-bearing for the `crop` provenance field of the surviving seed, even when the resulting `placements`/`canonicalKey` are identical across the dropped duplicates.**
14. **Pareto front / seed ranking** (`nonDominatedIntrinsicPeriodicSeeds`, `CELLS:925-931`; `rankIntrinsicPeriodicSeeds`, `CELLS:910-914`; `selectIntrinsicPeriodicSeedFront`, `CELLS:917-922`): the non-dominated filter is `seeds.filter(candidate => !seeds.some(other => other !== candidate && dominates(other, candidate)))` — an **O(n²) all-pairs scan preserving the original array's relative order** for retained elements (a `.filter`, not a re-sort); `rankIntrinsicPeriodicSeeds` is a stable `.toSorted(compareSeeds)` afterward. So the crop Pareto front's pre-rank order is crop-enumeration order (step 13), and only the final rank (§6 `compareSeeds`) determines the front slice.
15. **`sourceCropSurvival` / `sourceAuditWitnesses` output ordering** (`PORTFOLIO:904-909,910-928`): both explicitly `.toSorted(role.localeCompare, then sourceKey.localeCompare)` (survival) or via `rankIntrinsicPeriodicSeeds(...).slice(0,16)` (witnesses) before being returned — i.e. these diagnostic arrays have their own final canonical order independent of the internal `Map` accumulation order.
16. **`eligibleSourceDomainEntries`** (`PORTFOLIO:1221-1248`, replay-envelope path only): `.toSorted((a,b) => eligibleSourceDomainEntryKey(a).localeCompare(eligibleSourceDomainEntryKey(b)))` where the key is `JSON.stringify([familyKey, role, sourceKey, sourceKind, cellKey])` — used to build a **digest input** (§8), so this order directly determines hash bytes.
17. **`canonicalJson`** (`PORTFOLIO:1285-1293`, digest/replay path only): object keys sorted via `.toSorted(([k1],[k2]) => k1.localeCompare(k2))` — again `localeCompare`, feeding SHA-256 digest bytes (§8, §12).

## 6. Comparators and tie rules

All comparators below return the JS convention (`<0` first-before-second, `0` tie, `>0` second-before-first) and, unless noted, are consumed by stable sorts.

- **Eligible-family sort** (`CELLS:290-296`): `members.length desc → members.length*collisionAreaMm2 desc → key.localeCompare(asc)`. Note the second key is a **float product** (`Number * Number`, not exact) — see §7.
- **`transformOrder`** (`CELLS:48-52`): `index asc → rotationDeg asc → mirrored asc(false<true)` via `effect`'s `Order.combineAll`/`Order.mapInput`. Purely numeric/boolean, locale-independent, safe to port as a plain tuple comparison.
- **`compareCells`** (`CELLS:2313-2326`, the canonical periodic-cell rank): 
  1. `finiteCropDiagnosticPriority(first) - finiteCropDiagnosticPriority(second)` asc, where priority is `0` if `threeByThreeLatticeLegal && threeByThreeCentreContactComplete`, `1` if only `threeByThreeLatticeLegal`, else `2` (`CELLS:2328-2332`) — i.e. **fully-diagnosed-legal cells always rank before partially-legal ones, which always rank before neither**, regardless of density.
  2. `densityOrder`: exact `bigint` cross-multiplication comparing `memberDoubledAreaGrid2/determinantGrid2` ratios **without floating division** — `compareBigInt(second.memberDoubledAreaGrid2 * first.determinantGrid2, first.memberDoubledAreaGrid2 * second.determinantGrid2)` (`CELLS:2314-2317`) — i.e. **higher density (more material per unit lattice area) ranks first**; this is the exact-rational analogue of the float `density` field but is what actually governs ordering.
  3. `envelopeMaximumSideMm` asc (float subtraction).
  4. `hullWasteRatio` asc (float subtraction).
  5. `sharedBoundaryLengthMm` **desc** (`second - first`, float subtraction) — more shared boundary wins.
  6. `canonicalKey.localeCompare` asc — final deterministic tie-break.
- **`periodicCellFront`'s outer sort** (`CELLS:673-677`): `sourceKind.localeCompare asc`, then `compareCells`. `sourceKind` is one of `'axis-union' | 'nfp-boundary-vertex-pair' | 'edge-contact-pair' | 'legacy'` (the last only when `basisProvenance` is absent) — plain ASCII, `localeCompare` and codepoint order coincide for these specific literals, but the code still calls `localeCompare` (§12 risk still applies generically even if this specific call site is safe today).
- **`compareSeeds`** (`CELLS:833-841`, drives `rankIntrinsicPeriodicSeeds`): `componentCount asc → isolatedPieceCount asc → largestComponentSize desc → compareIntrinsicPeriodicSeedEnvelope(...) → canonicalKey.localeCompare asc`. Fewer positive-contact components and fewer isolated pieces rank first; larger largest-component ranks first; then envelope (below); then lexicographic canonical key.
- **`compareIntrinsicPeriodicSeedEnvelope`** (`CELLS:864-884`, max-side-first) and **`compareIntrinsicPeriodicSeedEnvelopeAreaFirst`** (`CELLS:887-907`, area-first) — **two distinct comparators with the same three terms in different priority order**, both with the same three-tier `exactEnvelope`-presence fallback (§3): if either side's exact envelope is missing, both undefined → float fallback triad in the same term order as the exact branch; exactly one undefined → the side **with** an exact envelope is treated as **better** (`return firstEnvelope === undefined ? 1 : -1`, i.e. presence of exact data always wins over its absence, independent of magnitude). The area-first variant (`compareIntrinsicPeriodicSeedEnvelopeAreaFirst`) is the one actually used for production **execution ordering** (§5 step 12); the max-side-first variant (`compareIntrinsicPeriodicSeedEnvelope`) is the one used inside `compareSeeds` for **Pareto ranking/selection**. These must not be conflated in the Rust port — they are genuinely different orderings used for different purposes.
- **`periodicSeedDominates`** (`CELLS:933-976`, Pareto dominance predicate): six-term "no worse in all, strictly better in at least one" predicate over `(componentCount asc-is-better, isolatedPieceCount asc-is-better, largestComponentSize desc-is-better, maximumSide asc-is-better, area asc-is-better, span asc-is-better)`, using the same exact-grid-vs-float fallback as the envelope comparators (but note: **when exactly one side lacks an exact envelope, dominance is unconditionally `false`** — `if (firstEnvelope !== undefined || secondEnvelope !== undefined) return false`, `CELLS:937` — a different, stricter rule than the "presence wins" rule used in the rank comparators above; a mixed exact/non-exact pair can never dominate either way, only tie or be incomparable for ranking purposes).
- **Crop coordinate ordering** (`cropCoordinates`, `CELLS:822-826`): `row asc, column asc` (traversal `'row'`) or `column asc, row asc` (traversal `'column'`) — plain integer comparison.
- **`edgeContactProvenanceKey` compare / `compareEdgeContactRelations`** (`CELLS:1544-1556`): relation retention max-by-`lengthMm` (`CELLS:1298-1307`, float `>`, tie broken by `edgeContactProvenanceKey(...).localeCompare(...) <` — smaller key wins on tie, i.e. the *opposite* convention from most other tie-breaks which sort ascending and take index 0; here it is expressed as a direct replace-condition, not a sort) then `compareEdgeContactRelations` for the retained-list sort: `lengthMm desc → squaredGridLength(vector) asc (exact bigint) → provenanceKey.localeCompare asc`.
- **Edge-contact pair candidate sort** (`CELLS:1363-1369`): `determinant asc (exact bigint) → squaredSpan asc (exact bigint, sum of two squared lengths) → contactLengthMm desc (float) → sourceKey.localeCompare asc`. Smaller-determinant (smaller lattice cell), smaller-span, then more total contact length, wins.
- **`rankContinuations`** (`PORTFOLIO:1438-1452`): ranks by the **index position** of each continuation's `seed` in `rankIntrinsicPeriodicSeeds(continuations.map(seed))` (i.e. re-derives a fresh seed-rank over just this continuation subset, not a global rank), tie-broken by `sourceId.localeCompare asc`; continuations whose seed is missing from the rank map (should not happen given every continuation's seed came from the same array being ranked) fall back to `Number.MAX_SAFE_INTEGER`.
- **`preferPeriodicContinuation`** (`PORTFOLIO:1464-1472`): non-witness continuations (`sourceId` not starting with `'raw-witness:'`) always beat witness continuations regardless of any other criterion; among two continuations with the same witness-status, the one with the lexicographically (`localeCompare`) smaller `sourceId` wins, using `<=` (so on an exact string tie, `first` wins — but `sourceId` ties should be impossible given `sourceId` is itself a dedup identity per family/role/cell/crop-index).
- **`sourceAuditWitnesses` replace condition** (`PORTFOLIO:761`): `provenance.sourceKey < current.sourceKey` — **plain JS `<` on strings, i.e. raw UTF-16 code-unit order, not `localeCompare`.** This is the one clear exception to the "everything user/geometry-key-facing uses localeCompare" pattern in this cluster and must be ported as a distinct (simpler, safer) comparison, not folded into the same helper as the `localeCompare` call sites.
- **`makeSourceAuditReplayEnvelope`/`validateSourceAuditReplayEnvelope`** ordering comparators — covered in §5 items 16-17 (`eligibleSourceDomainEntryKey(...).localeCompare(...)`, `canonicalJson`'s key `localeCompare`).

## 7. Numeric semantics

- **Grid conversion** (`toGridMm`/`fromGrid`, `src/workers/irregular/clipper2OffsetPolicy.ts:44-58`): `toGridMm` returns `undefined` for non-finite input; scales by `1000` (`CLIPPER2_OFFSET_POLICY.scale`); rounds via `Math.floor(Math.abs(valueMm)*1000 + 0.5) * Math.sign(valueMm)` — **round-half-away-from-zero on the absolute value, then sign-restored**, not `Math.round` (which rounds half-**toward**-positive-infinity and would differ for negative half-way values); finally checked with `Number.isSafeInteger`, returning `undefined` on overflow (never throws, never silently wraps). `fromGrid` is a bare `value/1000` division, **no rounding**, i.e. `fromGrid` is not a true inverse of `toGridMm` in general (it can reintroduce binary64 rounding error for values not exactly representable as `n/1000`). Used throughout this cluster via `gridPoint`/`fromGridPoint` (`CELLS:2341-2349`), `anchorPoint` (`CELLS:2139-2143`), and `boundaryCandidatePoints` (`CELLS:2059-2062`).
- **Exact grid arithmetic** is `bigint` throughout the geometry-derivation core: `GridPoint {x: bigint, y: bigint}`, `crossGrid`, `dotGrid`, `squaredGridLength`, `polygonAreaGrid2`, `absBigInt`, `compareBigInt` (`CELLS:2355-2365`, all pure exact integer ops, no overflow-checked arithmetic — JS `bigint` is arbitrary precision so this is a non-issue in TS, but **is** a issue in Rust: the migration prompt (§8.2) requires checked arithmetic and a wide/arbitrary-precision fallback; `i128`/`i256` bounds must be proven against real coordinate/product magnitudes (grid coordinates × grid coordinates × member counts × lattice indices) before choosing a fixed-width type).
- **Two near-identical but separately-defined `compareBigInt(s)` functions**: `compareBigInts` imported from `src/workers/irregular/canonicalGridMath.ts:12-14` (`first === second ? 0 : first < second ? -1 : 1`) is used only inside `CELLS` for the exact-envelope seed comparators (`CELLS:881,903,956-960` etc. via the imported name); a **locally-defined, differently-named** `compareBigInt` (singular) at `CELLS:2363-2365` (`first < second ? -1 : first > second ? 1 : 0`) is used for everything else in `CELLS` (grid-point compares, edge-contact ordering, etc.). Both compute the same mathematical sign for all inputs — this is a naming/duplication hazard, not a behavioral divergence, but a Rust port collapsing these into one function must verify by inspection (not just by name-matching) that every call site is semantically the "sign of `a - b`" comparator and not, e.g., a different one accidentally introduced later. Flag prominently for the port reviewer (§12).
- **`BigInt(number)` conversions**: `BigInt(coordinate.row)`, `BigInt(coordinate.column)` (`CELLS:749-750`), `BigInt(n)`, `BigInt(m)` (`CELLS:1975-1976`) — always applied to small, provably-integer loop counters (`rows`/`columns` bounded by `q = floor(familyMembers.length / memberCount)`, and `n,m ∈ {-1,0,1}`), so no precision hazard here. `BigInt(envelope.areaGrid2 as string)` (`CELLS:881` etc.) parses an already-exact decimal string back to `bigint` — this round-trips exactly by construction (the string was produced by `.toString()` on a `bigint`), but a Rust port must ensure its own `i128`/`BigInt`-equivalent `to_string()`/`from_str()` round-trip is equally exact (no scientific notation, no locale thousands separators — Rust's default integer `Display`/`FromStr` satisfy this, JS `bigint.toString()` also always emits plain decimal with no thousands separators for base 10).
- **`Number(bigint)` narrowing (precision-lossy by construction, not overflow-checked)**: `density: Number(memberDoubledAreaGrid2) / (2 * Number(determinantGrid2))` (`CELLS:1130`, diagnostic-only per §3); `hullWasteRatio: Number(hullDoubledAreaGrid2 - memberDoubledAreaGrid2) / Number(hullDoubledAreaGrid2)` (`CELLS:2268-2269`, **load-bearing**, feeds `compareCells` term 4); both silently round to the nearest representable `f64` for magnitudes beyond `2^53`, with no error and no flag. A Rust port must reproduce the exact `f64` rounding of `BigInt -> f64` (i.e. round-to-nearest-even of the mathematical value), not a naive `as f64` cast if the source integer type doesn't guarantee the same rounding rule (Rust's `i128 as f64` and `num_bigint::BigInt::to_f64()` both round-to-nearest but must be independently verified against V8's `Number(bigint)` algorithm for tie cases).
- **Float accumulation order** (not reassociated relative to source): `sharedBoundaryLengthMm += contact` inside a nested `for` loop over `(n,m,memberIndex)` combinations for centre tiles only, then over all non-centre `placed` indices (`CELLS:1990-2015`) — **summation order is loop-iteration order**, i.e. binary64 addition is not commutative/associative in general and the exact final float bit-pattern depends on this order; a Rust port must iterate in the identical nested order and accumulate with a plain `+=`, not a `sum()`/fold over a differently-ordered collection or a `Kahan`-style compensated sum (which would change the bit pattern).
- **`envelopeMaximumSideMm`/`areaMm2`/`spanMm` (float mm derived from float mm bounds, not grid-derived)**: `measureBaseCellShape` (`CELLS:2245-2271`) operates on plain float millimeter points (`geometry.polygon.points.map({x,y}) + point`), i.e. **not** grid-quantized at this stage — `Math.max(bounds.maxX-bounds.minX, bounds.maxY-bounds.minY)`. Two plain float subtractions then a `Math.max`; order matters only in that it must remain `(maxX-minX)` and `(maxY-minY)` in that operand order (subtraction is not commutative in float rounding in general, though for typical magnitudes here the difference is usually inconsequential — still, preserve operand order exactly).
- **`combinedBoundsNonnegative`** (`CELLS:2080-2092`): plain float `>=` `0` checks (`geometry.bounds.minX + point.x >= 0`), no epsilon — an exact float comparison after a float addition; a Rust port must perform the identical `f64` addition then exact `>=` compare, not introduce a tolerance (the migration prompt explicitly forbids introducing epsilons into exact comparisons, §2 of the prompt).
- **`Number.isSafeInteger` gates**: `unionForbiddenBoundaries` (`CELLS:1794`, aborts the whole union — returns `undefined` — if any coordinate's `Number(bigint)` cast is not a safe integer, since Clipper2's JS binding takes `number` coordinates); `sourceAuditSurvivalCountsValid` (`PORTFOLIO:1268-1279`) and the replay envelope's `nonDominatedCropCount` check (`PORTFOLIO:1060-1065`) similarly gate on `Number.isSafeInteger(value) && value >= 0`.
- **No `NaN`/`Infinity` production paths observed** inside pure arithmetic in this cluster beyond the explicit `Number.isFinite`/`isSafeInteger` guards already covered (`toGridMm`, envelope metrics via `canonicalLayoutGeometry.ts`, which itself checks `.every(Number.isFinite)` before accepting a metric, `src/workers/irregular/canonicalLayoutGeometry.ts:328-338`) — this cluster does not itself re-check `Number.isFinite` on the float mm fields it consumes from those functions; it trusts the upstream metric functions' own finiteness gates.
- **No BigInt used in canonical JSON/hash encoding within this cluster** — everywhere a `bigint` value needs to be serialized for provenance/keys it is first `.toString()`-converted to a decimal string (`determinantGrid2`, `memberDoubledAreaGrid2`, rational numerator/denominator strings via `serializeRationalPoint`, `CELLS:1868-1873`). The local `canonicalJson` encoder (`PORTFOLIO:1285-1293`) therefore never has to special-case `bigint` (and would throw via `JSON.stringify` if it ever received one, since `JSON.stringify` cannot serialize `bigint` — this is a latent landmine if a future field change ever puts a raw `bigint` into a structure passed to `canonicalJson`, worth a defensive note for the Rust port's equivalent encoder, which should assert/panic rather than silently mis-encode).

## 8. Serialization and hashing

Two independent string-key/canonicalization schemes coexist in this cluster; they must **not** be conflated in the Rust port.

### A. Geometry/basis canonical keys (exact-grid, no JSON, no hashing)

- **`canonicalTransformedPolygonKey`** (`CELLS:2145-2152`): min-corner-translate to `(0,0)` in exact grid units, then `canonicalCycle` (below). Used only for transform-shape dedup (§5 item 3), never externally serialized.
- **`canonicalCycle`** (`CELLS:2217-2226`): for a closed exact-grid point cycle, generates all `2 * n` variants (both winding directions × every rotation offset), renders each as `` `${x},${y}` `` joined by `;`, **bare `.toSorted()`** (UTF-16 code-unit order, §5 item 10), takes index `[0]`. This is the rotation/winding-normalization the migration prompt (§9) calls "ring-origin normalization" and "winding normalization" — the exact string format (`x,y;x,y;...`, decimal `bigint` renders, no leading `+`, `-` for negatives via `bigint.toString()`'s default) must be reproduced byte-for-byte since it feeds `canonicalCellKey` (below), which is the `canonicalKey` field used pervasively as a dedup and hash-adjacent identity.
- **`canonicalCellKey`** (`CELLS:2154-2201`): for each of the 4 quarter-turns (`0/90/180/270°`, exact integer rotation of `bigint` coordinates — `(x,y)→(-y,x)→(-x,-y)→(y,-x)`, `CELLS:2169-2180`), computes each member's `canonicalCycle` after re-translating to the rotated min-corner, joins per-member keys with `.toSorted()` (bare, §5 item 10) and `|`, then appends `:${v1};${v2}` **and separately** `:${v2};${v1}` (both basis orderings) as two variants per quarter-turn — **8 total variants** (4 turns × 2 basis orders) — takes the global-bare-`.toSorted()` minimum, prefixed with `` `${role}:` ``. This is the whole-cell identity used for cross-cell dedup (`periodicCellFront`'s `unique` map, `identities` Set in crop enumeration indirectly via `canonicalCollisionLayoutIdentity`, not this key directly — crops use a **different** identity function, next).
- **`canonicalCollisionLayoutIdentity`** (`src/workers/irregular/canonicalLayoutGeometry.ts:139-150`, a different module/cluster) is the identity used for **crop-level** dedup (`CELLS:771,780,784`) and for `periodicContinuationFutureKey`'s `geometry` field (`PORTFOLIO:1461`) — takes the minimum of 4 quarter-turn identities over the *placed pieces'* canonical grid polygons (not the base-cell members). This is a **different function from `canonicalCellKey`** even though both do "minimum over 4 quarter-turns" — do not merge them in the Rust port; they operate on different inputs (base-cell 2-vector-basis-plus-members vs. a flat list of placed pieces) and are semantically distinct identities used for different dedup domains (per-cell vs per-crop).

### B. Digest/replay canonical JSON (`PORTFOLIO`, replay-envelope path only, not exercised in production — §1)

- **`canonicalJson(value)`** (`PORTFOLIO:1285-1293`): recursive; `null`/non-object → `JSON.stringify(value)` (so numbers/strings/booleans render exactly as V8's `JSON.stringify` would — including `-0 → "0"`, standard IEEE754-to-shortest-round-trip-string number formatting, and standard JSON string escaping); arrays → `[` + comma-joined recursive results + `]` (**no sorting of array elements** — array order is preserved exactly, only **object keys** are sorted); objects → filter out entries whose value is exactly `=== undefined`, then `.toSorted(([k1],[k2]) => k1.localeCompare(k2))` (**locale-aware**, §12 hazard), each rendered as `` `${JSON.stringify(key)}:${canonicalJson(value)}` ``, joined by `,`, wrapped in `{}`. No whitespace anywhere (fully dense). This is a bespoke encoder, **not** the "canonical checkpoint JSON" encoder referenced generically in the migration prompt §9 — it is local to this file and used only for three digest inputs:
  - `sourceAuditPreparedInputDigest(pieces) = sha256(canonicalJson(pieces))` (`PORTFOLIO:1203-1207`) — hashes the **entire prepared-piece array** (including nested `ImportedPiece`/`CollisionGeometry`/`transforms` structures) exactly as the domain classes expose their own properties (subject to the constructor-conditional-omission semantics of §3).
  - `sourceAuditEligibleDomainDigest(catalog, scope, basisSourceKey) = sha256(canonicalJson(eligibleSourceDomainEntries(...)))` (`PORTFOLIO:1209-1215`) — `eligibleSourceDomainEntries` is already `localeCompare`-sorted (§5 item 16) before this digest, so `canonicalJson`'s own key-sort only affects the per-entry field order, not entry order (arrays are never reordered by `canonicalJson`).
  - `sourceAuditReplayDigest(replay) = sha256(canonicalJson(replay))` (`PORTFOLIO:1217-1219`).
  - `sha256(value) = createHash('sha256').update(value).digest('hex')` (`PORTFOLIO:1281-1283`) — standard SHA-256 over the UTF-8 bytes of the `canonicalJson` string (Node's `createHash('sha256').update(string)` encodes the JS string as UTF-8 by default), lower-case hex digest. **UTF-8 encoding of a JS string is UTF-16-to-UTF-8 transcoding**, which for any surrogate-pair or lone-surrogate content in piece IDs/labels must be reproduced exactly by the Rust port's string handling (Rust `String` is always valid UTF-8 internally, but the *source* JS strings could theoretically contain unpaired surrogates from malformed input that `JSON.stringify`/UTF-8 encoding handle via replacement-character substitution — an edge case worth a differential test, not just an assumption).
- **`eligibleSourceDomainEntryKey`** (`PORTFOLIO:1250-1257`) and **`sourceAuditSurvivalKey`** (`PORTFOLIO:1260-1266`) both use **raw `JSON.stringify(array)`** (not `canonicalJson`) over small fixed-shape tuples of strings — since these are homogeneous string arrays with no object-key-ordering ambiguity, plain `JSON.stringify` is deterministic and does not need the custom encoder; still must be reproduced with standard JSON array/string escaping in Rust (e.g. via `serde_json::to_string` on a `Vec<String>`/tuple, which is byte-compatible for pure-ASCII content but must be verified for escaping of `"`, `\`, control characters, and non-ASCII if any of `familyKey`/`sourceKey`/`cellKey` ever contain them).
- **Replay envelope format markers**: `formatVersion: 3` (numeric literal type, `PORTFOLIO:122,1000`) and `algorithmVersion: 'intrinsic-periodic-source-audit-v3'` (`PORTFOLIO:123,1001`) are both validated with exact equality (`PORTFOLIO:1027-1030`) before anything else — a Rust port must treat these as opaque exact-match version gates, never "upgrade" or "coerce" a differently-versioned envelope.

## 9. Caches touched and the exact historical access sequence

This cluster **owns no persistent cache of its own** (§4 — everything is function-scoped and discarded per call). It is, however, a heavy **caller** into the shared NFP/geometry cache (`NfpIfpService.computeNfp`, owned by `src/workers/irregular/nfpIfpService.ts`, a different cluster) and into placement validation (`PlacementValidation.checkSheetless`, `src/workers/irregular/placementValidation.ts`). Documenting call sites and call order here (the parts *this* cluster controls); the NFP cache's own internal validate/lookup/stale-evict/recompute/publish sequence is out of scope for this doc and must come from that cluster's own characterization.

Ordered `computeNfp` call sites within one `enumerateIntrinsicPeriodicFamily` invocation:

1. **P1 phase** (`CELLS:426-444`), for each retained transform representative, `deriveCells` calls `computeNfp` once per **ordered** `(fixedMember, movingMember)` pair over `input.members × input.members` (`CELLS:1043-1050`) — for a P1 cell (`members.length === 1`), this is exactly **one** self-pair NFP computation (`fixed === moving` piece/geometry/point, since there is only one member).
2. **P2 pair-enumeration phase** (`CELLS:448-502`), for each unordered `(first, second)` transform pair, **one** `computeNfp` call to place `second` relative to fixed `first` (`CELLS:466-470`) — this determines the candidate placement points (`boundaryCandidatePoints`) tried for legality before any cell derivation happens.
3. For each **legal** P2 candidate point, `deriveCells` is called with 2 members, so its internal `(fixedMember, movingMember)` double loop makes **4** `computeNfp` calls (self×self, self×other, other×self, other×other) — note this recomputes the P1-style self-NFP for each member **again** even though it may have already been computed during the P1 phase for the same representative geometry; whether the underlying `NfpIfpService` cache absorbs this redundancy is that service's concern, but **this cluster issues the call regardless**, in this fixed nested order, every time `deriveCells` runs.
4. Within `deriveEdgeContactBasisCandidates` → `validateEdgeContactRelation` (`CELLS:1441-1502`), **no `computeNfp` calls** — edge-contact validation uses `PlacementValidation.checkSheetless` plus `sharedConvexPolygonBoundarySegments` (a different, non-NFP geometric routine) instead.
5. Within `diagnoseLattice`'s 3×3 sweep (`CELLS:1962-2022`), **no `computeNfp` calls** — legality is `PlacementValidation.checkSheetless` only, and boundary contact is measured via `sharedConvexPolygonBoundaryLength`, not NFP.

`PlacementValidation.checkSheetless` call ordering (all within this cluster's control flow, each call independently builds its own `placed` accumulator — no shared spatial index state persists across calls from this cluster):

- P2 candidate-point legality (`CELLS:479-483`) — checked against `[fixed]` only (single placed piece).
- Crop placement legality (`CELLS:754-763`) — checked incrementally against the **growing** `placed` array within one crop attempt (grows across `coordinates × cell.members` nested loop, §4/§5 item 13); a failure at any point aborts that crop attempt (`legal = false; break`) without rolling back already-pushed `placed` entries (irrelevant since the whole `placed` array is discarded on failure — but note the **order of the double break is `break` out of the inner member loop first, then the outer coordinate loop checks `!legal || sourceIndex >= q*memberCount` and breaks too**, `CELLS:761-767` — a two-level early-exit, not a single flat check).
- Edge-contact relation validation (`CELLS:1455-1459`) — checked against a **growing** `placed` array built from `members` in `members` array order (not fixed/moving order), independent of which specific `(fixedEdge, movingEdge)` pair is being validated; this placement-growth loop runs **once per candidate vector** tested (i.e. redundantly re-derives the same "is the base cell itself internally legal at this offset" check for every candidate edge-pair vector that reaches this stage), not once per relation.
- 3×3 lattice diagnostic (`CELLS:1979-1983`) — checked against a growing `placed` array across the full `n∈[-1,1] × m∈[-1,1] × members` sweep (9 × memberCount placements built up in strict `n` outer, `m` middle, `memberIndex` inner loop order) — this order determines **which tile is "the centre"** (`n===0 && m===0`, `CELLS:1985`) for the purposes of the `center: Set<number>` index bookkeeping, and any legality failure at any point aborts the **entire** diagnostic for that basis (`return {legal:false,...}` immediately, `CELLS:1969,1972,1984`), i.e. a single illegal tile anywhere in the 3×3 neighbourhood invalidates the whole basis candidate, not just that tile.

**Cross-call cache hint relevant to the Rust port (§9/§13 of the migration prompt):** because this cluster issues highly repetitive `computeNfp`/`checkSheetless` calls with structurally identical (or translated-identical) inputs across P1/P2/edge-contact/3×3-diagnostic phases and across multiple representative transforms, the **shared NFP/geometry cache's hit rate for this cluster's traffic is likely very high** — this is exactly the kind of "independent pairwise relative NFP computations after key deduplication" and "read-only spatial-index queries for an immutable state" the migration prompt (§14.1) flags as a good Rayon candidate *once the caller-side call graph above is preserved exactly*. The call **order** documented here is what the Rust port's single-threaded parity implementation must reproduce before any caching/parallelism redesign; only after single-thread parity is proven should the cache-namespace design (migration prompt §13.3) be evaluated for this traffic pattern specifically.

## 10. Cancellation / deadline / budget / evaluation-cap observation points

Two independent mechanisms, never conflated in source:

### A. Cooperative cancellation (`IrregularNfpIfpControl.checkpoint('candidate-points')`)

The `control` object supplied by the production coordinator only ever signals `reason: 'cancelled'` (constructed at `COORD:512-525` from `input.options?.isCancelled?.()`); it never itself signals `reason: 'deadline'` for this cluster's call sites (deadlines are enforced separately, part B). Every checkpoint call in this cluster uses the **same single phase literal**, `'candidate-points'` — never `'ifp'`, `'placed-nfp'`, `'ifp-boundary-intersection'`, or `'pairwise-nfp-boundary-intersection'` (those phases are used by other clusters). Complete inventory of checkpoint call sites (28 total across both files):

`CELLS`: `314, 390, 427, 450, 473, 717, 727, 731, 738, 1045` (10 sites) — top-level family loop, per-representative-transform loop (×2, one in the runtime-check block), P2 pair/candidate double loop (×2), crop-enumeration outer/rows/traversal-corner/coordinate loops (4 sites, nested), and inside `deriveCells`'s fixed×moving member double loop (1 site, innermost — checked **once per NFP call**, i.e. up to 4 times per `deriveCells` invocation for a P2 cell).

`PORTFOLIO`: `633, 699, 749, 776, 819` (5 sites) — top of `selectIntrinsicPeriodicContinuations`, top of the per-family loop, inside the source-audit cell loop, inside the ordinary-cell loop, inside the replay-witness loop.

**Critical omission (verified by grep, not an oversight to "fix" in the Rust port — preserve exactly):** `deriveEdgeContactBasisCandidates` (`CELLS:1246-1407`, a 4-level nested loop: `fixedMemberIndex × movingMemberIndex × fixedEdge × movingEdge`, each iteration potentially calling `validateEdgeContactRelation` which itself grows a `placed` array and calls `checkSheetless` once per member), `validateEdgeContactRelation` (`CELLS:1441-1502`), and `diagnoseLattice` (`CELLS:1955-2023`, a 3×3×members sweep) contain **zero** `control?.checkpoint(...)` calls anywhere in their bodies. These are the most expensive inner loops in the file (up to `members² × edges² × 2` relation candidates, each independently validated with a placement-growth simulation) and yet are **not cooperatively cancellable mid-loop** — cancellation is only observed at the caller's next checkpoint after these functions return. A Rust port must **not** add cancellation checks inside these functions "for responsiveness" — doing so would change the exact moment cancellation becomes observable relative to expensive lattice-membership computation, which the migration prompt (§13.2) explicitly forbids ("If parallel execution changes when a lookup occurs relative to a semantic cancellation or deadline checkpoint, the parallel design is not yet valid" — the same principle applies to adding *new* checkpoints, not just moving existing ones).

### B. Wall-clock deadlines (`performance.now()` deltas against `maximumRuntimeMs`)

Independent of cancellation; enforced by explicit `if (performance.now() - startedAt >= maximumRuntimeMs) { ...; break }` checks, never via `control.checkpoint`'s abort mechanism for this cluster. Complete inventory:

- `CELLS:315` — top-level family loop (`enumerateIntrinsicPeriodicCells`), breaks the family loop (remaining `selectedFamilies` never processed).
- `CELLS:391,428,455,474` — per-representative-transform loop, P1-cell loop, P2 outer-pair loop, P2 inner-candidate-point loop, each setting `runtimeCoverageComplete = false` (and, for the two P2 sites, also `pairCoverageComplete = false`) before breaking.
- `PORTFOLIO:302-313` — the **per-continuation global budget check** inside `runIntrinsicPeriodicFamilyPortfolio`'s execution loop: `remainingMs = maximumTotalRuntimeMs - (performance.now() - startedAt - replayProbeExcludedMs)`; if `<= 0`, the continuation is recorded with `status: 'global-deadline'` **without being executed at all** (no decoder call), and the loop **continues to the next continuation** (does not `break`) — i.e. once the global budget is exhausted, **every remaining continuation in the execution-ordered list still gets a `runs` entry**, each individually marked `'global-deadline'`, rather than the array being truncated. This is a specific, testable shape (`runs.length === continuations.length` always holds, even under global-deadline exhaustion) that a Rust port must preserve — do not "optimize" by skip-appending once the budget is known exhausted.
- `PORTFOLIO:322` — per-continuation runtime cap passed to the decoder: `maximumRuntimeMs: Math.min(maximumContinuationRuntimeMs, remainingMs)` — the **smaller** of the fixed per-continuation cap (production: 30,000 ms) and whatever wall-clock budget remains from the shared 240,000 ms total; this is recomputed fresh for **every** continuation (not decremented from a running "remaining continuation budget" separate from the global one), i.e. the per-continuation cap can only ever shrink as the portfolio's total elapsed time grows, never grow back.

### C. Evaluation-cap (candidate-evaluation count, not wall-clock)

- `maximumContinuationCandidateEvaluations` — production value `INTRINSIC_SHARED_ARCHIVE_PERIODIC_EVALUATION_CAP = 19_862` (`SHARED:47`), passed through to `constructIntrinsicStrictState` as `maximumCandidateEvaluationCount` (`PORTFOLIO:324-326`). The decoder (a different cluster, `DECODER`) enforces this and reports `truncationReason: 'maximum-candidate-evaluations'` on its result; `PORTFOLIO:370-380` maps that into `status: 'evaluation-cap'` **without calling `finalizeIntrinsicStrictState`** (i.e. an evaluation-capped construction never gets ranked/hashed into a completed-metrics candidate — it is recorded but excluded from the archive entirely, `PORTFOLIO:394-396` only flat-maps `run.result?.metrics`, and `result` stays `undefined` for evaluation-cap runs).
- This same `maximumContinuationCandidateEvaluations` value, when **defined** (always true in production), is also what triggers the cost-based **execution reordering** described in §5 item 12 (`continuationsForExecution`, `PORTFOLIO:594-601`) — i.e. the evaluation cap being active is the same condition that activates the "cheaper seeds first" execution order. A Rust port must treat "evaluation cap is set" as the single boolean gate for **both** effects (decoder truncation **and** execution reordering), not two independently-toggleable behaviors, since production always sets it and the two effects are coupled through this one `undefined`-check in source.

### D. Cancellation vs. deadline error classification at the continuation boundary

`PORTFOLIO:336-352`: if a continuation's `constructIntrinsicStrictState` call fails with `IrregularNfpIfpControlAbortError` and `reason === 'cancelled'`, the **entire portfolio run fails** (`return yield* Effect.fail(constructed.error)` — propagates up through `runIntrinsicPeriodicFamilyPortfolio`, `runIntrinsicSharedArchivePortfolio`, and `coordinateIntrinsicSharedArchive` as a hard job failure). If it fails with `IrregularNfpIfpControlAbortError` and `reason === 'deadline'` (a *decoder-internal* deadline distinct from this cluster's own §B wall-clock checks), the continuation is recorded with `status: 'deadline'` and the loop **continues** to the next continuation (not a global failure). Any **other** error tag is recorded as `status: 'invalid'` and also does not halt the loop. This three-way classification (`cancelled → propagate/fail-fast`, `deadline → per-continuation soft status`, `other → per-continuation soft status`) is exactly the "cancellation classifications" / "deadline classifications" the migration prompt (§2) forbids changing.

## 11. Error paths

- **`IrregularGeometryInputError`** (`operation: string, message: string`, `src/workers/irregular/services.ts:42-45`) — the only error type this cluster directly *constructs* (as opposed to merely propagating): `invalidReplay(message)` (`PORTFOLIO:1425-1432`), always with `operation: 'intrinsicPeriodicSourceAuditReplay'`, used for 5 distinct rejection messages inside `validateAndReconstructSourceAuditWitness` (`PORTFOLIO:1295-1364`: `'...provenance does not match its seed'`, `'...unknown or duplicate piece'`, `'...not canonically sheetless legal'`, `'...canonical identity mismatch'`, `'...topology mismatch'`, `'...envelope metric mismatch'` — 6 distinct messages, all sharing the operation tag). This function is only reached from the **live, non-replay** witness-admission path too (`PORTFOLIO:817-833`, called even when `sourceAuditReplay === undefined`, for freshly-discovered witnesses — not just for validating an externally-supplied replay envelope), so **this error path is live in production** whenever `admitSourceAuditWitnesses` is true (it is, §1) and a freshly-discovered witness fails self-validation — which should be geometrically impossible for a witness derived from the same run's own catalog, but the code does not special-case "trust freshly-derived witnesses without re-validation" — it always re-validates through the same function used for externally-supplied replay data. A Rust port must not skip this re-validation for the live (non-replay) path as an "optimization," since a validation failure here becomes a hard `IrregularGeometryInputError` that propagates out of `runIntrinsicPeriodicFamilyPortfolio` (no `Effect.catch` around this specific call, `PORTFOLIO:823`).
- **`IrregularGeometryInputError`/`IrregularNestingNotImplementedError`/`IrregularNfpIfpControlAbortError`** propagated (not constructed) from `GeometryKernel.transformCollisionGeometry`, `NfpIfpService.computeNfp`, and `PlacementValidation.checkSheetless` — this cluster's `Effect` type signatures (`CELLS:275-281,373-378`, `PORTFOLIO:230-235`) union in exactly these three tags plus, for `PORTFOLIO`, `IntrinsicStrictDecoderError` (from the decoder). None of these three propagated tags are ever caught/reinterpreted inside `CELLS`; `PORTFOLIO` catches decoder-level `IrregularNfpIfpControlAbortError` specifically at the continuation boundary (§10.D) but otherwise also lets them propagate.
- **Silent `undefined`-returning failure paths (not exceptions)** — these are geometry-legality "no" answers, not error conditions, and are pervasive by design:
  - `unionForbiddenBoundaries` (`CELLS:1785-1810`): returns `undefined` on `Number.isSafeInteger` failure (coordinate too large for Clipper2's `number` input) or on any Clipper2 exception (`try { booleanOpWithPolyTree(...) } catch { return undefined }`, `CELLS:1803-1807`) or on `collectForbiddenTree` failure (`CELLS:1809`, itself catching `parent.child(index)` exceptions, `CELLS:1814-1819`). All three failure modes collapse to the same `undefined`, and the caller (`deriveAxisBasisCandidates`) treats `undefined` as "no axis-basis candidates from this call," not as an error — silently degrading to whichever other basis-derivation strategies (NFP-boundary-vertex, edge-contact) still produce candidates. **A Rust Clipper2 binding that throws a different exception type, or one that succeeds where `clipper2-ts` would have thrown (or vice versa), changes which basis sources are available for a given input — this is a real parity risk, not just an error-handling nicety.**
  - `canonicalizeBasis` (`CELLS:1910-1919`): returns `undefined` for a zero-determinant (collinear/degenerate) pair — recorded as a `'degenerateBasis'` rejection sample (`CELLS:1104-1106`), not an error.
  - `measureBaseCellShape` (`CELLS:2245-2271`): returns `undefined` when the convex hull has `< 3` points, or when `hullDoubledAreaGrid2 <= 0` or member area exceeds hull area (a geometric impossibility check) — recorded as `'baseShapeRejected'` (`CELLS:1117-1120`).
  - `gridPoint` (`CELLS:2341-2345`): returns `undefined` whenever `toGridMm` fails for either coordinate (non-finite or grid-overflow input) — propagates as `undefined` through many call sites, several of which (`deriveCells`, `CELLS:1051-1059,1064-1071`) convert this into an explicit **typed error** (`{cells: [], ..., rejected: {invalidMovingGrid: 1}, ...}` or `{..., rejected: {invalidForbiddenGrid: 1}, ...}`) rather than propagating an exception — i.e. this specific "coordinate didn't survive exact-grid conversion" condition is modeled as a **rejected-cell diagnostic**, not a thrown error, even though it represents a genuine data-validity problem. This is a real, source-verified oddity: most `gridPoint`-fails-silently paths just skip/filter, but these two sites in `deriveCells` **abort cell derivation for the entire member set** with a specific reason code, short-circuiting before any basis candidates are computed.
- **Job-level `IrregularPortfolioError`** (`COORD:739-762`, `category: 'search'`, `operation: 'intrinsicSharedArchive'`) is raised **outside** this cluster (in `COORD`) whenever `intrinsicSharedArchiveProductionValid` is false — this is the single most consequential error path this cluster's *coverage/completeness output* feeds into (§1), even though the error object itself is constructed elsewhere.

## 12. JS-specific semantics hazards for a Rust port

1. **`localeCompare` vs. bare/default `.toSorted()` are two distinct, non-interchangeable orderings used throughout this cluster, and mixing them up is the single highest-value correctness risk in a mechanical port.** `localeCompare` (used ~15 times across both files, enumerated in §5/§6) invokes ICU-backed Unicode collation under Node's default locale; bare `.toSorted()` (used for `rejected` reason maps and the two `canonicalCycle`/`canonicalCellKey` variant-string sorts, §5 item 10) uses raw UTF-16 code-unit comparison via the ES spec's default comparator (stringify-then-compare). For pure-ASCII, single-case, digit/punctuation-only inputs the two coincide in practice — but several `localeCompare` call sites operate on strings that **can** contain arbitrary user-supplied Unicode: `family.key`/`familyKey` embeds `JSON.stringify(interchangeabilityKey)` where `interchangeabilityKey` defaults to a user-controlled `piece.source.id` or an explicitly user-set interchangeability key (`FAMILYGROUP:124-130`), and `sourceId` strings embed that same `familyKey`. **This directly affects `selectedFamilies` truncation order (§5 item 1) and continuation tie-breaking/`sourceId` ordering (§5 items 11-12, §6) — both are "survivor order" per the migration prompt's non-negotiable list.** A Rust port needs a verified ICU-equivalent collation (e.g. `icu_collator`/`rust_icu` configured to match V8's default-locale root collation) for every `localeCompare` call site, and must **not** substitute `str::cmp`/byte ordering as a shortcut, even though byte ordering is exactly correct for the bare-`.toSorted()` sites.
2. **Two identically-behaving but separately-named `compareBigInt(s)` functions** (`canonicalGridMath.compareBigInts` vs. `CELLS`'s local `compareBigInt`, §7) — a real but purely cosmetic duplication; verify semantic equivalence by testing, not by assuming from the name, before consolidating in Rust.
3. **Stable-sort reliance.** Every `.toSorted(comparator)` call in this cluster (dozens, §5/§6) relies on ES2019+ stable sort semantics for correct tie-breaking when a comparator's explicit tie-break terms still leave ties (e.g. `compareCells`'s final `canonicalKey.localeCompare` term is usually a full tie-break, but several intermediate/no-op-comparator sorts, like `.toSorted()` with no comparator at all, or `.toSorted(x => x.x - x.y)`-style partial comparators used transiently, rely on stability for elements the comparator itself does not fully order). Rust's `sort_by`/`sort_by_key` are stable by default (unlike `sort_unstable_by`) — use the stable variants throughout, and treat any use of an unstable sort as a parity bug by default.
4. **`Map`/`Set` insertion-order reliance is pervasive and load-bearing**, not incidental — enumerated exhaustively in §4/§5 (`transformedByCanonicalKey`, `relations`, `perFamily`, `sourceAuditWitnesses`, `sourceCropSurvival`, `directValidCropsByCanonicalCell`, the `unique`/`bySourceKind` maps in `periodicCellFront`, `identities` Set in crop enumeration, `boundaryLineIntersections`'s dedup map, several basis-candidate dedup maps in `deriveAxisBasisCandidates`/`deriveNfpBoundaryVertexBasisCandidates`). Per the migration prompt (§9), Rust `HashMap`/`HashSet` must **never** be used as an ordering source for any of these — each needs either an explicit insertion-order-preserving structure (e.g. `indexmap::IndexMap`/`IndexSet`, verified to match JS Map/Set semantics including "re-inserting an existing key does not move its position, only replaces its value" — JS `Map.prototype.set` on an existing key preserves original insertion position, which `IndexMap::insert` also does) or an explicit `Vec` + separate lookup index maintained by hand.
5. **`Array.prototype.includes` used for a linear structural-equality scan** (`selectPeriodicTransformRepresentatives`, `CELLS:619`, `!result.includes(candidate)`) — `Array.prototype.includes` uses the SameValueZero algorithm, which for object references (as here — `candidate` is an object, not a primitive) is reference identity, not structural equality. This is O(n) per check but behaviorally simple (pointer/reference equality) — a Rust port using `Vec<T>::contains` on a non-`PartialEq`-derived-for-content type, or accidentally deriving structural `PartialEq`, would need to consciously choose reference-identity semantics (e.g. compare by index/ordinal, not by value) to match.
6. **`Object.prototype.hasOwnProperty`-gated optional fields** (§3) — several domain classes use a "declare + conditionally assign in constructor" pattern to produce true property omission (not `undefined`-valued presence). A Rust `Option<T>` field is the natural analogue, but the custom serializers in this cluster (`canonicalJson`'s explicit `!== undefined` filter, `makeBasisProvenance`'s spread-omission idioms, `PORTFOLIO:1191,1194,1208-1210,1357-1359`) must be reproduced as "skip the field entirely," not "serialize `null`" or "serialize an empty-but-present value."
7. **`JSON.stringify` default number formatting** feeds several cache/dedup keys indirectly (`intrinsicCollisionFamilyKey`'s `JSON.stringify([...])`, `eligibleSourceDomainEntryKey`'s `JSON.stringify([...])`, `periodicContinuationFutureKey`'s `JSON.stringify({...})`) — JS `JSON.stringify` on a `number` uses the ECMAScript `Number::toString` algorithm (shortest round-trip decimal representation), which differs from Rust's default `f64` `Display`/`ToString` in edge cases (though most values here are integers or simple strings, not arbitrary floats, so the practical exposure is low — still worth a differential test rather than an assumption, especially since `familyKey`/`sourceId` values are used as dedup/tie-break keys where any formatting divergence would silently change tie-break outcomes).
8. **`performance.now()`-based wall-clock budgets are inherently non-portable in absolute terms** but the **relative structure** (which checks exist, in what order, what they gate) is exactly what must be ported (§10) — the actual millisecond thresholds (30,000 / 25,000 / 15,000 / 240,000 / etc., enumerated in §1) are production constants that must be copied verbatim, not "tuned" for Rust's expected higher throughput; the migration prompt is explicit that runtime ceilings are not to be loosened to make porting easier, and conversely a faster Rust implementation finishing the same bounded work well under a deadline is fine and expected (only the deadline *values* and *check positions* are contractual, not the amount of real work that fits inside them).
9. **`Effect`-library `Order.combineAll`/`Order.mapInput`** (`transformOrder`, `CELLS:48-52`) is a declarative multi-key comparator combinator from the `effect` package — behaviorally it is exactly a tuple/lexicographic comparator (`index asc, rotationDeg asc, mirrored asc`), but a Rust port should verify there is no library-specific tie-break or NaN-handling nuance baked into `effect`'s `Order.Number`/`Order.Boolean` beyond plain numeric/boolean ordering (a quick source check of the `effect` package's `Order` module is warranted before assuming a plain tuple comparison is byte-identical, particularly around how it treats `NaN` inputs — `rotationDeg` should never be `NaN` in practice, but the comparator's own behavior under that input should be verified rather than assumed).

## 13. Parallelism assessment

### Chronology-bound — must stay logically serial

- **Continuation execution loop** (`PORTFOLIO:301-392`): each continuation's allowed decoder runtime is `Math.min(maximumContinuationRuntimeMs, remainingMs)` where `remainingMs` is computed from **cumulative elapsed wall-clock time across all prior continuations in execution order** (`PORTFOLIO:302-303`). This is a genuine shared, monotonically-shrinking resource budget consumed in strict sequence — true concurrent execution of continuations would change how much time each one gets relative to the documented serial schedule, which the migration prompt (§2) forbids ("deterministic caps," "checkpoint chronology"). If this is ever parallelized, the *time budget itself* must first be made execution-order-independent by a deliberate, separately-approved design change (out of scope for a semantics-preserving port) — not silently altered by running things concurrently.
- **`winner` selection via `Array.prototype.find` over `runs` in execution order** (`PORTFOLIO:398-402`, §5 item 12): when multiple continuations converge to the same `canonicalGeometryHash`, the reported winner is whichever one **appears first in execution order**. This is exactly the "archive admission as tasks finish" / "survivor selection as candidates finish" hazard class the migration prompt (§14.2) calls out as high-risk — any parallel execution of continuations must still publish `runs` in the documented serial execution order (not completion order) before this `find` runs, or must reproduce the find via an explicit ordinal-indexed reconstruction per the prompt's deterministic parallel pattern (§14.3): compute all continuation results independently in parallel by stable ordinal, write into stable slots, then perform the serial `runs`-order-dependent `find`/ranking/archive-admission exactly as today.
- **`selectIntrinsicPeriodicContinuations`'s per-family, then cross-family reservation/fill selection** (§5 item 11) is a multi-phase, `Map`-mutation-heavy, order-dependent reduction (family order → per-family continuation order → global `preferredByFuture` resolution → family-key-sorted reservation → global fill re-rank) with several `localeCompare`/insertion-order dependencies threaded through it. This is a selection *algorithm*, not an embarrassingly parallel batch — it should remain serial in its outer structure even if individual crop/legality computations inside it are parallelized (next section).
- **Global continuation dedup (`seenOrdinaryFutures`) and `preferredByFuture` resolution** are inherently sequential reductions over a shared mutable set/map — parallelizing the loops that populate them would require a different (and therefore non-preserving) conflict-resolution strategy unless carefully redesigned to compute a stable-ordinal-indexed dedup pass afterward (per §14.3 pattern) rather than mutating shared state from concurrent tasks.

### Good candidates for Rayon (pure, independent, stable-ordinal-indexable)

- **Crop enumeration across `(rows, traversal, corner)` combinations** (`enumerateIntrinsicPeriodicCellCrops`, `CELLS:707-809`, §5 item 13) — each `(rows, traversal, corner)` combination is a **fully independent, pure computation** given `(cell, familyMembers)`: it builds its own fresh `placed` array, does not read or write anything outside its own iteration, and only interacts with the outer scope by pushing into `candidates`/`identities` on success. This is the concrete instance the migration prompt (§14.1) names directly: *"independent periodic-cell candidate evaluation with stable catalog indices."* A Rayon port must: (1) enumerate the exact same ordered list of `(rows, traversal, corner)` ordinals serially first (matching `CELLS:726-730`'s triple loop exactly), (2) evaluate each ordinal's candidate (legal-or-not, and if legal, its `canonicalKey`/seed) in parallel, (3) then **replay the original ordinal order serially** to perform the `identities.has(...)` first-write-wins dedup and build `candidates` in the documented order (§5 item 13's "first triple-loop iteration to reach a given canonical identity wins" rule is order-sensitive and must be resolved after the parallel phase, not folded into it).
- **`deriveEdgeContactBasisCandidates`'s 4-level relation-discovery loop** (`CELLS:1257-1312`) — for a fixed `members` array, each `(fixedMemberIndex, movingMemberIndex, fixedEdge, movingEdge)` combination independently computes candidate vectors and calls `validateEdgeContactRelation`, whose own legality simulation is self-contained (builds its own `placed` array from `members` each time, §9). The **reduction into `relations: Map`** (max-by-length-then-min-by-key, §4) is a well-defined associative-enough reduction that could be computed by evaluating all combinations in parallel (indexed by a stable `(fixedMemberIndex, movingMemberIndex, fixedEdge, movingEdge, candidateIndex)` ordinal) and then serially folding into the map in the documented tie-break order — but note the reduction is **not simply commutative for ties**: the tie-break compares `edgeContactProvenanceKey(...)` lexicographically, which is well-defined regardless of fold order, so a parallel map-reduce with a deterministic per-key combine function *is* safe here, unlike the continuation-selection dedups above which depend on encounter order, not just key comparison.
- **Per-representative-transform P1 cell derivation** (`CELLS:426-444`) — each transform representative's `deriveCells` call is independent of every other representative's (no shared mutable state between iterations other than the `rejected`/`rejectedSamples` accumulators, which are pure appends that could be reconstructed from stable-ordinal-indexed parallel results and folded serially afterward, preserving the documented 8-sample-per-call/32-sample-per-family caps by replaying in original order).
- **Per-pair P2 enumeration's outer `(firstIndex, secondIndex)` loop body** (`CELLS:448-502`) is largely independent per pair **except** for the shared `enumeratedPairCount`/`pairCoverageComplete`/`runtimeCoverageComplete` budget counters and the wall-clock deadline checks interleaved throughout (§10) — this is a "good candidate in principle, high-risk in practice" case: the pure NFP/legality/cell-derivation work per pair is independent, but the **counting and early-termination behavior is chronology-bound** (a pair late in iteration order must not be evaluated at all once `maximumPairsPerFamily`/deadline is reached, and `enumeratedPairCount` must reflect exactly how many pairs were *attempted*, not how many were *legal* — `enumeratedPairCount += 1` happens unconditionally per pair before its offsets are even computed, `CELLS:460`). A safe Rayon design here must precompute the exact serial attempt-count/truncation-point first (a cheap, sequential pass), then parallelize only the pure work for the pairs that would have been attempted, never let parallel pairs "race" the truncation decision itself.
- **Independent transform-family NFP/geometry preparation** across families (the outer `selectedFamilies` loop, `CELLS:313-326`) is tempting but **not** independent in the way it looks: the family loop shares a single wall-clock deadline (`startedAt`/`maximumRuntimeMs`) and a `break`-on-timeout early-exit that depends on cumulative time already spent on **earlier** families in the fixed sort order (§5 item 1) — parallelizing across families would change which families get processed at all under time pressure, altering `familyCoverageComplete`/`runtimeCoverageComplete` (production validity gates, §1). This must remain serial at the family-loop level; only the *work inside* each family's processing (the candidates above) is safe to parallelize.

### Why the diagnostic/audit machinery deserves special caution

The source-survival audit and replay-envelope validation (§1, §8) are digest/hash-producing code paths reachable from the live path (audit) or dormant-but-tested (replay). Both build their digest inputs from **already-sorted, deterministic** structures (`eligibleSourceDomainEntries`, `canonicalJson`), so their *hashing* step is a pure reduction safe to leave serial (SHA-256 is cheap relative to the geometry work) — but the **data they hash** must be assembled in the exact documented order first; do not parallelize the assembly of `eligibleSourceDomainEntries`/`sourceCropSurvivalResult`/`sourceAuditWitnessResult` in a way that could nondeterministically interleave with the sorts already specified in §5, since these arrays are hash inputs (§8) and any nondeterministic assembly order upstream of a stable final sort is only safe if the sort's comparator is a true total order with no residual ties — several of these comparators (e.g. `rankIntrinsicPeriodicSeeds`'s reliance on `canonicalKey.localeCompare` as a final tie-break) generally are total orders, but this should be proven per comparator, not assumed, before trusting a parallel-then-sort restructuring.
