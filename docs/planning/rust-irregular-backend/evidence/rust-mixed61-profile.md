# Rust Mixed-61 Hotspot Profile (Release, 1-thread)

**Date:** 2026-07-30
**Branch:** `rust-irregular-backend` @ `04ceaf9c9d49bb2eefff68625d2899a2e942b261` (working tree left uncommitted per task instructions)
**Machine:** Linux 6.18.38 x86_64 (NixOS), Intel(R) Core(TM) Ultra 7 270K Plus, 16 hardware threads,
125 GiB RAM. `rustc 1.97.1 (8bab26f4f 2026-07-14)`.
**Case:** Mixed-61 `2000x2700` Compact (performance-contract.md C1, the primary gate).
**Context:** this task's brief documents Rust 1-thread Mixed-61 = 36.2 s vs TS 45.2 s (~1.25×),

## 1. Methodology

### 1.1 Sampling profiler attempted first, and why it was not usable here

Per the task instructions, `samply` was tried first:

```
$ cargo install samply --locked        # succeeded, v0.13.1
$ cat /proc/sys/kernel/perf_event_paranoid
2
$ samply record --save-only -o /tmp/mixed61-test.json.gz -- ./target/release/examples/run_mixed61
'/proc/sys/kernel/perf_event_paranoid' is currently set to 2.
In order for samply to work with a non-root user, this level needs
to be set to 1 or lower.
```

- No `sudo` password is available in this environment (`sudo -n true` fails); writing
  `/proc/sys/kernel/perf_event_paranoid` directly also fails (`Permission denied`).
- `capsh --print` shows `cap_perfmon`/`cap_sys_admin` only in the *bounding* set, not the
  *effective*/*permitted* set of this unprivileged process — `perf_event_open` is unreachable
  regardless of flags.
- `samply record --help` (v0.13.1) has **no `--no-perf` flag on Linux** (that fallback exists only
  for other platforms' alternative backends); Linux recording is perf-events-only in this version.
- `perf`, `valgrind`, and `ltrace` are not installed, and `nix-shell` cannot install them (read-only
  Nix store in this sandbox: `error: creating directory "/nix/store/.links": Read-only file system`).

Sampling profilers are therefore categorically unavailable in this environment. This falls back to
method 2 from the task brief: temporary, targeted manual instrumentation.

### 1.2 Standalone Rust profiling target (kept)

A new example, `crates/irregular-nesting-native/examples/run_mixed61.rs`, loads a prepared
`NestingRequest` + `IrregularNestingSettings` from
`crates/irregular-nesting-native/tests/vectors/mixed61-2000x2700-compact-request.json` and calls
`result::coordinator::compute_irregular_nesting` directly — a pure Rust process with no Node/N-API/
libuv overhead, giving any future profiler (once `perf_event_paranoid` is fixed, or on a different
host) a clean single-purpose target.

The fixture JSON is generated by the (kept) script
`scripts/rust-parity/dump-mixed61-2000x2700-request.ts`, which **re-serializes the real
`tests/fixtures/irregularSheetInvariance/mixed61-request.json` fixture verbatim** (only overriding
`sheet`→`2000x2700`, a documented no-op since that is already the fixture's own default sheet, and
`historyMode`→`off`) into the plain-JSON shape `tests/coordinator_vectors.rs`'s `decode_request`
expects. This is deliberately **not** a re-run of `preparePieces`/`makeCompactQualityIrregularOptimizerSettings`
from scratch — an earlier version of this script did that (with `padding: 0`) and silently produced
a *different, faster, wrong* case (16.7 s, wrong hash). The final script's output was verified to
reproduce the acceptance-bar hash exactly before being used for any timing:

```
$ ./target/release/examples/run_mixed61
[run_mixed61] run=0 elapsed_ms=32712.5 placed=61 unplaced=0 \
  collision_identity_sha256=3839e80d26be257381f1962816765a886d4b7e3c3d78120892e4a6a943dfa742
```

matches the acceptance-bar collision-identity SHA-256 (`3839e80d…`) exactly, and
`verify-mixed61-hash.ts` against the same fixture through the real N-API addon independently confirms
both hashes (`3839e80d…` collision, `ef2b783a…` fitted canonical, 61/61 placed) — see §4.

### 1.3 Manual instrumentation (temporary; fully reverted)

`[profile.release] debug = true` was added to `Cargo.toml` for DWARF call-stack resolution (kept
only conditionally — see §5, ultimately reverted). A temporary module
`crates/irregular-nesting-native/src/profiling_temp.rs` implemented a thread-local, stack-based
**exclusive (self-time)** scope profiler: on entering a scope, the parent's elapsed-so-far is flushed
to its own counter and its clock reset; on leaving (via `Drop`), the scope's own elapsed time is
flushed and the parent's clock resumes. This yields self-time per bucket (excluding time spent in
nested instrumented buckets), matching how the TS `--cpu-prof` self-time percentages in
`baseline-evidence.md` were read — not inclusive/wall time.

Seven single-line entry points (marked `// PROFILE_TEMP`, all now removed) were instrumented, chosen
to align with `baseline-evidence.md`'s TS CPU-profile categories:

| Bucket | Instrumented function |
| --- | --- |
| NFP/IFP candidates | `nfp_ifp::service::generate_placement_candidates` |
| Search/decode orchestration | `archive::shared::run_intrinsic_shared_archive_direct_portfolio` |
| Canonical keys | `search::beam_state::canonical_ring_key` (the module's own doc: "the single most important algorithm in this cluster ... feeds every canonical key used for state dedup throughout the live production search") |
| Validation | `validation::placement::assess_placement` |
| Clipper | `clipper::engine::boolean_op` + `clipper::offset::ClipperOffset::execute` |
| Spatial index | `validation::spatial_index::PlacedCollisionSpatialIndex::query` |
| Scoring | `search::placement_scorer::score_candidate` |

Instrumentation overhead was measured at ≈0.5% of wall-clock (comparing instrumented vs. clean runs
at matching system load — see §2), too small to distort the ranking.

**Cleanup:** every `PROFILE_TEMP` call site was removed, `profiling_temp.rs` was deleted, its `pub
mod` line removed from `lib.rs`, and the `report()` call removed from the example
(`grep -rn PROFILE_TEMP crates/irregular-nesting-native` is empty; `git status` after cleanup shows
only the intended new files — the example, the fixture, the dump script — plus files being edited
concurrently by an unrelated agent sharing this host, listed and excluded in §6).

### 1.4 A note on shared-host contention

This sandbox is shared with at least one other concurrently running agent (observed editing
`archive/periodic_family.rs`, `js_number/js_math.rs`, `search/strict_decoder.rs`, and two TS files
unrelated to this task, and running its own `cargo test --release` mid-session — confirmed via `ps`
and a `cargo` build-lock wait). One measurement batch coincided with that agent's build/test load
(load average 12.18/16 cores) and produced inflated, unusable wall-clock samples (38.3 s, 42.4 s) for
a `debug=true`-only run. A repeat at load average 2.43 reproduced the original clean baseline exactly
(32712.5 ms vs. 32714.8–32728 ms). All **ranked hotspot percentages** below come from three
back-to-back runs during a quiet period (load average ≤ ~3, no concurrent build in progress) and are
mutually consistent (elapsed 32914.8 / 32880.6 / 32942.3 ms; every bucket within ≈1% of its mean
across the three runs) — see §2.

## 3. Comparison against the TS CPU-profile baseline

`baseline-evidence.md`'s Mixed-61 TS `--cpu-prof` self-time breakdown (41,972 samples, 45.5 s):

| TS category | TS share | Rust analogue here | Rust share |
| --- | ---: | --- | ---: |
| NFP/IFP candidate generation | 29.6% | `generate_placement_candidates` | 13.2% |
| search / decoders / portfolios | 14.4% | `run_intrinsic_shared_archive_direct_portfolio` (self) | 31.8% |
| beam-state canonical keys | 12.9% | `canonical_ring_key` alone | 25.3% |
| placement validation / convex predicates | 6.8% | `assess_placement` | 1.9% |
| clipper2 | 4.8% | `boolean_op` + offset `execute` | ~0.0% |
| spatial index | 3.9% | spatial-index `query` | 1.6% |
| GC / Effect runtime (TS-only, no Rust equivalent) | 13.4% | — | — |

Two divergences stand out and are the strongest concrete leads for optimization:

- **Canonical keys are proportionally ~2× hotter in Rust than in TS** (25.3% vs. 12.9% for the whole
  category, and vs. only 3.1% for `canonicalRingKey` specifically in TS's own top-functions list).
  Since `canonical_ring_key` is called 4.94M times, even a small fixed per-call allocation/formatting
  cost compounds heavily — see Top-5 candidate #1 below.
- **Search/decode orchestration self-time (31.8%) is proportionally ~2.2× TS's 14.4%.** Only 74.8% of
  total time was attributed to specific functions in this pass; the remainder sits inside
  `construct_intrinsic_strict_state`'s own body and its many un-instrumented helpers. This needs a
  second, finer instrumentation pass (or a working sampler) before drawing firm conclusions, but see
  candidate #2 below for plausible contributors already visible in the source (BigInt/i128 grid math,
  `Arc`/`Vec` cloning per candidate, string-comparator-based dominance sorting).
- NFP/IFP candidate generation is proportionally *less* hot in Rust (13.2% vs. 29.6%) — plausibly
  because the Rust NFP/IFP memo (`LegalCandidateMemo`) is at least as effective as TS's, and/or
  Clipper-based offsetting (row 7, ~0%) is essentially free here, unlike TS's `clipper2` (4.8%).

## 5. `debug = true` decision

`[profile.release] debug = true` was added to enable DWARF symbols for `samply`, since `debug`-level
DWARF emission does not change LLVM codegen decisions (well-established: it only controls whether the
codegen backend also emits debug metadata alongside the same optimized machine code). However, given
`samply` turned out to be unusable in this environment (§1.1) and a clean, contention-free
before/after wall-clock comparison could not be obtained in this shared-host session (§1.4), **`debug
= true` was reverted** rather than kept on unverified evidence. `Cargo.toml` is back to its original
state (`codegen-units = 1`, `lto = "thin"`, `overflow-checks = true`, no `debug` key). A future
profiling session on a quiet/private machine can re-add it and confirm neutrality before keeping it.
